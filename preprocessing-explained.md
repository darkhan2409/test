# Препроцессинг простыми словами

Разбор того, что мы построили: зачем, как, и на чём спотыкались.

---

## Часть 1. Что вообще происходит

### Задача одной картинкой

Банк хранит данные в разных системах, и все они «грязные» — разные форматы,
опечатки, пропуски, дубли. Модель такое есть не может.

```
грязные данные из 5 систем банка
        ↓
   ПРЕПРОЦЕССИНГ        ← это то, что мы строим
        ↓
   чистые данные
        ↓
   ТОКЕНАЙЗЕР           ← следующий этап
        ↓
   числа для модели
```

### Простой пример: как выглядит грязь

Одна транзакция, как она лежит в системе платежей:

```
client_ref     = "000123"
operation_time = "15.01.2026 14:30"
amount         = "15 000,50"
currency       = "тенге"
```

Проблемы, которые тут есть:

- **сумма — не число, а строка** с пробелом и запятой
- **валюта написана словом**, а в другой системе будет `KZT`, в третьей `398`
- **время в местном формате**, а нужно единое
- **ID клиента** свой у каждой системы

Задача препроцессинга — превратить это вот в такое:

```json
{
  "client_id": "C000123",
  "event_id": "3237ced6a1b2c3d4e5f60718293a4b5c",
  "event_type": "TRANSFER",
  "timestamp_utc": "2026-01-15T09:30:00Z",
  "fields": {
    "amount_base_bucket": "bucket_17",
    "currency": "KZT"
  },
  "calendar_time_features": {
    "hour_of_day_local": 14,
    "day_of_week_local": 3
  }
}
```

## Часть 2. Словарик

Термины, которые встречаются постоянно.

| Термин | Что это простыми словами |
|---|---|
| **Событие** | Одно действие клиента: перевод, вход в приложение, снятие наличных |
| **Профиль** | Что известно о клиенте: регион, работает или нет, как давно с банком |
| **Cutoff T** | Дата отсечки. Берём только то, что было **до** неё |
| **Бакет (корзина)** | Диапазон вместо точного числа. Не «15 000,50», а «от 10 до 50 тысяч» |
| **MISSING** | Пометка «значения нет». Не ноль! Ноль может быть настоящей суммой |
| **Карантин** | Куда откладывают брак вместо того, чтобы молча выкинуть |
| **Хэш** | «Отпечаток» данных. Одинаковые данные → одинаковый отпечаток |
| **Детерминизм** | Одинаковый вход всегда даёт одинаковый результат. Всегда. Везде |
| **BUILD** | Разовый расчёт правил на обучающих данных (например, границ корзин) |
| **ENCODE** | Применение этих правил ко всем данным |
| **Golden-векторы** | Замороженный эталон: вот вход, вот что обязано получиться |

### Три слова, которые легко путать

Это самая частая путаница, поэтому отдельно:

| | Когда |
|---|---|
| **MISSING** | Значения нет вообще. Клиент не указал регион |
| **RARE** | Значение было, но редко. Магазин встретился 3 раза за год |
| **[UNK]** | Значение новое, при обучении такого не видели |

`MISSING` делает препроцессинг. `RARE` и `[UNK]` — токенайзер, потом.

### Зачем нужен cutoff T

Представь: учим модель предсказывать, уйдёт ли клиент. Обучаем на данных
за январь, а в признаки случайно попало февральское событие «клиент закрыл счёт».

Модель «угадает» идеально — но не потому что умная, а потому что подсмотрела
ответ. В бою так не будет, и модель провалится.

Cutoff T — черта, за которую заглядывать нельзя.

### Зачем нужны корзины

Модель не может работать с бесконечным количеством разных чисел. Ей нужны
категории.

```
15 000,50 ₸  →  bucket_17  (диапазон 10 000 – 50 000)
```

Границы корзин считаются **один раз** на обучающих данных, потом замораживаются.

## Часть 3. Одна транзакция через весь путь

Вот та самая грязная запись. Смотрим, что с ней делает каждый компонент.

### Этап 2, шаг за шагом

**2.1 SourceReader — прочитать и проверить формат**

Смотрит паспорт системы (Source Contract) и сверяет: те ли колонки, те ли типы.

```
на входе:  {"client_ref": "000123", "amount": "15 000,50", ...}
на выходе: то же самое, но проверенное
```

Важно: он **не чинит** данные. `"abc"` вместо суммы проходит дальше живым —
чинить числа это работа другого компонента. Если зарубать сразу, все краевые
случаи умрут на первом шаге и никогда не проверятся.

**2.2 IdentityResolver — опознать клиента**

В платежах он `client_ref = "000123"`, в картах `cardholder_id = "CH000005"`,
в CRM `cif = "CIF000002"`. Это один человек.

```
"000123" → C000005
```

**2.3 TimestampNormalizer — привести время**

```
"15.01.2026 14:30" (Алматы)  →  2026-01-15T09:30:00Z (UTC)
                                 + зона Asia/Almaty
```

Зона хранится **именем**, а не смещением. Почему — см. проблему №1 ниже.

**2.4 CutoffFilter — отсечь будущее**

```
T = 2026-01-31
событие 15 января  →  проходит
событие 5 февраля  →  отбрасывается
```

Отброшенное — **не брак**. Оно не идёт в карантин, просто вне окна наблюдения.

Реальные числа: 76 797 → 74 447 (отброшено 2 350).

**2.5 Deduplicator — убрать дубли**

Три вида:

```
точный дубль:  одна запись пришла дважды        → оставить одну
бизнес-дубль:  разные номера, один и тот же факт → оставить одну
конфликт:      один номер, РАЗНЫЕ данные внутри  → опасно!
```

Конфликт разрешается только по объявленному правилу. Нет правила →
**обе записи в карантин**, ни одна не проходит.

Реальные числа: 74 447 → 74 444 (убрано ровно 3, те самые что подложил генератор).

**2.6 EventMapper — определить тип события**

```
op_code "TRF"  →  event_type = "TRANSFER"
```

Плюс здесь появляется `event_id` — стабильный отпечаток записи.
Прогони обработку дважды — получишь тот же id.

Реальные числа: 28 591 событие, все id уникальные.

**2.7 Sessionizer — свернуть клики в сессии**

```
screen_open, button_click, screen_open, form_submit ...
        ↓
одно событие APP_SESSION
(длительность, число экранов, путь по приложению)
```

Реальные числа: 39 053 действия → 2 502 сессии.

**2.8 FeatureSchema + MISSING — разложить по местам**

Каждое поле встаёт на своё место по схеме. Нет значения → `MISSING`.

```
direction отсутствует  →  MISSING
```

**2.9 CategoryNormalizer — причесать категории**

```
"  тенге  ", "kzt", "398", "ТЕНГЕ"  →  KZT
```

Реальные числа: 12 разных написаний валюты → 4 значения.

**2.10 NumericValidator — превратить строку в число**

```
"15 000,50"  →  15000.50
"abc"        →  MISSING (не ноль!)
NaN          →  MISSING
-1 (возраст) →  MISSING (вне допустимого диапазона)
```

**2.11 FXNormalizer — привести к тенге**

Берёт **исторический** курс на дату события, а не сегодняшний.

```
1250 USD, 15.01.2026, курс 498.3835  →  636 633.25 ₸
```

Если курса нет — берётся последний доступный, но не старше 3 дней.
Совсем нет → сумма `MISSING`, но **событие не удаляется**: покупка была,
независимо от того, смогли ли мы пересчитать.

**2.12 DeterministicSampler — выбрать образец**

Чтобы посчитать границы корзин, не нужны все 76 тысяч записей — хватит выборки.
Но выборка должна быть **одинаковой** при любом числе процессов.

**2.13 Bucketizer — разложить по корзинам**

```
15000.50 ₸  →  bucket_17
```

Границы считаются один раз, на обучающих данных, потом замораживаются.

Готово для 11 полей: сумма (64 корзины), зарплата (32), длительность (32),
экраны (8), возраст (16), плюс шесть life-long.

**2.14 FieldPolicies — политики полей**

Убирает технические ID, режет длинные списки.

```
merchant_id, atm_id  →  исключены (15 406 значений)
список экранов       →  обрезан до 8
```

**2.15 ProfileBuilder — собрать профиль**

Берёт последний снимок профиля до T плюс считает **life-long признаки** —
то, что описывает всю жизнь клиента:

```
account_age              = 1053 дня   → bucket_23
lifetime_event_count     = 47         → bucket_14
lifetime_product_count   = 2          → bucket_2
```

Зачем: модель видит не всю историю, а последние N событий. Если клиент с нами
3 года, а в окно попали последние 20 действий — модель не узнает, что он старый.
Life-long признаки это компенсируют.

Реальные числа: 5 549 снимков → 200 профилей.

**2.16 TimelineBuilder — выстроить хронологию**

Все события клиента в правильном порядке. При одинаковом времени —
детерминированный tie-break (приоритет источника, потом номер записи).

**2.17 TimeFeatureBuilder — календарные признаки**

```
2026-01-15T09:30:00Z + Asia/Almaty  →  час 14, день недели 3
```

Плюс флаг `lifetime_first` на самом первом событии клиента.

### Что получилось на выходе

```
76 797 сырых записей
   ↓
31 093 события у 199 клиентов
+ 200 профилей
+ 1 запись в карантине
```

## Часть 4. Что делали ДО этого

### Этап 0 — фабрика фейковых данных

Нельзя отлаживать обработку, если нечего обрабатывать. Поэтому сначала —
генератор синтетики.

Что он делает:
- 200 клиентов, 5 систем-источников, 76 797 записей
- **нарочно разные форматы** у источников — это и проверяет Source Contract
- специально подкладывает **32 вида брака**

Зачем брак: чтобы проверить, что пайплайн его ловит. Примеры того, что
подкладывается:

```
"abc" вместо суммы
одна транзакция записана дважды
два события с одинаковым временем
сумма в долларах, а курса на эту дату нет
клиент вообще без событий
событие ровно на границе T
```

Каждый случай записан в отдельный список: «клиент №7 — это тот, у кого дубли».

**Умное решение:** если какой-то брак не удалось внедрить — сборка **падает**.
Иначе можно думать «я проверил обработку дублей», а дублей в данных нет —
проверка была пустышкой.

Плюс отдельный маленький набор `golden_input` (12 клиентов, 2 394 записи) —
замороженный эталон для проверок.

### Этап 1 — фундамент

Не обработка данных, а «служебный слой», на котором всё стоит.

| Что | Зачем |
|---|---|
| Сериализация | Записывать данные в файл **всегда одинаково**, до байта |
| Хэши | Стабильные отпечатки и ID |
| Настройки | Параметры проекта |
| Карантин + счётчики | Куда девать брак и как его считать |
| Модели данных | Описание, как выглядит правильное событие |
| Debug-режим | Сохранять промежуточные шаги для будущего UI |

**Решение, которое стоит понять — разделение настроек на две кучи.**

```
ПРАВИЛА (идут в хэш):     дата T, seed, пороги
ОБСТАНОВКА (не идут):     путь к папке, число процессов, debug
```

Зачем так. Если бы путь к папке попал в хэш:

```
ты запускаешь:      C:\Users\darkhan\...   → хэш А
коллега запускает:  D:\projects\...        → хэш Б
```

Данные те же, результат тот же, а хэши разные → проверка воспроизводимости
падает на ровном месте.

Обратная беда: если дату T **не** класть в хэш — можно незаметно поменять
правило обработки, и никто не заметит.

## Часть 5. Реальные проблемы, которые всплыли

Самое поучительное. Ни одну из них нельзя было предвидеть на бумаге.

### Проблема 1. Два места по-разному считали границу по дате

**Что произошло.** Первый прогон дал 197 клиентов вместо 199.

**Причина.** Отсечка по дате T делалась в двух местах кода. Одно считало
полночь по UTC, другое — полночь по Алматы. Разница 5 часов.

```
снимок "1 февраля"
  по UTC:     1 февраля 00:00 UTC     → после T, отбросить
  по Алматы:  31 января 19:00 UTC     → до T, оставить
```

Один и тот же снимок в одном месте попадал в окно, в другом — нет.

**Почему опасно.** Ничего не падало. Просто два клиента тихо терялись.
Нашлось только потому, что сверили число клиентов с ожидаемым.

**Класс ошибки:** *два места реализуют одно правило по-разному*.
Не проявляется, пока правило не поменяют в одном из них.

**Как чинили.** Свели к одной реализации + тест, который сравнивает
результаты обоих мест.

### Проблема 2. Брали первое попавшееся описание поля

**Что произошло.** Первый прогон 2.10 дал **22 391 ошибку разбора** из 38 тысяч.

**Причина.** Функция возвращала первое описание поля с таким именем.
Для суммы первым шёл карточный процессинг — там суммы **целым числом в тиынах**
(`1058283`). Этим описанием разбирались и суммы из платежей, где
**строка в тенге** (`"370 247,74"`).

**Как чинили.** Добавили выбор описания по конкретному источнику.

**И важное продолжение.** Он сначала написал в комментарии «эту функцию
не надо использовать для таких полей». Но комментарий ничего не запрещает.
Переделали так, что функция **физически не возвращает** эти поля —
ошибиться стало невозможно.

### Проблема 3. Seed не работал

**Самая красивая ошибка проекта.**

**Что произошло.** Есть настройка `seed` — чтобы можно было сказать
«прогони ещё раз с другим seed и посмотри, изменится ли результат».

Не менялось **ничего**. При двух соседних значениях seed выборка совпадала
на 500 записей из 500.

**Причина.** `seed = 20260101` — маленькое число, занимает только хвостик
длинного 64-битного числа. А выбор записей решался по **началу** этого числа,
куда seed не доставал.

**Почему тесты не поймали.** Они проверяли «seed влияет на результат» —
влияет, галочка. А надо было проверять «влияет **достаточно**».

Похоже на: проверили, что руль поворачивается, но не проверили,
что колёса при этом двигаются.

**Как чинили.** Seed сначала «размазывается» по всем битам, потом применяется.

**Урок.** Эта формула была помечена как «уверенность средняя» — придумана
нами, а не взята из регламента. Ровно там ошибка и нашлась.
**Помечать неуверенность работает.**

### Проблема 4. Порядок цепочки был кривым

**Что произошло.** Регламент требует разложить по корзинам признаки вроде
«возраст аккаунта» и «сколько всего транзакций». Но по порядку цепочки эти
признаки считаются **после** того, как корзины уже посчитаны.

То есть в момент расчёта границ таких значений ещё не существует.

**Как чинили.** Переставили: считать профиль **раньше** бакетизации.
Проверили, что это безопасно — life-long признаки считаются из дат и счётчиков,
ни один не зависит от корзин.

**Красивая проверка.** Он не написал «правило соблюдено». Он взял старый скрипт,
где профиля нет, и запустил. Тот **упал сам**:

```
BucketizationError: account_age_bucket: в TRAIN-выборке
                    нет ни одного валидного значения
```

Правило доказало себя тем, что сломалось при нарушении.

### Похожие дырки в регламенте (не баги, а нестыковки)

Регламент писался «сверху», а на реализации всплыли места, где правила
противоречат друг другу:

| Где | В чём нестыковка |
|---|---|
| §29.1 vs §5 | Правило: id события = 32-символьный хэш. Примеры: `evt_1` |
| §9 vs §37.2 | Дубли удаляются **до** приведения валют — значит одну покупку из двух систем не опознать |
| §19.6 vs §29 | Предписан алгоритм, который **не может** удовлетворить требование о независимости от числа процессов |
| §24 vs §37.2 | Требует бакетизировать значения, которых на момент бакетизации ещё нет |
| §34 vs §33 | Две причины карантина не имеют счётчика |

Всё записано, регламенты дополняются.

## Часть 6. Приёмы, которые появились по ходу

### Приём 1. Запрещать не проверкой, а отсутствием возможности

**Два способа что-то запретить.**

Способ А — проверка:
```
если тип поля == "текст":
    ошибка "текст запрещён"
```
Работает. Но проверку **можно забыть написать** в новом месте.

Способ Б — убрать возможность:
```
типы полей: число, категория, бакет
```
Текстового типа просто нет в списке. Объявить текстовое поле **невозможно**.

**Аналогия.** Способ А — повесить табличку «сюда не заезжать».
Способ Б — не строить дорогу.

Где применили:
- нет текстового типа → свободный текст не объявить
- нет типа «по умолчанию» → неизвестный код не получит левый тип
- нет варианта «завести категорию» → свалки не существует
- у бакетизатора нет метода «посчитать границы» → он их только применяет
- нет ветки «зоны нет → считаем по UTC» → правдоподобно-неверный ответ невозможен

### Приём 2. Мутационная проверка

**Проблема.** Ты написал тест. Он зелёный. Но откуда ты знаешь, что он
**правда что-то проверяет**?

**Решение.** Специально сломай код и посмотри, заорёт ли тест.

```
сломал код → тест упал   → тест рабочий, вернуть код обратно
сломал код → тест молчит → ТЕСТ ПУСТЫШКА
```

**Аналогия.** Купил пожарную сигнализацию. Она не пищит — значит пожара нет?
Или батарейка села? Единственный способ узнать — поднести зажигалку.

### Что нашла мутационная проверка

Три раза попались **вырожденные тестовые данные** — когда данные подобраны так,
что проверять нечего:

| Где | В чём вырожденность |
|---|---|
| Порядок файлов | Windows сам отдаёт файлы отсортированными → убери сортировку из кода, тест не заметит |
| Порядок экранов | Экраны назывались `SCREEN_01..12` — уже по алфавиту. Хронология и алфавит совпадали |
| Порядок событий | Номер записи рос вместе со временем → третий ключ сортировки в одиночку воспроизводил хронологию |

Плюс нашлось, что главное свойство карантина («забыть метрику невозможно»)
было **заявлено в комментарии и не покрыто ни одним тестом**.

**Вывод:** свойство, которое ты называешь гарантией, обязано иметь тест.
Иначе это не гарантия, а намерение.

### Приём 3. Прогон на данных находит то, чего не находят тесты

Все четыре архитектурные проблемы выше нашлись **прогоном на полном наборе**,
а не тестами.

Логика простая: **тесты проверяют то, что ты придумал проверить.
Прогон показывает то, что ты не придумал.**

### Приём 4. Не подгонять под метрику

Одна мутация выжила честно — оказалось, что она ничего не меняет на текущих
данных. Можно было придумать искусственный источник, чтобы её «убить»
и получить красивые 38 из 38.

Не стали. Как только начинаешь подгонять код под метрику, метрика перестаёт
что-либо значить.

## Часть 7. Что отложено

Механизмы, которые сознательно не реализованы.

**Ждёт боевых данных** (разблокируется само):
- слияние клиентов
- отмена операций (reversal)
- дубли между разными системами

**Ждёт решения бизнеса** (данные не помогут):
- `top_intent` — нужен утверждённый справочник «экран → намерение»

Принцип один: **непроверенный механизм опаснее отсутствующего**.
В синтетике таких случаев нет, проверить не на чем — значит писать нельзя.
