# Этап 2, часть Б — поля и значения (2.8–2.14)

Компоненты 8–14 цепочки §37.2. К этому моменту запись уже стала событием: у
неё есть клиент, время, тип и `event_id`. Дальше меняется **содержимое полей**.

```
событие с сырым payload
  →  8 FeatureSchemaRegistry  разложить по объявленным полям, пропуск → MISSING
  →  9 CategoryNormalizer     "  тенге ", "kzt", "398" → KZT
  → 10 NumericValidator       "25,99" → 25.99, "abc" → MISSING
  → 11 FXNormalizer           25.99 EUR → 12075.4738 KZT по курсу на дату
  → 12 DeterministicSampler   набрать выборку для расчёта границ (ничего не меняет)
  → 13 Bucketizer             12075.4738 → bucket_37
  → 14 FieldPolicies          убрать технические ID, обрезать длинные списки
```

**Сквозная мысль этой части:** имя поля задаётся один раз и не меняется, а
значение под ним меняет форму четыре раза. В `amount_base_bucket` лежит
сначала `"25,99"`, потом `Decimal("25.99")`, потом `Decimal("12075.4738")`,
и только потом `"bucket_37"`.

## 2.8 FeatureSchemaRegistry — разложить по объявленным полям

### Что за задача

Здесь запись перестаёт быть «тем, что прислал источник», и становится набором
**объявленных** признаков. Что не в схеме — того для модели не существует.

Плюс главное различие §15: применимо, но значения нет → `MISSING`; неприменимо
→ ключа нет вовсе.

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `config/feature_schema.yaml` | появился | 504 строки: какие поля у каких типов событий |
| `src/preprocessing/schema/feature_schema.py` | появился | модель схемы и её инварианты |
| `src/preprocessing/feature_projection.py` | появился | применение схемы и MISSING policy |

### Что внутри каждого файла

**`feature_schema.py`** — восемь моделей.

`FieldSpec` (`:130`) — описание поля: имя, `source_field`, тип, политика
словаря, `required`, `domain`, `priority`, плюс необязательные `computed`,
`multivalue`, `order_significant`, `max_values_per_field`, `model_input`,
`fx_normalized`, `currency_field`, `numeric`, `high_cardinality`.
Валидатор `_check_consistency` (`:189`) — четырнадцать правил.

`SharedFieldSpec` (`:288`) — то же описание **без** `source_field`, `numeric`,
`priority` и `required`.

`FeatureSchema` (`:384`) — вся схема. `_check_schema` (`:394`) сверяет
одноимённые поля между типами событий.

`section_specs(section)` (`:444`) — единственный корректный способ добраться до
`numeric` и `source_field`. `field_specs()` (`:431`) — только общая часть.

**`feature_projection.py`** — `MissingPolicy` (`:50`): что считается пропуском.
`FeatureProjector.project` (`:206`), `_value_of` (`:266`) — решение §15.1.
`load_feature_schema` (`:138`) сверяет схему с утверждённым списком типов.

### Ключевые решения и почему именно так

**1. Имена полей конечные, форма значения — нет**
(`config/feature_schema.yaml:1-8`).

Поле называется `amount_base_bucket` с самого начала, хотя бакетом станет
через пять шагов. *Иначе:* переименование в середине цепочки потеряло бы связь
между сырым значением и его конечным местом, а дампы соседних компонентов
перестали бы сопоставляться.

**2. `source_field` задан на уровне типа события** (`:137-143`).

Одна и та же `amount_base_bucket` приходит из `amount` в ядре платежей и из
`amount_minor` в карточном процессинге. В общую часть описания
(`SharedFieldSpec`) он не входит: источник значения на токен не влияет.

**3. `SharedFieldSpec` существует, чтобы ошибка стала невозможной, а не
задокументированной** (`:288-302`).

Это вторая архитектурная проблема проекта. Функция возвращала **первое**
описание поля с таким именем. Для суммы первым шёл карточный процессинг — там
суммы целым числом в тиынах; этим описанием разбирались и суммы из платежей,
где строка в тенге. Первый прогон дал **22 391 ошибку разбора** из 38 тысяч.

Сначала в комментарии написали «эту функцию не надо использовать для таких
полей». Но комментарий ничего не запрещает. Переделали так, что функция
**физически не возвращает** `source_field`, `numeric`, `priority` и `required`:
обращение к ним даёт ошибку на месте, а не расхождение в числах через два
компонента.

**4. Одноимённое поле обязано совпадать по типу, политике и domain** (`:410`).

Причина не очевидна из §11 и выведена из токенайзера: токен значения имеет вид
`value:<поле>:<значение>` и про тип события **не знает**. Два разных domain у
одного имени дали бы один токен для разных сущностей.

**5. `domain` bucket-поля запрещено объявлять в конфиге** (`:254-262`).

§11.1 говорит «препроцессинг публикует полный domain», §19 считает его по
TRAIN. Объявленный руками, он разошёлся бы с посчитанным при первом изменении
числа бакетов. Загрузчик такой конфиг **отвергает**.

**6. У closed-set поля domain обязан содержать `MISSING`** (`:206-211`).

Токенайзер включает domain в словарь целиком; без `MISSING` пропуск оказался бы
вне словаря и стал бы `[UNK]`.

**7. Тип события без полей в схеме — блокирующая ошибка**
(`feature_projection.py:155-161`).

Это дало бы событие с токеном типа и пустым содержимым — почти наверняка
забытая строка конфига.

**8. `required` трактуется по §15.1** (`:147-154`).

Регламент разницы не проговаривает. `true` — поле применимо к каждой записи
этого типа, отсутствие даёт `MISSING`; `false` — применимо не всегда, тогда
ключа нет вовсе. Без этой трактовки два исхода §15.1 нечем различить.

**9. Список заглушек закрыт** (`feature_projection.py:55-57`).

«Похоже на заглушку» — не критерий: иначе однажды исчезнет настоящее значение.
Утверждённые: `N/A`, `n/a`, `-`, `--`, `НЕТ ДАННЫХ`, `нет данных`.

**10. `computed`-поля здесь пропускаются** (`:226-230`).

Life-long признаки считает ProfileBuilder (2.15). Поставить им `MISSING` тут
значило бы объявить пропуском то, что просто ещё не посчитано.

### Пример на реальных данных

Описание поля из `config/feature_schema.yaml` (событие `CARD_PURCHASE`):

```yaml
- name: merchant_category
  source_field: merchant_category
  type: categorical
  vocabulary_policy: frequency_pruned   # open-set: RARE решает токенайзер
  required: true
  priority: 3
- name: merchant_id
  source_field: merchant_id
  vocabulary_policy: excluded
  model_input: false                    # §22: до модели не доходит
  high_cardinality: exclude
```

Наша запись `CP-000000-00001` после проекции:

```
fields = {"amount_base_bucket": "25,99",   ← ещё строка!
          "currency": "978",               ← ещё код
          "direction": "IN"}
```

Три поля вместо одиннадцати колонок сырой записи: `counterparty_ref`,
`loaded_at`, `payload_version`, `branch_region` в схеме не объявлены — значит
для модели их нет.

Инъекция «нет ключа `direction`» (`CPX-000005-no-direction`): у поля
`direction` в схеме `required: true`, поэтому получается `"direction": "MISSING"`,
а не отсутствие ключа.

### Что сломается, если этого не будет

Модель получит всё, что прислал источник, включая технические поля и
идентификаторы. Пропуски будут выглядеть как пустые строки, и токенайзер
превратит их в отдельный токен `""`.

## 2.9 CategoryNormalizer — причесать категории

### Что за задача

Одна и та же валюта приходит как `KZT`, `kzt`, `тенге`, `ТЕНГЕ`, `398`. Для
модели это должно быть одно значение.

Порядок операций фиксирован: **trim → Unicode NFKC → регистр → alias**.

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `config/category_mapping.yaml` | появился | алиасы и политика нарушения domain |
| `src/preprocessing/category_normalizer.py` | появился | канонизация значений |

### Что внутри

**`ViolationPolicy` (`:64`)** — ровно два значения: `missing` и
`schema_violation`.

**`CategoryMapping` (`:108`)** — версия, умолчания (`trim`, `unicode`, `case`,
`on_violation`), правила по полям.

**`load_category_mapping` (`:122`)** — три проверки: поля справочника
существуют в схеме; **каждое** категориальное поле описано хотя бы пустой
строкой; алиас не ведёт в значение вне `domain`.

**`CategoryNormalizer._normalize_scalar` (`:260`)** — сам порядок операций.
`_canonicalize` (`:283`) — trim, Unicode, регистр.
`_on_violation` (`:295`) — §16.1.

### Ключевые решения и почему именно так

**1. Третьего исхода нет** (`:64-74`).

«Завести новую категорию» нельзя **объявить**: в перечислении такого значения
не существует.

**2. `OTHER` нигде не подставляется.**

§16.3 разрешает его только как утверждённую категорию со стабильным смыслом,
поэтому ошибка нормализации даёт `MISSING`, а не `OTHER`.

**3. Алиас в значение вне domain — блокирующая ошибка загрузки** (`:151-162`).
Это тихая порча closed-set поля.

**4. Цепочки алиасов запрещены** (`:100-104`).
`A → B → C` дал бы результат, зависящий от числа проходов по таблице.

**5. В таблицах только то, что требует перевода**
(`config/category_mapping.yaml`, комментарий к `currency`).

`KZT: KZT` мешал бы отличать в отчёте реальные срабатывания справочника от
совпадений значения с самим собой.

**6. `MISSING` проходит нетронутым** (`:261-263`). Он поставлен §15 осознанно.

**7. Excluded-поля не нормализуются** (`:236-240`). Работа впустую, а тронутое
значение выглядело бы утверждённым.

**8. Пропуск внутри многозначного поля не превращает в `MISSING` всё поле**
(`:254-257`). Остальные значения остаются осмысленными.

**9. Решение о редкости здесь не принимается.** Open-set поле нормализуется и
остаётся как есть: `RARE` и `[UNK]` — работа токенайзера после заморозки
словаря, а здесь про частоты не известно ничего.

### Пример на реальных данных

Наша запись: `"currency": "978"` → канонизация (`978` регистр не меняет) →
алиас `"398": KZT`, `"840": USD`, `"978": EUR` → **`EUR`**.

Подтверждается эталоном: в `prepared_events.json` у события
`CP-000000-00001` стоит `"currency":"EUR"`.

Полная таблица валюты (`config/category_mapping.yaml`):

```yaml
currency:
  aliases:
    ТЕНГЕ: KZT   TENGE: KZT   "398": KZT
    ДОЛЛАР: USD  DOLLAR: USD  "840": USD
    ЕВРО: EUR    EURO: EUR    "978": EUR
```

Пять написаний тенге из генератора (`KZT`, `kzt`, `тенге`, `ТЕНГЕ`, `398`)
сводятся к одному: `kzt` → регистр → `KZT`; `тенге` → регистр → `ТЕНГЕ` →
алиас → `KZT`; `398` → алиас → `KZT`.

### Что сломается, если этого не будет

Словарь токенайзера получит пять токенов вместо одного, и модель будет считать
`тенге` и `KZT` разными валютами. Хуже: `398` из карточного процессинга и `398`
из платежей попадут в разные корзины частот, и часть из них схлопнется в `RARE`.

## 2.10 NumericValidator — превратить строку в число

### Что за задача

Источник присылает `"25,99"`, `"15 000,50"`, `2792228`, `"abc"`, `"NaN"`,
`null`, `-1`. Нужно число — или `MISSING`. Третьего исхода нет.

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `config/feature_schema.yaml` | изменён | блок `numeric` у bucket-полей |
| `src/preprocessing/numeric_validator.py` | появился | разбор и проверка §17 |

### Что внутри

**`_parse_value` (`:96`)** — §17.1: `bool` отвергается, `int` и `Decimal`
проходят, `float` **отвергается**, строка нормализуется NFKC и разбирается по
локали.

**`validate_numeric` (`:139`)** — единственная реализация правил §17, вынесена
из класса, чтобы у правила остался **один** владелец.

**`NumericValidator._validate_one` (`:198`)** — спеки берутся **по секции**.

**`_invalid` (`:233`)** — единственный исход невалидного числа.

### Ключевые решения и почему именно так

**1. Все четыре запрета §17.2 выполнены устройством.**

Единственное, что метод умеет вернуть кроме числа, — `MISSING`. Нуля в коде
нет, `[UNK]` взять неоткуда, бакетов ещё не существует, исключений компонент
не бросает.

**2. Разбор идёт по `Decimal`, а не по `float`** (`:105-108`).

Деньги в двоичной дроби дали бы плавающую границу бакета, а ошибка округления
вскрылась бы только на сравнении хэшей.

**3. Целочисленность проверяется до применения `scale`** (`:152-158`).

Сумма в тиынах целая (`2792228`), а те же деньги в тенге — уже нет
(`27922.28`). Дробная часть у целочисленного поля — не «округлим», а «не то
значение».

**4. `"1,234.56"` — ошибка разбора, а не повод угадать** (`:121-123`).

**5. `bool` не считается числом** (`:98-100`). `True` иначе стал бы суммой в
один тенге.

**6. Business range и clipping разведены явно**
(`schema/feature_schema.py:114-116`).

Первое — значение бессмысленно (`MISSING`), второе — осмысленно, но вне
TRAIN-диапазона (крайний бакет, §19.4).

**7. Правило знака задаётся полю, а не типу** (`:161-163`). Для баланса
отрицательное валидно, для возраста — нет.

**8. Метрики заведены даже там, где §33 их не определяет** (`:236-243`).

§17.2 требует мониторить `numeric_nan_rate` и
`numeric_business_range_error_rate`, а §33 определяет только
`numeric_parse_error_rate`. Метрики заведены **без порогов**: придумывать
пороги за регламент нельзя, а не считать величину, которую он требует считать,
тем более. Это записано как правка регламента.

### Пример на реальных данных

Блок `numeric` для суммы в двух источниках (`config/feature_schema.yaml`):

```yaml
# core_payments: строка в тенге
numeric: {numeric_type: decimal, signed: false, unit: KZT, scale: 1,
          locale: ru_KZ, min_value: 0, max_value: 100000000000}
# card_processing: целое в тиынах
numeric: {numeric_type: integer, signed: false, unit: KZT, scale: 0.01, ...}
```

Разбор на настоящих значениях:

| вход | результат | почему |
|---|---|---|
| `"25,99"` (наша запись) | `Decimal("25.99")` | локаль `ru_KZ`: запятая → точка |
| `"24 534,82"` | `Decimal("24534.82")` | плюс убраны разделители тысяч |
| `2792228` (тиыны) | `Decimal("27922.28")` | целое × `scale 0.01` |
| `"abc"` (`CPX-000005-bad-amount`) | `MISSING` | не разбирается |
| `"NaN"`, `"-Inf"` | `MISSING` | не-конечное значение |
| `null` | `MISSING` | поставлен ещё §15 |
| `-1` (возраст, `NEGATIVE_AGE`) | `MISSING` | `signed: false`, `min_value: 14` |
| `"5 000 000 000,00"` | `Decimal("5000000000.00")` | **валидно**: внутри business range |

Последняя строка важна: `clip_high` — не ошибка разбора. Значение осмысленно и
проходит §17; в крайний бакет его прижмёт §19.

### Что сломается, если этого не будет

Суммы останутся строками и доедут до бакетизации, где сравнение с границами
даст либо ошибку, либо лексикографический бред (`"9"` больше `"10"`).
Классическая замена невалидного числа нулём сдвинула бы все границы бакетов
вниз.

## 2.11 FXNormalizer — привести к тенге

### Что за задача

Сумма в валюте не сравнима с суммой в тенге. Пересчёт идёт по курсу **на дату
события**, а не сегодняшнему.

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `config/fx_config.yaml` | появился | базовая валюта, поля источника курсов, утверждённые поставщики |
| `src/preprocessing/fx_normalizer.py` | появился | построение таблицы курсов и пересчёт |

### Что внутри

**`FxConfig` (`:51`)** — версия, базовая валюта, имена полей источника, список
утверждённых поставщиков.

**`FxRateTable` (`:96`)** — курсы по валютам, два параллельных списка на
валюту: даты и значения. `build` (`:113`) отбрасывает строки неутверждённого
поставщика и считает их (`rejected`, `:107`). `rate_at` (`:162`) — двоичный
поиск «последний не позднее даты».

**`FXNormalizer._convert` (`:263`)** — пять исходов: базовая валюта не
конвертируется; валюта неизвестна → `MISSING`; курса до события нет →
`MISSING`; курс старше лимита → `MISSING`; иначе `сумма × курс`.

**`_missing` (`:304`)** — §18.2 п.5.

### Ключевые решения и почему именно так

**1. Запрет будущего курса структурный** (`:162-173`).

`bisect_right` отдаёт срез строго левее правой границы — взять более позднюю
запись **неоткуда**.

**2. Давность считается в календарных днях, а не в часах** (`:292`).

Курс публикуется на дату, и пятница → понедельник это три дня, а не «три дня
десять часов». По часам обычные выходные съедали бы весь бюджет, и каждое утро
понедельника давало бы `MISSING`.

**3. `fx_max_staleness_days` живёт в настройках, а не в конфиге FX**
(`config/fx_config.yaml`, шапка).

Это доменная политика прогона: она входит в `preprocessing_state_sha256`
вместе с cutoff и seed.

**4. Неутверждённый поставщик в таблицу не попадает, и это считается**
(`:123-127`, `:107-110`).

«Курсов меньше, чем ожидали» не должно выясняться по журналу.

**5. Все четыре предписания §18.2 п.5 выполняются вместе** (`:304-313`):
сумма → `MISSING`, валюта сохраняется, **событие не удаляется**, растёт
`fx_missing_rate`.

Факт покупки состоялся независимо от того, удалось ли пересчитать сумму.

**6. Сумма, уже признанная невалидной, не пересчитывается** (`:267-269`).

### Пример на реальных данных

Наша запись — покупка на 25,99 EUR 11 декабря 2023 года.

Курсы EUR за декабрь (`data/golden_input/fx_rates/2023-12-01.jsonl`):

```json
{"currency":"EUR","rate_date":"2023-12-08","rate_to_kzt":"464.7946","source":"NBK"}
{"currency":"EUR","rate_date":"2023-12-11","rate_to_kzt":"464.6200","source":"NBK"}
{"currency":"EUR","rate_date":"2023-12-12","rate_to_kzt":"464.3976","source":"NBK"}

```

|---|---|---|
| `CPX-000009-fx-usd`, 1 250,00 USD, 17.09.2025 | курс на дату есть | пересчёт, `exact_rate` |
| `CPX-000009-fx-weekend`, 980,50 «доллар», воскресенье | курса нет → берётся пятничный | пересчёт, `fallback_rate` |

Границы бакетов посчитаются по смеси тенге, долларов и евро — 1 000 USD
окажется в том же бакете, что 1 000 KZT. Если же брать сегодняшний курс,
результат обработки станет зависеть от **даты запуска**, что §29 запрещает
прямо.

## 2.12 DeterministicSampler — выбрать образец

### Что за задача

Чтобы посчитать границы бакетов, все 76 тысяч записей не нужны — хватит
выборки. Но выборка обязана быть **одинаковой** при любом числе процессов.

Компонент прозрачный: он ничего не меняет в записях, только смотрит.

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `src/preprocessing/sampler.py` | появился | priority sampling и слияние выборок |
| `src/preprocessing/core/settings.py` | изменён | `bucket_sample_size` — политика, не окружение |

### Что внутри

**`SAMPLING_ALGORITHM` (`:41`)** — описание алгоритма словами, пункт перечня
§31: имя, что выбирает, откуда ключ, чем разрешается совпадение, что
исключается, от чего результат **не** зависит, и почему не reservoir.

**`FieldReservoir` (`:83`)** — выборка по одному полю: `k` значений с
наименьшим ключом. `offer` (`:93`), `merge` (`:99`), `_compact` (`:110`).

**`DeterministicSampler` (`:128`)** — `consume` (`:152`) пропускает поток через
себя, `offer` (`:162`) считает ключ записи и предлагает значения.

**`sample_key` (`:207`)** — у события это `event_id`, у записи без события —
ссылка на строку источника.

### Ключевые решения и почему именно так

**1. Priority sampling вместо классического reservoir.**

Это **противоречие внутри регламента**, а не выбор из вкуса. §19.6 предписывает
алгоритм («deterministic reservoir sampling»), §29 п.5 требует свойство
(«выборка не зависит от числа воркеров»). Классический алгоритм R этому
свойству удовлетворить **не может**: он идёт по потоку и на каждом шаге
бросает жребий из одного общего генератора.

Здесь каждая запись получает ключ только из себя и `global_seed`, а в выборку
идут `k` наименьших. Результат равен `sorted(все ключи)[:k]` — и §29 п.5
становится арифметическим фактом, а не свойством, за которым надо следить.

**2. Слияние воркеров — то же взятие `k` наименьших** (`:99-108`).

Значения, отброшенные при уплотнении буфера, потерять нельзя: каждое из них
больше всех `k` оставшихся.

**3. Совпадение приоритетов разрешается ключом записи** (`:76-80`).

**4. `MISSING` в выборку не попадает** (`:171-172`), и отсеивается **здесь**, а
не в §19: к моменту расчёта границ уже не из чего понять, почему значения нет.

**5. Сырое значение в выборку не пускается вовсе** (`:174-180`).

Не `MISSING`, а **ошибка**: сэмплер работает после NumericValidator, и молча
пропустить неразобранное число значило бы посчитать границы по части данных.

**6. Формула seed исправлена на шаге 2.12, и это самая красивая ошибка
проекта.**

Первая версия делала простой XOR с `global_seed` и прошла все тесты. Замер на
20 000 ключей: два соседних seed давали пересечение выборок **500 из 500** — то
есть «повторим с другим seed» давало тот же самый эксперимент. Причина:
`20260101` занимает 25 младших бит, а порядок задают старшие. После умножения
на нечётную константу золотого сечения — **0 из 500**.
`hash_policy_version` → `1.1.0`.

### Пример на реальных данных

Отдельного файла у выборки нет — она живёт внутри BUILD. Наблюдаемый результат
описан в `sampler.summary()` (`:193`): по каждому полю `seen`, `selected`,
`truncated`.

`bucket_sample_size` = 50 000 (`core/settings.py:80`), и на текущем объёме
выборка ничего не отсекает: значений на поле десятки тысяч. Флаг `truncated`
(`:122`) как раз и говорит, применялась ли выборка вообще, — если нет,
«выборка» это все данные.

Описание алгоритма, которое уезжает в артефакты §31:

```json
{"name": "priority_sampling", "selects": "k_smallest_by_key",
 "key_source": "record_key_and_global_seed",
 "tie_break": "record_key",
 "excludes": ["MISSING", "значения, не прошедшие §17"],
 "independent_of": ["число воркеров", "порядок записей", "порядок завершения задач"]}
```

### Что сломается, если этого не будет

Границы бакетов станут зависеть от числа процессов: 1 воркер и 4 воркера дадут
**разные** артефакты, и §29 п.10 провалится. Причём выяснится это на этапе 4, а
причина будет выглядеть как «что-то с параллельностью».

## 2.13 Bucketizer — разложить по корзинам

### Что за задача

Число превратить в метку. `12075.4738` → `bucket_37`. Границы считаются
**один раз** на TRAIN (BUILD) и замораживаются; ENCODE их только применяет.

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `config/bucketization.yaml` | появился | метод и число бакетов по полям |
| `src/preprocessing/bucketizer.py` | появился | расчёт границ (BUILD) и разметка (ENCODE) |
| `src/preprocessing/core/quantiles.py` | появился на 3.2 | арифметика границ, общая с §25.2 |

### Что внутри

**`BucketMethod` (`:55`)** — только реализованные: `quantile` и `equal_width`.

**`FieldEdges` (`:118`)** — границы одного поля: метод, запрошенное число,
сами границы, `min_train`, `max_train`, размер выборки.
`bucket_count` (`:132`) — **фактическое** число.
`domain()` (`:139`) — метки плюс `MISSING`.
`bucket_of(value)` (`:148`) — `bisect_right`, интервалы левозамкнутые.
`intervals()` (`:152`) — метаданные для декодирования, крайние интервалы
открыты.
`as_state()` (`:185`) — границы **строками**.

**`BucketEdges` (`:207`)** — артефакт BUILD целиком.

**`fit_bucket_edges` (`:259`)** — функция, а не метод класса.

**`Bucketizer` (`:342`)** — применение. Метода `fit` **нет**.
`_label_of` (`:389`) считает clipping отдельно;
`_check_domain` (`:419`) — §33.4.

### Ключевые решения и почему именно так

**1. BUILD и ENCODE разделены типами, а не соглашением** (`:342-347`).

`fit_bucket_edges` — функция, возвращающая замороженный артефакт; у класса
`Bucketizer` метода `fit` нет вовсе. Посчитать границы на Validation, Test или
на одном примере им **физически нечем**.

**2. Границы хранятся строками десятичных дробей** (`:185-191`).

Значение ровно на границе должно попадать в один и тот же бакет всегда, а
двоичная дробь этого не гарантирует.

Это четвёртая форма вырожденных данных. Мутация «читаем границы через float»
сначала **выжила**: границы в тесте были взяты «дробными для надёжности»
(`100.05`, `2500.5`), а такие float переживают точно. На настоящем артефакте
через float портятся **247 границ из 315**: квантильная граница — это значение
выборки, поэтому среди них целые (`294` → `294.0`) и суммы с хвостовым нулём
(`2500.50` → `2500.5`). Данные теста были аккуратнее реальных и потому слабее.

**3. Квантильная граница берётся как значение выборки, а не интерполяция**
(`core/quantiles.py`).

Интерполяция породила бы границу, которой в данных нет, и дробную границу на
целочисленном поле.

**4. Clipping происходит сам, и смысл §19.4 в том, чтобы это заметить**
(`:404-412`).

Сравнение с границами так и работает — новый бакет создать неоткуда. Поэтому
считаются `numeric_clip_rate` и раздельные счётчики низа и верха.

**5. Метка вне опубликованного domain — блокирующая ошибка** (`:419-431`).

По построению это невозможно и означает, что границы и `bucket_field_domains`
приехали из разных BUILD.

**6. Поле без единого валидного значения — блокирующая ошибка**
(`:280-285`).

Молчаливый один бакет спрятал бы сломанный источник.

**7. `labels`, `domain` и `intervals` при загрузке не читаются**
(`:166-174`).

Они выводятся из границ. Прочитать их значило бы завести второй источник
истины.

**8. Проверка clipping потребовала отдельного приёма** (`PLAN.md`, 2.13).

На полной выборке clipping **структурно невозможен**: `min_train`/`max_train`
взяты из тех же данных, что потом размечаются. Настоящий случай — ENCODE видит
значения, которых BUILD не видел, поэтому проверка гоняет BUILD по усечённой
выборке. На ней clipping и проявился: 15 низких, 102 высоких.

### Пример на реальных данных

Конфиг (`config/bucketization.yaml`):

```yaml
defaults: {method: quantile, bucket_count: 32}
fields:
  amount_base_bucket:   {method: quantile,     bucket_count: 64}
  age_bucket:           {method: equal_width,  bucket_count: 16}
  screens_count_bucket: {method: quantile,     bucket_count: 32}
```

`age_bucket` — единственное поле с равной шириной: возраст ограничен диапазоном
14…120 и читается человеком, равные интервалы здесь понятнее квантильных.

Опубликованные domain (`data/golden_expected/bucket_field_domains.json`), 11
полей:

| поле | запрошено | фактически |
|---|---|---|
| `amount_base_bucket` | 64 | 64 (+ `MISSING`) |
| `age_bucket` | 16 | 16 |
| `account_age_bucket` | 32 | 32 |
| `screens_count_bucket` | 32 | **8** |

Последняя строка — §19.3 на реальных данных: значения целые и их мало, поэтому
квантильные границы совпали, дубли удалены, зафиксировано фактическое число.

Наша запись: `Decimal("12075.4738")` → `"bucket_37"` (значение из эталона).
Проверить, между какими границами оно легло, здесь нельзя: файл
`artifacts/<версия>/bucket_edges.json` в git не хранится.

### Что сломается, если этого не будет

Модель получит бесконечное множество разных чисел вместо десятков категорий —
и не выучит из них ничего. Если же считать границы на каждом прогоне заново,
`bucket_37` будет означать разные суммы в разные дни, и модель, обученная
вчера, завтра станет неверной.

## 2.14 FieldPolicies — политики полей

### Что за задача

Последний фильтр перед выдачей. Три правила, и все три — про то, чего в модели
быть **не должно**: длинных списков (§21), технических идентификаторов (§22),
свободного текста (§23).

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `src/preprocessing/field_policies.py` | появился | проверки до данных и применение к полям |

Своего конфига **нет**: §11 объявляет эти атрибуты полем схемы, и второй
источник истины был бы лишним.

### Что внутри

**`TEXT_POLICY` (`:49`)** — политика §23 как данные. Ключевое:
`declarable_field_types` берётся из самого `FieldType`, а не переписывается
руками; `rare_assignment: tokenizer_only`.

**`check_field_policies` (`:79`)** — проверки до обработки данных.

**`_check_no_direct_identifiers` (`:106`)** — §23 по классификации контракта, а
не по имени поля.

**`FieldPolicies.apply` (`:181`)** — убирает поля с `model_input: false` и
обрезает многозначные.

**`_limit` (`:215`)** — §21 пп. 1–5.

### Ключевые решения и почему именно так

**1. `order_significant` обязателен у каждого многозначного поля**
(`schema/feature_schema.py:225-229`).

«Не указано» означало бы, что порядок значений определяет источник, а не
решение человека.

**2. Обрезкой владеет только этот компонент** (docstring, `:20-24`).

Sessionizer лимит знает, но применяет его лишь для аномалии §33.13. Знать
лимит и применять его — разные вещи: при рассогласовании теперь портится
метрика, а не данные.

**3. Убранное поле считается, а не пропускается молча** (`:204-209`).

Решение «не показывать модели» видно в дампе как отдельный шаг, а не как
отсутствие строки.

**4. В `HighCardinalityPolicy` только реализованные стратегии**
(`schema/feature_schema.py:53`).

`replace_with_category`, `keep_frequent` и `hashing` из §22 объявить нечем.

**5. §23 выполняется устройством** (`:51-58`).

Текстового типа в `FieldType` нет. Проверяется то, что устройством не
выражается: что через `source_field` не утекает колонка, помеченная как
`direct_identifier` — **по классификации владельца источника**, а не по виду
значения.

**6. Перечень типов берётся из самого `FieldType`** (`:54-58`).

Если текстовый тип однажды появится, состояние изменится **само**, а вместе с
ним и `preprocessing_state_sha256`. Переписанная копия списка промолчала бы.

**7. `RARE` препроцессингом не назначается** (`:63-65`), и это охраняется
тестом — временная гарантия со сторожем.

### Пример на реальных данных

**§22 в действии.** У события `CARD_PURCHASE` в
`data/golden_expected/prepared_events.json` ровно четыре поля:

```
amount_base_bucket, currency, merchant_category, terminal_country
```

`merchant_id` объявлен в схеме, но `model_input: false` — до выхода он не
доехал. В сырой записи он был: `"merchant_id": "M-2889"`.

**§21 в действии.** Клиент `C000004` — роль «переполнение многозначного поля»,
у него 11 продуктов. В эталонном профиле:

```json
"products": ["BROKERAGE","CARD","CHILD_CARD","DEPOSIT","INSURANCE","LOAN","METALS","PENSION"]
```

Ровно **восемь** значений (лимит `max_values_per_field: 8`), и они
**отсортированы по алфавиту** — потому что у `products` объявлено
`order_significant: false`: набор продуктов это множество, а не
последовательность.

Для сравнения — экраны сессии, где порядок значим:

```json
"screens": ["TRANSFERS","PROFILE","QR","PAYMENTS","CARDS","SUPPORT","LOANS"]
```

Не по алфавиту: это хронология первого появления, и обрезка отрезала бы
**хвост**, а не произвольные элементы.

### Что сломается, если этого не будет

`merchant_id` попадёт в словарь и даст десятки тысяч токенов, встреченных по
одному разу. Модель не сломается — она станет хуже, и понять почему будет не по
чему. Списки продуктов разной длины дадут события разного размера, и лимит
токенов на событие начнёт съедаться случайными полями.
