# Этап 3 — оркестрация BUILD / ENCODE (3.0–3.5)

Семнадцать компонентов написаны. Этап 3 соединяет их в две фазы и превращает
результат в файлы, которые уедут токенайзеру.

**Главное различие, вокруг которого построен весь этап:**

| | BUILD (§27) | ENCODE (§28) |
|---|---|---|
| на чём | **только** TRAIN | любой набор: TRAIN, golden, позже Validation/Test |
| что делает | **считает** правила: границы бакетов, границы дельты, domain | **применяет** замороженные правила |
| выход | `artifacts/<версия>/` | `data/prepared/<набор>/` |
| сколько раз | один раз на версию | сколько угодно |
| код | `run_build` | `run_encode` |

## 3.0 Перегенерация golden-набора с 14 клиентами

### Что за задача

Отложенный хвост этапа 0, сделанный **до** первого эталонного прогона.
В golden-наборе было ровно 12 клиентов — все ролевые, ни одного обычного.
Эталон без happy path неполон: поломка нормального пути прошла бы мимо
golden-векторов.

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `src/generator/build_dataset.py` | изменён | `golden_clients = MIN_CLIENTS + debug_clean_clients` |
| `src/generator/config.py` | изменён | поле `debug_clean_clients`, `golden_vectors_version` → 1.1.0 |
| `data/golden_input/` | перегенерирован | 14 клиентов вместо 12 |

### Ключевые решения и почему именно так

**1. Число «чистых» клиентов публикуется полем манифеста, а не константой.**

Первая версия импортировала константу из `debug_dump` в генератор — связь
получалась по коду, хотя фильтр и так читает из `_meta/` две таблицы, то есть
зависимость по данным уже существовала. Поле в манифесте вдобавок выражает то,
чего константа не может: **у main и golden число чистых клиентов может
отличаться**.

Умолчания у чтения нет (`core/debug_dump.py:314`): набор без этого поля
отвергается, потому что подставленное число было бы догадкой о чужих данных.

**2. `golden_vectors_version` поднята до 1.1.0.**

Состав набора изменился, и §29.2 требует его версионировать: два разных набора
под одной версией неразличимы по манифесту.

**3. «Чистый» проверяется не только отсутствием роли.**

У обоих клиентов есть события во всех трёх событийных источниках и снимок
профиля. Клиент-роль «нет событий» формально тоже без краевых случаев в
манифесте, но показывать на нём нечего.

### Пример на реальных данных

`data/golden_input/_meta/manifest.json` сейчас:

```
n_clients = 14, debug_clean_clients = 2, golden_vectors_version = "1.1.0",
total_records = 2554, файлов 148
```

Чистые клиенты — `C000012` и `C000013` (первые два, которых нет среди 12
ролевых). Все 32 краевых случая на месте.

### Что сломается, если этого не будет

Эталон проверял бы только обработку брака. Правка, ломающая обычную
транзакцию, прошла бы через golden-векторы зелёной.

## 3.1 ArtifactHasher — отпечаток состояния

### Что за задача

Один вопрос: **тем ли состоянием посчитаны данные, что лежит рядом с ними.**
Ответ — `preprocessing_state_sha256`.

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `src/preprocessing/artifact_hasher.py` | появился | сборка состояния §30 и его хэш |
| `src/preprocessing/cutoff.py` | изменён | добавлен `cutoff_policy_state` |
| `src/preprocessing/field_policies.py` | изменён | добавлена `TEXT_POLICY` |
| `src/preprocessing/core/hashing.py` | изменён | добавлен `content_hex` |
| `src/preprocessing/schema/feature_schema.py` | изменён | `state()` и `numeric_rules()` |
| `tests/test_artifact_hasher.py` | появился | каждый раздел §30 влияет на хэш |

### Что внутри

**`SPEC_30_SECTIONS` (`:53`)** — восемнадцать разделов §30, дословно.

**`PreprocessingState` (`:95`)** — frozen dataclass, 22 поля: 18 из §30 плюс
четыре сверх перечня, **каждое со своей причиной прямо в docstring поля**:

| раздел | почему сверх §30 |
|---|---|
| `hash_policy` | §29.1 п.13 требует прямо |
| `bucketization_config` | по границам не восстановить, чем они посчитаны: §19.3 удаляет совпавшие, и 32 запрошенных бакета неотличимы от 8 |
| `profile_policy` | §6 и §24 определяют `prepared_profile`, а в §30 профиль не назван |
| `run_policy` | `global_seed`, `T`, `fx_max_staleness`, разрыв сессии, лимиты |

**`build_state` (`:158`)** — собирает состояние. Артефакты BUILD — обязательные
параметры, а не «если посчитаны».

**`verify_state_hash` (`:232`)** — сверка.

**`_check_state_is_complete` (`:258`)** — две проверки при импорте модуля.

### Ключевые решения и почему именно так

**1. Хэшируется разобранное состояние, а не текст конфигов.**

Переставленные строки YAML, правка комментария и другой отступ не меняют ни
одного решения пайплайна, а хэш по тексту менялся бы от каждого из них — и
быстро перестал бы значить «состояние другое».

**2. Полнота выражена сигнатурой** (`:99-101`).

Ни одного значения по умолчанию: забыть раздел — это ошибка при сборке
объекта, а не тихо неполный хэш. Отсутствие умолчаний **проверяется при
импорте** (`:273-283`), потому что добавленное позже умолчание вернуло бы
возможность забыть.

**3. Разделы названы по §30 дословно, включая проекции соседей** (`:191-195`,
`:214`).

`closed_set_domains` и `numeric_rules` выводятся из Feature Schema,
`bucket_field_domains` — из границ, `calendar_timezone_policy` — из политики
времени. Дублирование внутри пре-образа безвредно: оба вида берутся из одного
объекта в один момент. Зато перечень §30 сверяется с кодом **глазами за
минуту**, а не вычитывается из трёх модулей.

**4. «Продолжить с предупреждением» не выражается** (`:232-244`).

`verify_state_hash` ничего не возвращает — проверять её результат нечем, а
значит и проигнорировать нечего.

**5. Мутационная проверка нашла здесь ложную «поймку».**

Чтобы убедиться, что импортная страховка работает, умолчание поставили полю в
**середине** dataclass. Прогон дал `1 error during collection` — мутация
«поймана». Поймал её **Python**: за полем с умолчанием шли поля без умолчаний,
и класс не создавался вовсе. Наша проверка не выполнялась ни разу.

Мутацию переставили на **последнее** поле — dataclass стал валидным, упасть
могла только своя проверка, и она упала со своим сообщением.

**6. Пин перечня §30 в тесте** (`tests/test_artifact_hasher.py:48`).

Список разделов продублирован в тесте намеренно: это единственное место, где
перечень сверяется **с регламентом**, а не сам с собой. Пункт, вычеркнутый разом
из кода и из состояния, иначе не уронил бы ни одной проверки.

### Пример на реальных данных

Состояние на основном наборе: **22 раздела, 82 173 байта канонического JSON**,
хэш `2d2d31de…` (замер на 3.1). После настоящего BUILD (3.2) хэш стал
`1dc34b8d…` — именно он лежит в
`data/golden_expected/preprocessing_state_sha256.json`:

```
"1dc34b8d541a6615fda037688255a36f01ef605231e7ab2d53fd976f1a289894"
```

Замер влияния (из отчёта 3.1): `global_seed`, `fx_max_staleness`,
`session_gap` и `T` хэш **меняют**; `workers` и `debug` — **нет**.

### Что сломается, если этого не будет

Можно молча поменять любой конфиг после BUILD и обработать данные границами,
посчитанными по другой схеме. Никакой ошибки при этом не будет — просто часть
значений попадёт не в те бакеты.

## 3.2 BUILD PHASE

### Что за задача

§27 — девятнадцать шагов: загрузить и проверить конфиги, прогнать цепочку,
набрать выборку, посчитать границы бакетов и границы дельты, опубликовать
domain, собрать baselines, проверить независимость от порядка, посчитать хэш и
заморозить.

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `src/preprocessing/pipeline.py` | появился | `run_build`, `freeze_configs`, `prepare_records`, `freeze_build` |
| `src/preprocessing/time_delta.py` | появился | границы delta-канала §25.2 |
| `config/time_delta.yaml` | появился | конфигурация delta-канала |
| `src/preprocessing/core/quantiles.py` | появился | арифметика границ, общая с §19 |
| `src/generator/build_dataset.py` | изменён | `dataset_role` в манифесте |

### Что внутри

**`Dataset` (`:154`) и `TrainDataset` (`:204`)** — асимметрия намеренная:
ENCODE выполняется на любом наборе, BUILD — только на TRAIN.

**`FrozenConfigs` (`:241`)** — тринадцать загруженных конфигов.
`versions()` (`:264`) собирает комплект §30 **из самих конфигов**.

**`freeze_configs` (`:295`)** — §27 шаги 1–9. `identity_table` —
обязательный параметр.

**`prepare_records` (`:354`)** — цепочка §37.2 от чтения до политик полей,
**общая часть BUILD и ENCODE**. Останавливается перед бакетизацией: на BUILD
границ ещё нет, и это единственная точка, где два прохода расходятся.

**`run_build` (`:525`)** — шаги 1–18. Единственный вход — целый TRAIN-набор.

**`freeze_build` (`:899`)** — шаг 19.

**`time_delta.py`** — `TimeDeltaEdges` (`:102`), `DeltaSampler` (`:195`),
`collect_deltas` (`:239`), `fit_time_delta_edges` (`:278`).
`FIRST_EVENT` и `WINDOW_START` (`:47-49`).

**`core/quantiles.py`** — три функции, ни артефактов, ни версий, ни имён.
`internal_edges` (`:44`) реализует §19.3.

### Ключевые решения и почему именно так

**1. Запрет §27 выражен дважды структурно** (`:536-540`, `:204-232`).

Во-первых, у `run_build` **нет параметра**, которым можно передать пример или
батч. Во-вторых, `TrainDataset` собирается только из набора, чей манифест
объявил роль `train`.

Позвать BUILD на golden-наборе не получится не потому, что кто-то это заметит,
а потому, что объект-аргумент из него **не построится**.

**2. Роль публикует генератор, а не имя каталога** (`:176-180`).

Каталог можно переименовать, скопировать и смонтировать куда угодно, а манифест
едет вместе с записями.

**3. Шаг 10 вырожден, и это заявлено прямо** (`:566-567`).

Разбиений Validation/Test нет, TRAIN — весь набор, от утечки защищает §14. Это
**отложенный механизм**, а не примечание: когда разбиения появятся, отбор
станет отдельным шагом со своей проверкой.

**4. `time_delta` — отдельный модуль, а не поле бакетизации.**

§25.2 требует разных компонентов, и различие не косметическое: границы полей
применяет препроцессинг, границы дельты — токенайзер **после truncation**.
Общей осталась только арифметика (`core/quantiles.py`): значение ровно на
границе обязано попадать в один бакет в обоих случаях, а две копии одного
правила однажды разойдутся на единицу.

**5. Дельта считается, но не сохраняется** (`time_delta.py:14-18`).

2.17 её не считал вовсе; здесь она живёт внутри расчёта границ и в запись не
попадает.

**6. У первого события клиента дельты нет, и в выборку оно не идёт**
(`collect_deltas`, `:257-260`).

Ноль вместо неё означал бы «предыдущее событие в тот же миг» и сдвинул бы
первый бакет на всех клиентах сразу.

**7. `FIRST_EVENT` и `WINDOW_START` публикуются отдельным ключом и в `labels()`
не входят** (`time_delta.py:121-134`).

Попасть в них расчётом нельзя. Но в `domain()` они есть — иначе `min_count`
токенайзера схлопнул бы их в `RARE`.

**8. `PartitionOrder` содержит только `canonical` и `reversed`** (`:120-131`).

«Случайный порядок» сделал бы проверку шага 16 невоспроизводимой, а
невоспроизводимая проверка хуже отсутствующей.

**9. Baselines в состояние не входят, `bucket_edges` входят** — и граница между
ними **не** «конфиг против данных» (`:598-609`, `artifacts.py:29-39`).

Оба посчитаны из TRAIN. Граница в том, **участвует ли артефакт в
преобразовании**: границы применяются к каждому значению и меняют выход,
поэтому их подмена обязана менять хэш; baselines ни на одно значение не
влияют.

Формулировка «хэш зависит от конфигурации, а не от данных» тут **неверна и
опасна**: в токенайзере ровно та же пара — `token_counts_open_set` считается по
TRAIN и в хэш **не входит**, а Vocabulary тоже считается по TRAIN и **входит**,
потому что именно он превращает значение в `token_id`.

**10. Шаг 16 выполнен наполовину, и это заявлено явно** (`:865-882`).

Проверяется свойство §29 пп. 5–6: BUILD прогоняется по партициям в каноническом
и обратном порядке, артефакты сравниваются побайтно. Сравнение процессов
(1 против 4) остаётся за 4.1 — здесь оно дало бы половину проверки под видом
целой.

**Следствие:** артефакты BUILD заморожены **до** полной проверки детерминизма,
поэтому `golden_expected` замораживать нельзя, пока 4.1 не пройден.

**11. Комплект версий собирается из конфигов, а не перечисляется руками**
(`:264-292`).

Версия и конфиг, из которого она взята, приезжают вместе.
`closed_set_domains_version` наследует версию схемы,
`bucket_field_domains_version` — версию границ: собственных версионируемых
файлов у этих domain нет, и выдумывать им номер значило бы завести версию,
которую нечем менять.

### Пример на реальных данных

Прогон на TRAIN (числа из отчёта 3.2):

```
32 543 записи в обработке
preprocessing_state_sha256 = 1dc34b8d…
11 bucket-полей
delta-канал: 32 бакета по 30 894 дельтам, диапазон 0…10 479 366 секунд
artifacts/0.1.0/ — 7 канонических файлов плюс читаемые копии
```

Ноль в диапазоне дельт — это пара tie-break, разошедшаяся на одну секунду.

Golden-набор BUILD **отвергает по роли**. Обратный обход партиций и повторный
запуск дают байт-в-байт те же артефакты.

Конфиг delta-канала (`config/time_delta.yaml`) объявляет метод `quantile` —
единственный: дельты распределены с тяжёлым хвостом (минуты у активного клиента
и месяцы у спящего), и равная ширина отдала бы почти всё в первый бакет.

### Что сломается, если этого не будет

Границы придётся пересчитывать на каждом прогоне — и `bucket_37` начнёт
означать разные суммы в разные дни. Без разделения BUILD/ENCODE ничто не
помешает посчитать границы на тестовой выборке, то есть заглянуть в данные,
которых модель видеть не должна.

## 3.3 ENCODE PHASE

### Что за задача

§28 — двадцать шесть шагов. Загрузить замороженные артефакты, **проверить
хэш**, прогнать ту же цепочку, применить границы, упорядочить, проверить
контракт §2.2, записать метрики и lineage.

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `src/preprocessing/pipeline.py` | изменён | `run_encode`, `FrozenArtifacts`, `EncodeResult` |
| `src/preprocessing/output_contract.py` | появился | финальная проверка §2.2 |
| `src/preprocessing/bucketizer.py` | изменён | `BucketEdges.from_state` |
| `src/preprocessing/time_delta.py` | изменён | `TimeDeltaEdges.from_state` |
| `tests/test_encode_phase.py`, `tests/test_output_contract.py` | появились | round-trip границ и все запреты §2.2 |

### Что внутри

**`FrozenArtifacts` (`:957`)** — артефакты, прочитанные с диска.
`load` (`:973`) читает четыре файла; `identity_table` (`:994`) достаёт таблицу
identity из **состояния**, а не с диска.

**`run_encode` (`:1040`)** — шаги 1–24 и 26. Порядок: загрузить конфиги →
подставить domain из артефакта → **собрать состояние и сверить хэш** → цепочка
→ бакетизация → порядок и календарь → контракт → метаданные и lineage.

**`output_contract.validate_output` (`:89`)** — проверяет и возвращает **отчёт о
проверенном**.

**`_check_utc` (`:124`)**, `_check_event` (`:143`), `_check_fields` (`:207`).

### Ключевые решения и почему именно так

**1. Шаг 1 стоит первым не для порядка** (`:1054-1057`).

Пока `preprocessing_state_sha256` не сошёлся, обрабатывать нечего: конфиги
могли измениться после BUILD, и границы оказались бы посчитаны по одной схеме,
а применялись бы к другой. Правка любого YAML после BUILD **останавливает**
ENCODE, а не портит выход молча.

**2. «ENCODE не пересчитывает границы» выражено устройством** (`:960-963`).

У `Bucketizer` нет метода `fit`, а `fit_bucket_edges` в ENCODE-пути просто не
вызывается. Границы приходят единственным способом — `FrozenArtifacts.load`.

**3. Таблица identity берётся из замороженного состояния** (`:994-1007`).

Набор на входе другой: у golden свои 14 клиентов против 200 у TRAIN, и таблица
оттуда дала бы состояние, не совпадающее с замороженным.

**4. `labels`, `domain`, `intervals` при загрузке не читаются**
(`bucketizer.py:166-174`, `time_delta.py:173-182`).

Второй источник истины однажды разойдётся с первым. `reserved` delta-канала
тем более: дать файлу право переименовать `FIRST_EVENT` значило бы разойтись с
токенайзером, у которого имя зашито.

**5. Контракт §2.2 проверяет НЕ всё, и это осознанно** (docstring
`output_contract.py:8-16`).

Свободного текста нет, потому что в `FieldType` нет текстового типа;
`event_type` внутри `fields` отвергает модель §5. Писать проверку на то, чего
нельзя объявить, значит завести код, который никогда не сработает, — и однажды
принять его срабатывание за ложную тревогу.

**Но у невыразимости есть срок.** §13 токенайзера прямо говорит, что
BPE/subword может быть добавлена «в отдельной версии архитектуры». Поэтому
проверяется не текст в каждом значении, а **сама гарантия**:
`test_field_type_still_has_no_text_kind` падает ровно тогда, когда в
`FieldType` появляется новый тип.

**6. Отчёт считает, сколько значений проверено** (`:59-62`).

«Контракт прошёл» на пустом потоке не значит ничего, и счётчик — единственный
способ отличить работающую проверку от отработавшей вхолостую.

**7. Зона проверяется до сравнения с T** (`:154-157`).

Наивное время сравнивать с aware нельзя: без этой очерёдности вместо названной
ошибки вылетел бы `TypeError` из глубины сравнения.

**8. Найдено прогоном: справочные записи считались профилями** (`:66-72`).

Курсы валют (1 250 штук) шли в отчёте контракта как профили, которых 200. Ни
одна проверка от этого не падала, а число клиентов выглядело завышенным втрое.
Заведён отдельный счётчик `reference`.

### Пример на реальных данных

Прогон ENCODE на TRAIN (отчёт 3.3):

```
31 093 события, 200 профилей, 1 250 справочных записей
контракт проверил 117 505 полей: 29 167 bucket-значений, 54 356 closed-set
```

Golden прошёл ENCODE на **тех же** замороженных артефактах: 374 события,
14 профилей, 13 клиентов с событиями. Повторный прогон и обратный обход
партиций дают тот же выход байт-в-байт. Подменённый
`preprocessing_state_sha256` **останавливает** ENCODE.

Четвёртый случай вырожденных данных нашёлся именно здесь — см. 2.13, мутация
«границы читаются через float».

### Что сломается, если этого не будет

Границы будут пересчитываться под данные каждого прогона — то есть модель,
обученная на TRAIN, получит на inference другую разметку тех же сумм. Без
проверки хэша это произойдёт молча.

## 3.4 Output dataset — выход §32 и контракт §2

### Что за задача

Здесь препроцессинг заканчивается и начинается чужая ответственность. Всё, что
токенайзер получит, он получит отсюда, и §2 перечисляет это **девятнадцатью**
пунктами.

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `src/preprocessing/prepared_output.py` | появился | запись выхода и карта контракта |
| `tests/test_prepared_output.py` | появился | 19 пунктов и форма записей |

### Что внутри

**`CONTRACT_ITEMS` (`:55`)** — перечень §2 дословно, сверяется с полями
`TokenizerContract` при импорте.

**`TokenizerContract` (`:121`)** — frozen dataclass с 19 обязательными полями.

**`ContractItem` (`:106`)** — пара «файл + поле».

**`profile_row` (`:151`) и `event_row` (`:165`)** — формы §32.1 и §32.2.

**`write_prepared` (`:194`)** — пишет два JSONL, одиннадцать файлов пунктов
контракта, метаданные, lineage, `data_quality.json` и `contract.json`.

### Ключевые решения и почему именно так

**1. Полнота выражена сигнатурой — третий раз по одному образцу** (§30, §2,
§31).

**2. Пункт описывается парой «файл + поле», а не именем файла** (`:106-111`).

`lifetime_first` и `calendar_time_features` живут **внутри** записей событий,
`fx_max_staleness` и версии — внутри метаданных. Контракт обязан отвечать на
вопрос «где это», а не «есть ли такой файл»; отдельный файл на одно булево поле
был бы выдумкой.

**3. Справочные записи в выход не идут** (`EncodeResult.events`/`profiles`).

Курсы валют — материал §18, они не события и не профиль.

**4. Lineage через `event_id`, а не через `source_meta`** (docstring,
`:36-43`).

§32.2 задаёт форму записи, и сырого `source_record_id` в ней нет — §2.2 не
хочет технических ID на входе токенайзера. Связь не теряется: `event_id`
считается из источника, его записи, типа и времени, то есть **восстанавливается
пересчётом**. Прогонный lineage лежит рядом отдельным файлом.

**5. JSONL канонизируется построчно** (`:269-277`).

Файл целиком не JSON-документ, зато его можно читать потоком и сравнивать
побайтно.

**6. Порядок записей задаётся явно** (`:203-204`): клиент, затем позиция.
Порядок строк — часть байт, которые сравнивают golden-векторы.

**7. Наблюдение, которое чуть не стало ложной тревогой.**

Текстовый поиск `null` в `prepared_events.jsonl` даёт одно совпадение — но это
подстрока синтетического `source_record_id` (`CPX-000005-null-amount`),
попавшего в `ordering_key`. Пустых значений в выходе нет. Заодно видно, что
сырой идентификатор источника всё же доезжает до токенайзера — внутри
`ordering_key`, как того и требует §13, но **никогда** как значение поля.

**8. Форму записи пишет `event_row`, а не `CanonicalEvent.to_output`.**

Две функции дают почти одинаковый результат, но с одним важным различием:
`to_output` (`schema/event.py:135`) добавляет `lifetime_first` **только если он
`true`**, а `event_row` пишет его **всегда** как булево. В эталоне лежит второй
вариант — там есть и `"lifetime_first":false`. Это не расхождение, а разделение
ролей: `to_output` — форма §32.2 у модели события, `event_row` — форма выхода,
где §2 п.19 требует поле у каждой записи.

### Пример на реальных данных

Состав каталога выхода (17 файлов на TRAIN):

```
prepared_profile.jsonl   prepared_events.jsonl
feature_schema.json      closed_set_domains.json
bucket_field_domains.json  bucket_metadata.json  time_delta_edges.json
currency_normalization_config.json  sessionization_config.json
field_priority.json      max_values_per_field.json
text_policy.json         cutoff_policy.json
data_quality.json        metadata.json  lineage.json  contract.json
```

`contract.json` — карта «пункт §2 → где он лежит»:

```json
{"lifetime_first": {"file": "prepared_events.jsonl", "field": "lifetime_first"},
 "fx_max_staleness": {"file": "metadata.json", "field": "fx_max_staleness_days"},
 "bucket_field_domains": {"file": "bucket_field_domains.json", "field": null}}
```

Настоящая строка `prepared_events.jsonl` (из эталона golden):

```json
{"calendar_time_features":{"day_of_week_local":0,"hour_of_day_local":15},
 "calendar_timezone":"Asia/Almaty","client_id":"C000000",
 "event_id":"7f4e756104f56698cfde7ceb85c1e604","event_type":"PAYMENT",
 "fields":{"amount_base_bucket":"bucket_37","currency":"EUR","direction":"IN"},
 "lifetime_first":false,
 "ordering_key":"2023-12-11T09:16:00Z|000010|CP-000000-00001",
```

Прогон: TRAIN — 31 093 события, 200 профилей, 17 файлов; все 19 пунктов

голых чисел в `fields` нет.

### Что сломается, если этого не будет

Токенайзер получит события, но не получит domain, приоритетов полей, лимитов и
версий — то есть не сможет ни собрать словарь, ни объяснить полученное
значение. Забытый пункт обнаружится не здесь, а на сборке словаря, и будет
выглядеть как «странно ведёт себя модель».

## 3.5 Артефакты §31

### Что за задача

Тридцать два пункта, по которым восстанавливают, **чем именно получены
данные**. Пункт, которого нет, обнаруживается через месяцы, когда
восстанавливать уже поздно.

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `src/preprocessing/artifacts.py` | появился | перечень §31, происхождение кода, запись |
| `src/preprocessing/sampler.py` | изменён | добавлен `SAMPLING_ALGORITHM` |
| `tools/mutation.py` | появился | harness мутационных прогонов |
| `tests/test_artifacts.py` | появился | перечень, прогонные факты, хэш кода |

### Что внутри

**`SPEC_31_ARTIFACTS` (`:61`)** — тридцать два имени дословно.

**`RequiredArtifacts` (`:102`)** — frozen dataclass, 32 поля без умолчаний.

**`code_provenance` (`:142`)** — происхождение кода:
`code_state_sha256` по каноническому списку файлов `src/`, `tools/`, `config/`
плюс `git_commit` и `dirty` справкой.

**`require_clean_tree` (`:204`)** — запрет там, где ложь дорога.

**`deterministic_build_config` (`:219`)** — собирается из кода и настроек и
содержит **прямой список того, что в хэш не входит**.

**`collect_artifacts` (`:250`)** и `write_artifacts` (`:334`) — один пункт, один
файл.

### Ключевые решения и почему именно так

**1. Происхождение кода — хэш содержимого, а не имя коммита** (`:169-179`).

`git commit` описывает код честно **только при чистом дереве**. BUILD с
незакоммиченными правками записал бы «собрано коммитом X», а пересборка из X
дала бы другое. Тихая ложь, вскрывающаяся позже всего.

Рассмотренные варианты «отказаться собирать при грязном дереве» и «писать
`dirty: true`» отклонены: первый заставил бы коммитить ради отладочного
запуска, второй оставляет флаг, который легко не заметить.

**2. `tests/` в хэш кода не входит** (`:54-56`).

Тесты прогон не выполняют, и их правка результата не меняет. Иначе хэш кода
менялся бы от каждой правки теста и перестал бы что-либо значить.

**3. `build_timestamp` — в артефакты, но не в хэш** (`:29-39`).

Попади оно в состояние, два одинаковых BUILD дали бы разные хэши, и сравнение
1 против 4 воркеров развалилось бы на пустом месте.

Удерживается это **не памятью**: `build_timestamp` передаётся в `freeze_build`
снаружи, внутри BUILD доступа ко времени нет, а тест
`test_run_specific_facts_stay_out_of_the_state_hash` падает, если прогонный
факт появится среди разделов состояния.

**4. Запрет на грязное дерево стоит там, где ложь дорога** (`:204-216`).

Не на каждом BUILD — на заморозке `golden_expected`.

**5. `golden_vectors` честно сообщает `expected_frozen: false`** (`:260-262`).

§29.2 п.1 требует заполнить эталон первым прогоном ENCODE, то есть на 4.2.
Пункт от этого не исчезает и не выдумывается.

**6. `deterministic_build_config` содержит список исключений явным текстом**
(`:241-246`).

Вопрос «почему хэш не изменился» задают регулярно — ответ лежит в артефакте, а
не в чьей-то памяти.

**7. Мутационный harness появился здесь** (`tools/mutation.py`).

Причина в самой методике: ручной прогон мутаций дважды подвёл одинаково —
мутация падала **не там**, где задумано, а «красный прогон» принимался за
доказательство. Оба раза её перехватывал Python.

Теперь мутация **объявляет**, каким тестом и с каким сообщением она обязана
быть поймана, а harness сверяет объявленное с фактическим. Вердикты: `CAUGHT`,
`WRONG_CATCH` (упало, но не то — **считается не пойманной**), `SURVIVED`,
`HUNG`, `NOMATCH`.

Второе, что здесь закрыто: скрипты сравнивали восстановленный исходник через
`read_text()`, а он нормализует переводы строк — «исходник восстановлен: True»
печаталось, когда файл менялся с LF на CRLF. Harness читает и пишет **байтами**;
29 испорченных до этого файлов нормализованы, `.gitattributes` не даёт
повториться.

### Пример на реальных данных

Прогон (отчёт 3.5): **39 файлов** — 32 пункта §31 плюс рабочие (состояние,
версии) и читаемые копии. Все 32 записаны и ни один не пуст.

Проверено там же: `code_state_sha256` реагирует на правку исходника и **не**
реагирует на правку теста; повторная заморозка с другим `build_timestamp` даёт
тот же `preprocessing_state_sha256` и другой `build_timestamp.json`.

Хэш кода на момент заморозки эталона виден в
`data/golden_expected/golden_manifest.json`:

```json
{"code_state_sha256":"cc124b444ee4232b56a9f409741eebe0b6daa3d291964748ea1938f77d1611e8",
 "git_commit":"45bb37df9996388814b33e017bfb81c483e48375",
 "python":"3.11.0rc2","golden_vectors_version":"1.1.0"}
```

### Что сломается, если этого не будет

Через полгода на вопрос «почему у этой суммы такой бакет» ответить будет
нечем: границы есть, а чем они посчитаны — неизвестно. Без хэша кода
«воспроизвели на другой машине» превращается в «получили похожий результат».
