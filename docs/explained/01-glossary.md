# Глоссарий

Все термины, которые встречаются в коде, конфигах и регламентах — простыми
словами. Читается отдельно от остальных документов.

Пометки: **[домен]** — банковское, **[ML]** — про модель и токенайзер,
**[техн]** — про код и воспроизводимость.

Формат статьи: объяснение → **У нас:** где в коде и пример настоящего
значения → **Путают с:** если есть с чем.

Английские термины оставлены как есть (`bucket`, `cutoff`, `hash`) — с ними
работать в коде, перевод только мешал бы.

---

## Шесть пар, которые путают чаще всего

Если читать глоссарий некогда, прочитай хотя бы это.

| | Первое | Второе | Разница |
|---|---|---|---|
| 1 | `MISSING` | `RARE` / `[UNK]` | значения **нет** ↔ значение **есть**, но редкое или новое. `MISSING` ставит препроцессинг, остальные два — токенайзер |
| 2 | **business range** | **clipping** | значение бессмысленно (возраст −1) → `MISSING` ↔ значение осмысленно, но вне обучающего диапазона → крайний бакет |
| 3 | **BUILD** | **ENCODE** | посчитать правила один раз ↔ применять их всегда |
| 4 | **cutoff T** | **окно модели** | граница «что вообще видно» (препроцессинг) ↔ сколько последних событий читает модель (токенайзер) |
| 5 | **партиция** | **воркер** | кусок данных (файл-месяц) ↔ процесс, который его обрабатывает |
| 6 | «не пройдена» | «не проведена» | проверка нашла расхождение ↔ проверку не удалось поставить, результат не значит ничего |

# [домен] Банковское

### Событие (event)

Одно действие клиента, у которого есть момент времени: перевод, покупка
картой, снятие наличных, сессия в приложении, push-уведомление. Событие — то,
из чего модель складывает историю клиента.

**У нас:** восемь типов событий в golden-наборе — `TRANSFER`, `PAYMENT`,
`LOAN_PAYMENT`, `CARD_PURCHASE`, `CASH_WITHDRAWAL`, `CARD_BLOCK`,
`APP_SESSION`, `PUSH_NOTIFICATION`. Модель события — `schema/event.py:62`
(`CanonicalEvent`), список типов задан в `config/event_mapping.yaml`.

**Путают с:** сырой записью источника. Не всякая запись становится событием:
строка app-лога — сырьё для сессии, снимок профиля — материал профиля, курс
валют — справочник (`event_mapper.py` docstring, §10 п.5).

### Профиль клиента (profile)

Что известно о клиенте на момент отсечки: регион, занятость, зарплата,
продукты, возраст. Один профиль на клиента, не история профилей.

**У нас:** `schema/profile.py:23` (`CanonicalProfile`), выход
`data/prepared/<набор>/prepared_profile.jsonl`. Настоящая запись из эталона:

```json
{"client_id":"C000000","profile_time_utc":"2026-01-31T19:00:00Z",
 "fields":{"region":"ASTANA","employment":"STUDENT","salary_bucket":"bucket_15",
           "products":["CARD","INSURANCE","LOAN"],"age_bucket":"bucket_12", ...}}
```

### Снимок профиля (profile snapshot)

Состояние профиля на конкретную дату, как его отдаёт банковская система.
Снимков много — по одному в месяц; профиль строится **из последнего снимка
не позже T**.

**У нас:** источник `profile_snapshots`, сырая запись:

```json
{"cif":"CIF000000","snapshot_date":"2024-01-01","region":"ASTANA",
 "employment":"STUDENT","salary":"473455","age":58,
 "account_open_date":"2010-01-01","products":["CARD","INSURANCE"]}
```

Выбор снимка — `profile_builder.py:341` (`_latest_snapshot`).

**Путают с:** «самым свежим снимком». Самый свежий может быть **после** T —
такой брать запрещено, это заглядывание в будущее (§6 п.1).

### Cutoff T (отсечка)

Дата и время, позже которых данные не существуют для этого прогона. Всё, что
после T, отбрасывается: модель не должна видеть будущее относительно момента,
на который её учат.

**У нас:** `core/settings.py:65`, значение по умолчанию
`2026-01-31 23:59:59 UTC`. Применяет `cutoff.py:100` (`CutoffFilter`).
Граница **включающая**: событие ровно в T проходит, `T + 1 секунда` — нет.

**Путают с:** окном модели (см. **truncation**). T отвечает на вопрос «что
вообще видно», окно — «сколько из видимого читает модель».

### Вне окна наблюдения ≠ брак

Запись после T отбрасывается, но это **не** ошибка данных: она не идёт в
карантин и не поднимает метрику ошибки. Считается отдельным отчётом, чтобы
«пропало 2350 записей» не выглядело загадкой.

**У нас:** `cutoff.py:80` (`CutoffReport`).

### Источник (source)

Одна банковская система-поставщик данных. У каждой свой формат: своё имя
клиента, свой способ записать время и сумму.

**У нас:** пять источников (`src/generator/sources/`):

| источник | клиент | время | сумма | валюта |
|---|---|---|---|---|
| `core_payments` | `client_ref` | `"11.01.2024 21:44"` | `"24 534,82"` строкой | `"тенге"`, `"ТЕНГЕ"`, `KZT` |
| `card_processing` | `cardholder_id` | `1705069132000` (epoch-мс) | `2792228` тиын | `"398"` |
| `app_logs` | `login_id` | `"2024-01-08T18:32:54"` без зоны | нет | нет |
| `profile_snapshots` | `cif` | `"2024-01-01"` дата | `salary: "473455"` | нет |
| `fx_rates` | нет | `rate_date` | `rate_to_kzt: "475.5434"` | `currency` |

Разнобой намеренный: на одинаковых источниках Source Contract нечего было бы
проверять.

### Source Contract (контракт источника)

Паспорт источника: какие колонки, каких типов, какая обязательна, где
первичный ключ, где поле клиента, где время, какой у источника ранг, какая
зона, какой класс PII у каждой колонки.

**У нас:** `config/source_contracts.yaml`, модель — `schema/source_contract.py:204`.
Колонка выглядит так:

```yaml
merchant_category: {type: string, required: false, nullable: false, pii: none}
```

Контракт читает не только ридер: ранг нужен сортировке (§13), зона — времени
(§12), правила correction/reversal — дедупликации (§9).

### client_id и ссылка источника

`client_id` — канонический идентификатор клиента внутри пайплайна, вида
`C000000`. Ссылка источника — то, как этого же человека называет конкретная
система: `000000`, `CH000000`, `CIF000000`, `L000000`.

**У нас:** таблица соответствий лежит **в наборе данных**, а не в конфиге:
`data/golden_input/_meta/identity_mapping.json`, секции вида
`app_logs.login_id`. Разрешение — `identity_resolver.py:285`.

**Путают с:** PII. `client_id` обязан быть непрозрачным (шаблон `^C[0-9]{6}$`),
а поле клиента в контракте не может иметь класс `direct_identifier` — иначе
паспортные данные стали бы ключом модели (§7 п.4).

### Identity mapping

Таблица «ссылка источника → `client_id`». Версионируется: смена связи меняет
состав данных клиента.

**У нас:** политика — `config/identity_mapping.yaml`, таблица — файл в
`_meta/` набора. Источников таблицы ровно два и оба выводятся из данных:
`DatasetIdentityTable` (`identity_resolver.py:129`) на BUILD и
`FrozenIdentityTable` (`:149`) на ENCODE. Относительного пути от текущего
каталога больше нет — на этом однажды прогорели (`CLAUDE.md`, восьмая форма).

### Lineage (происхождение записи)

Возможность ответить: из какой сырой записи, из какого файла и какой версии
схемы получилось это событие. Нужно, когда через полгода спросят «откуда тут
такая сумма».

**У нас:** `event_mapper.py:64` (`MappedRecord.lineage`) — событие → запись →
партиция → версия схемы; отдельный файл `lineage.json` в выходе
(`prepared_output.py:50`). В самих записях выхода сырого идентификатора нет,
но связь восстанавливается: `event_id` считается из источника, его записи,
типа и времени.

### Карантин (quarantine)

Куда откладывается запись, которую нельзя обработать. Главное правило §34:
**молча удалять запрещено** — у каждой отброшенной записи есть причина и
метрика.

**У нас:** `core/quarantine.py:94`. Восемь причин (`ReasonCode`, `:27`):
`unresolved_client_id`, `unknown_event_type`, `missing_event_time`,
`unknown_timezone`, `source_contract_violation`,
`unresolved_duplicate_conflict`, `incompatible_schema_version`,
`content_hash_mismatch`. Метрику поднимает сам `add()` — забыть про неё
нельзя, отказаться можно только явно (`count_metric=False`).

**Путают с:** отсечкой по T. Запись после T — не брак (см. выше).

### Дедупликация

Схлопывание повторов. Три разных случая, и лечить их одинаково нельзя:

- **точный дубль** — та же запись приехала дважды (тот же источник, тот же
  `source_record_id`, та же версия payload) → остаётся одна;
- **бизнес-дубль** — один факт под разными идентификаторами → ловится
  версионируемым отпечатком из объявленных полей (клиент, время, сумма,
  валюта, направление, мерчант);
- **конфликт** — тот же ключ, **разный** payload → разрешается только
  объявленным правилом; нет правила → **вся группа** в карантин.

**У нас:** `deduplicator.py:173`, политика — `config/dedup_policy.yaml`.
Запрещено главное искушение — `drop_duplicates(keep="first")`: «первая» это
та, что раньше легла в файл, а не та, что вернее (§9.3).

### FX-нормализация

Перевод суммы в базовую валюту по курсу **на дату события**, а не сегодняшнему.
Иначе транзакция 2023 года пересчиталась бы по курсу 2026-го, и результат
зависел бы от даты запуска пайплайна.

**У нас:** `fx_normalizer.py:212`, курсы — источник `fx_rates`, базовая валюта
KZT (`config/fx_config.yaml`). Правило поиска — последний курс **не позже**
события (`:162`, `rate_at`); будущий курс взять неоткуда по устройству
индекса.

### fx_max_staleness (допустимая давность курса)

Насколько старым может быть курс, которым считают. Курсы публикуются по
рабочим дням, поэтому «курса ровно на эту дату нет» — норма, а вот «курс
недельной давности» — уже нет.

**У нас:** `core/settings.py:71`, 3 календарных дня. Считается в **днях**, а
не в часах между моментами: пятница → понедельник это три дня, а не «три дня
десять часов», иначе каждое утро понедельника давало бы `MISSING`.

Если допустимого курса нет — §18.2 п.5 предписывает ровно четыре вещи, и все
четыре выполняются: сумма → `MISSING`, валюта сохраняется, **событие не
удаляется**, растёт `fx_missing_rate`. Покупка состоялась независимо от того,
смогли ли мы её пересчитать.

### Тиын

Разменная единица тенге, 1 KZT = 100 тиын. Карточный процессинг присылает
суммы целым числом тиын (`2792228`), ядро платежей — строкой в тенге
(`"24 534,82"`). Это одна и та же сумма в разных единицах.

**У нас:** `scale` в числовых правилах Feature Schema
(`schema/feature_schema.py:109`): тиыны приходят со `scale: 0.01`.
Целочисленность проверяется **до** применения `scale` — сумма в тиынах целая,
а те же деньги в тенге уже нет (`numeric_validator.py:153`).

### MCC

Merchant Category Code — четырёхзначный код категории торговой точки
(`5732` — электроника, `5999` — прочая розница). Международный стандарт,
приходит от карточного процессинга.

**У нас:** колонка `mcc` объявлена в контракте
(`config/source_contracts.yaml:136`), но **в Feature Schema её нет** — значит
до модели она не доходит. Категория едет отдельным полем `merchant_category`.

### merchant_id и merchant_category

`merchant_id` — идентификатор конкретной торговой точки (`M-2889`), их
десятки тысяч. `merchant_category` — категория (`ELECTRONICS`, `PHARMACY`),
их два десятка.

**У нас:** `merchant_id` объявлен в схеме с `model_input: false` и до
токенайзера не доходит (§22, `field_policies.py`); `merchant_category`
доходит и лежит в `fields` настоящего события эталона.

**Почему так:** попав в словарь, `merchant_id` дал бы десятки тысяч токенов,
каждый встреченный один-два раза. Модель не сломается — она станет хуже, и
понять почему будет не по чему (`tests/test_field_policies.py` docstring).

### business range (бизнес-диапазон)

Границы, за которыми значение бессмысленно **по существу**: отрицательный
возраст, сумма больше ВВП. Такое значение не чинят и не обрезают — оно
становится `MISSING`.

**У нас:** `min_value` / `max_value` в числовом блоке Feature Schema
(`config/feature_schema.yaml`, например `min_value: 0`,
`max_value: 100000000000` у суммы). Проверка — `numeric_validator.py:139`.

**Путают с:** clipping (см. в разделе [ML]). Business range — «значение
бессмысленно»; clipping — «значение осмысленно, но вне обучающего диапазона».

### late-arriving (опоздавшая запись)

Запись, которая приехала в хранилище заметно позже, чем произошло само
событие. Само по себе это не ошибка, но за долей таких записей следят.

**У нас:** метрика `late_arriving_rate` (§33.12), считается только у
источников, которые сообщают время загрузки — например `loaded_at` в
`core_payments` (`timestamp_normalizer.py:450`, `_is_late`).

**Путают с:** временем события. Время загрузки **не** может подменять
отсутствующее время события (§12.2) — иначе покупка «произошла» тогда, когда
её выгрузили.

### PII и классификация колонок

PII — персональные данные. В контракте класс проставлен **у каждой** колонки,
умолчания «не PII» нет: умолчание и есть та тихая ошибка, которую §4
запрещает.

**У нас:** `schema/source_contract.py:52` (`PiiClass`), пять значений: `none`,
`pseudonymous_id`, `quasi_identifier`, `sensitive`, `direct_identifier`.
Колонка с классом `direct_identifier` не может быть ни полем клиента, ни
первичным ключом, ни источником значения поля модели.

### Сессия и session_gap

Сессия — непрерывная работа клиента в приложении. Отдельные касания экрана
(`screen_open`, `button_click`) событиями не являются: событие — сессия
целиком.

Новая сессия начинается при смене клиента, при разрыве больше `session_gap`
или на явной границе (у нас это `LOGIN`).

**У нас:** `sessionizer.py:174`, `session_gap` = 30 минут
(`core/settings.py:74`), тип события `APP_SESSION`. Поля сессии: длительность,
число уникальных экранов, список экранов в хронологическом порядке.

### life-long признаки

Характеристики всей жизни клиента в банке: сколько дней открыт счёт, сколько
всего событий, сколько продуктов. Считаются на момент T.

**У нас:** шесть полей, `profile_builder.py:51` — `account_age_bucket`,
`first_seen_age_bucket`, `first_topup_age_bucket`,
`lifetime_event_count_bucket`, `lifetime_transaction_count_bucket`,
`lifetime_product_count_bucket`.

**Зачем:** модель видит не всю историю, а последние N событий. Клиент с нами
три года, а в окно попали последние двадцать действий — без life-long
признаков модель не узнает, что он старый.

### direction (направление движения)

`IN` — деньги пришли, `OUT` — ушли. Закрытый набор из трёх значений с
`MISSING` (`config/feature_schema.yaml:73`).

### payload_version

Номер версии содержимого записи у источника. Если одна и та же запись
приехала дважды с разным содержимым, побеждает большая версия — но **только**
там, где источник объявил такое правило (`update_rules: versioned_by_field`).
Ничья по версии при разном содержимом не разрешается вовсе: правило не
выбрало, и выбирать больше нечем.

**У нас:** `deduplicator.py:272` (`_resolve_by_version`).

### reversal / correction (отмена и исправление)

Отмена операции — не дубль, а отдельное событие (§9.4). Механизм **не
реализован**: ни один контракт не объявляет поле-признак отмены, и проверить
его было бы не на чем. Отложено до боевых данных (`PLAN.md`, «Ждёт боевых
данных»).

# [ML] Про модель и токенайзер

Здесь важное предупреждение: **токенайзер ещё не написан.** Всё, что помечено
ниже «определение — регламент токенайзера», в коде отсутствует, и это
сознательно: препроцессинг не имеет права ставить `RARE` или `[UNK]`.

### Признак (feature)

Одна характеристика, которую видит модель: сумма, валюта, категория мерчанта,
регион. У признака есть имя, тип, набор допустимых значений и приоритет.

**У нас:** имена признаков **конечные** — `amount_base_bucket` называется так
с самого начала, хотя проходит четыре превращения по дороге: сырая строка
`"24 534,82"` → число → тенге → `bucket_48`. Переименование в середине
потеряло бы связь между сырым значением и его местом
(`config/feature_schema.yaml:1-8`).

### Feature Schema

Единый список: какие поля существуют, у какого типа события, какого они типа,
с какими допустимыми значениями. Это общий контракт препроцессинга и
токенайзера.

**У нас:** `config/feature_schema.yaml` (504 строки), модель —
`schema/feature_schema.py:384`. Проверяет неочевидное правило: **одноимённое
поле в разных типах событий обязано иметь одинаковые тип, политику и domain** —
токен значения имеет вид `value:<поле>:<значение>` и про тип события не знает,
поэтому два разных набора значений у одного имени дали бы один токен для
разных сущностей.

### Токен

Элементарная единица, которую читает модель, — как слово для языковой модели.
Здесь токен строится не из текста, а из пары «поле = значение»
(`value:currency:KZT`) или из служебной метки.

**Определение — регламент токенайзера**, §7 и §14.4.1.1. В коде препроцессинга
токенов нет вовсе.

### token_id

Номер токена в словаре. Модель работает с числами, а не со строками.

**Определение — регламент токенайзера**, §15. Присваивается в каноническом
порядке, чтобы два прогона дали одинаковую нумерацию.

### Словарь (vocabulary)

Полный перечень токенов с их номерами. Строится **один раз** на обучающих
данных и замораживается.

**Определение — регламент токенайзера**, §14. Значение, которого в
замороженном словаре нет, становится `[UNK]`.

### Специальные токены

Служебные метки, не значения полей:

| токен | что означает | раздел |
|---|---|---|
| `[USR]` | начало блока профиля клиента | токенайзер §5.2 |
| `[EVT]` | начало события | токенайзер §5.1 |
| `[PAD]` | заполнитель до нужной длины | токенайзер §5.3 |
| `[MASK]` | закрытая позиция при обучении | токенайзер §5.4 |
| `[UNK]` | значение, которого не было в обучении | токенайзер §5.5 |

В коде препроцессинга их нет ни одного.

### Бакет (bucket, корзина)

Диапазон вместо точного числа. Модель не может работать с бесконечным
множеством разных сумм — ей нужны категории.

**У нас:** `bucketizer.py`, метка вида `bucket_48`. Настоящая запись эталона:
сумма стала `"amount_base_bucket":"bucket_48"`. Одиннадцать bucket-полей
(`data/golden_expected/bucket_field_domains.json`): суммы, зарплата,
длительность сессии, число экранов, возраст и шесть life-long.

### Границы бакетов (bucket edges)

Числа, по которым проходит деление на корзины. Считаются один раз на обучающих
данных и замораживаются в артефакте.

**У нас:** `bucketizer.py:259` (`fit_bucket_edges`) — только BUILD;
`bucketizer.py:342` (`Bucketizer`) — только применение, метода `fit` у него
**нет вовсе**. Границы хранятся **строками десятичных дробей**, а не числами
с плавающей точкой: значение ровно на границе обязано попадать в один и тот
же бакет всегда.

Интервалы левозамкнутые: `[граница[i-1], граница[i])` (`bucketizer.py:148`).

### Квантильная бакетизация

Границы ставятся так, чтобы в каждую корзину попало примерно поровну значений.
Альтернатива — равная ширина корзин (`equal_width`), но при тяжёлом хвосте
она отдаёт почти всё в первую корзину.

**У нас:** `BucketMethod` (`bucketizer.py:55`) содержит ровно два значения —
`quantile` и `equal_width`. `log_space` и `business_defined` из §19.2 не
внесены: объявить метод, которого нет в коде, нечем.

Квантильная граница берётся как **значение выборки** в позиции квантиля, а не
как интерполяция между соседями — интерполяция породила бы границу, которой в
данных нет.

### Фактическое число бакетов

Запросили 32, получили 8 — нормально: если значения целые и их мало,
квантильные границы совпадают, дубликаты удаляются, и фиксируется
**фактическое** число (§19.3).

**У нас:** так вышло с `screens_count_bucket` — запрошено 32, фактически 8
(`PLAN.md`, 2.13).

### domain (набор допустимых значений)

Полный перечень того, что может оказаться в поле. Токенайзер включает его в
словарь целиком, независимо от частоты.

**У нас:** у закрытых категорий объявлен в конфиге
(`domain: [KZT, USD, EUR, MISSING]`), у bucket-полей объявлять его в конфиге
**запрещено** — его публикует BUILD по посчитанным границам
(`schema/feature_schema.py:488`). Объявленный руками, он разошёлся бы с
посчитанным при первом изменении числа бакетов.

В domain bucket-поля всегда входит `MISSING`
(`data/golden_expected/bucket_field_domains.json`: `[..., "bucket_31", "MISSING"]`).

### closed-set и open-set

**closed-set** — набор значений известен заранее и закрыт (валюта, направление,
регион). **open-set** — значения могут появляться новые (категория мерчанта).

**У нас:** `VocabularyPolicy` (`schema/feature_schema.py:33`), четыре значения:

| политика | смысл |
|---|---|
| `closed_set` | фиксированный набор, `min_count` не применяется |
| `bucket_closed_set` | то же, но набор — метки бакетов |
| `frequency_pruned` | open-set: редкие значения станут `RARE` у токенайзера |
| `excluded` | поле до модели не доходит |

**Почему bucket-поля обязаны быть `bucket_closed_set`:** иначе редкий хвостовой
бакет схлопнулся бы в `RARE`, и крупные суммы перестали бы отличаться друг от
друга.

### MISSING

Пометка «значения нет, хотя поле применимо». Ставит препроцессинг.

**У нас:** строка `"MISSING"`, `schema/constants.py:5`. Настоящий пример из
эталона: у клиента `C000001` в профиле `"first_topup_age_bucket":"MISSING"` —
пополнений у него не было.

**Три вещи, которыми `MISSING` не является:**

- **не ноль** — ноль бывает настоящим значением (баланс, сумма);
- **не `[UNK]`** — `[UNK]` появляется у токенайзера после заморозки словаря;
- **не «поля нет»** — если поле неприменимо к этому типу события, ключа нет
  вовсе (§15.1). Разницу задаёт `required` в схеме.

### RARE

Значение, которое в обучающих данных **было**, но реже порога `min_count`.
Такие схлопываются в один токен, чтобы модель не запоминала случайности.

**Определение — регламент токенайзера**, §4.2. **Препроцессинг `RARE` не
назначает** — это охраняется составом `HighCardinalityPolicy`
(`schema/feature_schema.py:53`: только `exclude` и `pass_to_tokenizer`) и
тестом `test_high_cardinality_strategies_still_exclude_rare_assignment`.

**У нас в данных:** генератор специально кладёт категорию, которая встретится
реже порога — `TAXIDERMY` (`src/generator/catalogs.py:145`).

### [UNK]

Значение, которого в обучающих данных не было вовсе. Модель встречает его
впервые уже в бою.

**Определение — регламент токенайзера**, §4.3. В коде препроцессинга слова
`[UNK]` нет ни в одной ветке — и это принципиально: «не разобрались → `[UNK]`»
превратило бы любую ошибку в правдоподобный ответ.

**У нас в данных:** категория, которая встречается **только после T**
(`UNSEEN_ONLY_CATEGORY`, `src/generator/catalogs.py:146`) — в обучение она не
попадает по построению.

### min_count

Порог частоты: значение, встретившееся реже, становится `RARE`.

**Определение — регламент токенайзера**, §14. Применяется только к open-set
полям; к закрытым наборам и к бакетам — никогда.

### clipping (прижатие к краю)

Значение выше всех обучающих данных попадает в **самый верхний** бакет, ниже
всех — в самый нижний. Новый бакет не создаётся.

**У нас:** происходит само — сравнение с границами так и работает
(`bucketizer.py:148`). Смысл правила §19.4 не в том, чтобы это устроить, а в
том, чтобы это **заметить**: считаются `numeric_clip_rate` и отдельные
счётчики низа и верха.

**Тонкость проверки:** на полной выборке clipping невозможен структурно —
границы взяты из тех же данных, что потом размечаются. Настоящий случай — это
ENCODE на данных, которых BUILD не видел, поэтому проверка гоняет BUILD по
усечённой выборке (`PLAN.md`, 2.13).

**Путают с:** business range (см. [домен]).

### Утечка будущего (leakage)

Ситуация, когда в обучающие признаки попала информация, которой на момент
предсказания ещё не было. Модель «угадывает» идеально, а в бою проваливается.

**У нас:** от утечки защищает отсечка по T, стоящая **рано** в цепочке — до
расчёта профиля, агрегатов, сессий и границ бакетов. Если отсекать в конце,
каждый из этих расчётов успеет увидеть будущее, а в самих событиях это будет
не видно (`cutoff.py` docstring).

### truncation (обрезка истории)

Выбор последних N событий клиента, которые увидит модель. Всей истории может
быть десять тысяч событий, а окно модели — сотни.

**Определение — регламент токенайзера**, §18. Препроцессинг timeline
**не режет**: он сохраняет историю целиком (§26 п.7), решение о размере окна
принадлежит токенайзеру.

### delta_from_previous_event

Сколько времени прошло с прошлого события клиента. Важный признак: три покупки
подряд за минуту и три за месяц — разное поведение.

**У нас:** финальное значение **не хранится** и не считается вовсе
(`schema/constants.py:23`, `time_feature_builder.py` docstring). Причина:
дельту нужно считать **после** обрезки истории — сосед по полной истории может
в окно не попасть, и сохранённое значение оказалось бы неверным. Препроцессинг
считает только **границы** для неё (`time_delta.py`).

### FIRST_EVENT и WINDOW_START

Два зарезервированных значения канала времени. `FIRST_EVENT` — «предыдущего
события не существует, это самое первое в жизни клиента». `WINDOW_START` —
«предыдущее событие есть, но оно не попало в окно».

**У нас:** `time_delta.py:47-48`. Они **вне** обычных границ — попасть в них
расчётом нельзя. Различить их можно только благодаря флагу `lifetime_first`,
который ставит препроцессинг.

### lifetime_first

Флаг «это самое раннее известное событие клиента».

**У нас:** `time_feature_builder.py`. Не назначается, а **выводится** из
`position == 0`, проставленной сортировкой. Параметра, которым его можно
поставить в другое место, нет. Настоящий пример из эталона: у первого события
клиента `C000000` стоит `"lifetime_first":true`, у следующего — `false`.

### padding и attention_mask

Модель принимает последовательности одинаковой длины, поэтому короткие
дополняются токеном `[PAD]` справа, а `attention_mask` говорит модели, какие
позиции настоящие, а какие добивка.

**Определение — регламент токенайзера**, §19. В препроцессинге не существует.

### masking 80/10/10

Приём обучения: часть токенов закрывается, и модель учится их восстанавливать.
Из выбранных позиций 80% заменяются на `[MASK]`, 10% на случайный токен, 10%
остаются как есть.

**Определение — регламент токенайзера**, §20. В препроцессинге не существует.

### embedding

Превращение номера токена в вектор чисел, с которым дальше работает нейросеть.
Это уже сама модель, не токенайзер.

**Упоминается** в регламенте токенайзера (§10, §30) как то, куда уходят
token_id и признаки времени. В нашем коде нет.

### Многозначное поле (multivalue)

Поле, где значений несколько: список продуктов клиента, список экранов сессии.

**У нас:** режется до `max_values_per_field` (8 по умолчанию,
`core/settings.py:77`), причём у каждого такого поля обязан быть объявлен
`order_significant` — значим порядок или нет. Значим (экраны) — сохраняется
хронология и режется хвост; незначим — сортируется и режется.

**Тонкость:** `screens_count` считается по **полному** списку до обрезки,
потому что бакетизируется именно он. Числа расходятся намеренно, и на этом
стоит отдельный тест — «починка» из лучших побуждений сломала бы смысл
признака.

### Высокая кардинальность (high cardinality)

Поле, у которого слишком много разных значений: `merchant_id`, `device_id`,
`transaction_id`.

**У нас:** `HighCardinalityPolicy` (`schema/feature_schema.py:53`), две
реализованные стратегии: `exclude` (не доходит до модели) и
`pass_to_tokenizer` (доходит, решение о редкости — за токенайзером). Три
стратегии §22, которых в коде нет, в перечислении **не объявлены**.

### TRAIN / Validation / Test

Разбиение данных: на TRAIN учатся и считают правила, на Validation
настраивают, на Test проверяют.

**У нас:** разбиения **нет** — генератор делает один набор, и TRAIN это он
целиком. `DatasetRole` содержит только `train` и `golden_input`: объявить
набор, которого не существует, значило бы обещать разбиение
(`src/generator/config.py:14`).

### baseline и мониторинг качества

Значения метрик на эталонных данных, с которыми сравнивают текущий прогон.

**У нас:** 16 метрик §33 (`core/monitor.py:44`), от `cutoff_violation_rate` до
`profile_missing_rate`. Считаются как **доли**: числитель (сколько раз
случилось) и знаменатель (сколько раз могло случиться) хранятся отдельно.
Пороги **не применяются** — регламент говорит «уточняются по baseline банка»,
а на синтетике baseline нет.

**Тонкость:** доля без знаменателя — не ноль, а `None`. «Ноль ошибок» и «ни
одной попытки» — разные состояния (`core/monitor.py:213`).

# [техн] Про код и воспроизводимость

### Детерминизм

Одинаковый вход всегда даёт одинаковый выход — байт в байт, на любой машине,
при любом числе процессов, в любом порядке обхода файлов.

**У нас:** это требование регламента (§29), а не пожелание. На нём стоят
`event_id`, границы бакетов, эталон и сравнение прогонов. Проверяется:
BUILD/ENCODE в 1 процесс против 4 (`tests/test_conformance.py`), обход партиций
в прямом и обратном порядке (`pipeline.py:865`).

### seed и global_seed

Число, из которого выводится вся «случайность». Один и тот же seed → те же
данные и та же выборка.

**У нас:** `core/settings.py:68`, значение `20260101`. Тот же seed у генератора
(`data/raw/_meta/manifest.json`: `"seed": 20260101`).

**История, которую стоит знать:** первая формула комбинирования seed с ключом
записи была неверной. `20260101` занимает младшие биты 64-битного числа, а
выборка упорядочивается по значению целиком, то есть по старшим — при простом
XOR два разных seed давали **пересечение выборок 500 из 500**. Лечится
умножением на нечётную константу золотого сечения `0x9E3779B97F4A7C15`
(`core/hashing.py:45`), после чего пересечение стало 0 из 500.

### RNG

Генератор псевдослучайных чисел. «Псевдо» — потому что последовательность
полностью определяется seed.

**У нас:** только в генераторе синтетики (`src/generator/rng.py`). Поток
случайности выводится из seed и **ключа потока** (источник, клиент, номер
записи), а не из общего последовательного состояния — тогда результат не
зависит от порядка обхода. В препроцессинге случайности нет вообще.

### JSONL

Текстовый формат: одна строка — один JSON-объект. Удобен тем, что файл можно
читать потоком и сравнивать построчно, не загружая целиком.

**У нас:** и вход (`data/raw/<источник>/<дата>.jsonl`), и выход
(`prepared_events.jsonl`). Каждая строка канонизируется отдельно: файл целиком
не является JSON-документом, зато сравним побайтно.

### Канонический JSON (каноническая сериализация)

Способ записать данные так, чтобы одинаковое содержимое всегда давало
одинаковые байты: ключи отсортированы по байтам UTF-8, никаких лишних
пробелов, `-0.0` приводится к `0.0`, `NaN` запрещён.

**У нас:** `core/canonical.py:68` (`canonical_bytes`), формат зафиксирован в
`SERIALIZATION_CONFIG` (`:27`) и сам входит в хэшируемое состояние.

**Зачем:** обычный `json.dumps` порядок ключей не гарантирует. Без канона
`preprocessing_state_sha256` и сравнение прогонов не значили бы ничего.

### Хэш, SHA-256

«Отпечаток» данных фиксированной длины. Одинаковые данные → одинаковый
отпечаток; изменилось что угодно → отпечаток другой.

**У нас:** только SHA-256; встроенный питоновский `hash()` **запрещён** — он
рандомизирован между запусками процесса, и `event_id` менялся бы от прогона к
прогону (`core/hashing.py` docstring).

### length-prefix

Способ склеить несколько полей в один вход для хэша так, чтобы склейка была
однозначной: перед каждым полем пишется его длина в байтах.

**У нас:** 8 байт, big-endian (`core/hashing.py:59`, `HASH_POLICY`).

**Зачем:** разделитель-символ не годится — утверждение «этот символ не
встретится в данных» недоказуемо. Без префикса `("ab","c")` и `("a","bc")`
дали бы одинаковую склейку `abc` и один хэш.

### event_id

Стабильный идентификатор события: первые 128 бит SHA-256 от источника,
идентификатора записи, типа события и времени. 32 шестнадцатеричных символа.

**У нас:** `core/hashing.py:156`. Настоящее значение из эталона:
`f8227b0222955926162905514ce54046`.

**Главное свойство:** никакой случайности — ни UUID, ни текущего времени, ни
номера процесса. Повторный прогон обязан дать тот же идентификатор.
Совпадение `event_id` у двух разных записей — блокирующая ошибка.

### business fingerprint (бизнес-отпечаток)

Хэш от **смысловых** полей записи (клиент, время, сумма, валюта, направление,
мерчант) — им ловятся дубли, приехавшие под разными идентификаторами.

**У нас:** `core/hashing.py:175`, состав полей объявлен в
`config/dedup_policy.yaml` и версионируется вместе с ней. В пре-образ входит
маркер присутствия поля, иначе отсутствующий `direction` и `direction: ""`
дали бы один отпечаток.

### content hash / preprocessing_state_sha256

Отпечаток **всего состояния** препроцессинга: контракты, маппинги, схема,
политики, посчитанные границы. Отвечает на вопрос «тем ли состоянием посчитаны
данные, что лежит рядом с ними».

**У нас:** `artifact_hasher.py:95`, 22 раздела (18 из перечня §30 плюс четыре
обоснованных). Настоящее значение эталона:
`1dc34b8d541a6615fda037688255a36f01ef605231e7ab2d53fd976f1a289894`.

Несовпадение при загрузке **останавливает** обработку. Вариант «продолжить с
предупреждением» не выражается: `verify_state_hash` ничего не возвращает,
проверять её результат нечем.

**Что в хэш не входит и почему:** число процессов, пути к каталогам, debug,
время сборки, baselines. Критерий один — **участвует ли артефакт в
преобразовании данных**. Границы бакетов участвуют и входят, хотя тоже
посчитаны из данных; baselines только сравнивают при мониторинге.

### code_state_sha256

Отпечаток самого кода: хэш содержимого файлов `src/`, `tools/` и `config/`.

**У нас:** `artifacts.py:142`. Взят **вместо** имени коммита как основной
пункт: `git commit` описывает код честно только при чистом рабочем дереве, а
BUILD с незакоммиченными правками записал бы «собрано коммитом X», хотя из X
получилось бы другое. Коммит и флаг `dirty` пишутся рядом справкой.

`tests/` в хэш кода не входит: тесты прогон не выполняют.

### Партиция

Кусок данных, который читается и обрабатывается как единица. У нас партиция —
календарный месяц одного источника, то есть один файл.

**У нас:** `source_reader.py:69` (`Partition`), раскладка
`data/raw/<источник>/<YYYY-MM-DD>.jsonl`, где имя — первый день месяца. В
основном наборе 152 партиции, в golden — 148.

Порядок партиций задаётся **сортировкой в коде** по каноническому пути, а не
порядком, в котором их отдала файловая система (§29 п.1).

### Воркер, ProcessPoolExecutor, spawn

Воркер — отдельный процесс, обрабатывающий свою партицию. `ProcessPoolExecutor` —
стандартный питоновский пул процессов. `spawn` — способ запуска процесса
(на Windows единственный), при котором дочерний процесс стартует с нуля и
импортирует модули заново.

**У нас:** `parallel.py`, параллельно идут **чтение и разрешение клиента**;
дальше цепочка сходится, потому что дедупликации нужен весь поток.

**Следствие `spawn`, стоившее ложного замера:** всё, что родитель настраивает,
обязано уезжать в воркер **явно**. Предел ожидания жил константой модуля, и
подмена его в родителе ни на что не влияла — воркер импортировал модуль заново
и брал умолчание. Сквозная проверка показывала 30 секунд при объявленных 1, 3
и 6 (`CLAUDE.md`).

### Барьер старта

Точка, где воркеры дожидаются друг друга перед первой задачей.

**У нас:** `parallel.py:301`. Нужен, потому что запуск процесса на Windows
дороже чтения партиции на порядки: первый поднявшийся воркер успевает разобрать
всю очередь раньше, чем появятся остальные, и «параллельный» прогон оказывается
последовательным. Измерено: под нагрузкой без барьера опыт состоялся 1 раз из
10, с барьером — 10 из 10.

У барьера есть предел ожидания: барьер без таймаута висит насмерть, если
воркер не поднялся вовсе.

### «Не пройдена» против «не проведена»

Разные факты, и путать их нельзя. Выходы разошлись — проверка **не пройдена**,
это красный прогон. Работа фактически не разделилась между процессами —
проверка **не проведена**, сравнивать было нечего, и её надо повторить.

**У нас:** два разных типа ошибки, `ParallelismNotProvenError`
(`parallel.py:61`) и `ParallelOutputMismatchError` (`:70`).

**Зачем разделять:** «красное на несложившихся условиях» читается как «тест
мигает», и через месяц его отключат — и будут правы.

### tie-break

Правило, решающее порядок при полном совпадении основного ключа. У нас —
когда два события произошли в один и тот же момент.

**У нас:** три части ключа (§13), каждая на случай, когда предыдущей мало:
время → ранг источника → идентификатор записи (`timeline_builder.py:164`).

### ordering_key

Ключ сортировки, записанный строкой прямо в событие: решение о порядке видно в
данных, а не спрятано в коде сортировщика.

**У нас:** `timeline_builder.py:186`. Настоящее значение из эталона:

```
"2023-09-01T12:54:32Z|000020|CRD-CH000000-00027"
   время                ранг    идентификатор записи
```

Ранг печатается фиксированной шириной (`000020`), иначе строковое сравнение
поставило бы ранг `10` перед `9`.

### frozen dataclass

Класс-контейнер, поля которого нельзя изменить после создания.

**У нас:** приём, которым выражается **полнота**. `PreprocessingState`
(`artifact_hasher.py:95`), `RequiredArtifacts` (`artifacts.py:102`),
`TokenizerContract` (`prepared_output.py:121`) — у всех нет ни одного значения
по умолчанию, поэтому забыть раздел нельзя: это ошибка при сборке объекта, а не
тихо неполный результат.

**Тонкость, стоившая ложной мутационной проверки:** в Python поле со значением
по умолчанию не может стоять **перед** полем без умолчания — класс не создастся
вовсе. Мутацию «добавить умолчание» ловил сам Python, а не наша проверка
(`CLAUDE.md`, случай 4).

### pydantic, pydantic-settings

Библиотеки проверки данных. `pydantic` описывает, как выглядит правильный
объект, и отвергает неправильный при создании. `pydantic-settings` — то же для
конфигурации прогона.

**У нас:** все конфиги и все канонические модели. Проверки делаются **один раз
при загрузке**, а не на каждой записи: ошибка в конфиге обязана падать на
старте, а не через час обработки странным `KeyError`.

### StrEnum

Перечисление, значения которого — строки. Главный инструмент приёма «запрет
выражается отсутствием возможности»: чего нет в перечислении, то нельзя
объявить в конфиге.

**У нас:** `FieldType` (`schema/feature_schema.py:42`) — только `categorical`
и `bucket`, текстового типа нет, поэтому свободный текст объявить нечем;
`ViolationPolicy` (`category_normalizer.py:64`) — только `missing` и
`schema_violation`, «завести новую категорию» объявить нечем.

### Decimal против float

`float` — двоичная дробь, в ней `0.1 + 0.2 ≠ 0.3`. `Decimal` — десятичная,
считает как человек на бумаге.

**У нас:** деньги разбираются только через `Decimal`
(`numeric_validator.py`), границы бакетов хранятся строками. Ошибка округления
здесь всплыла бы не сразу, а на сравнении хэшей — то есть в самом дорогом месте.

**Замер, стоящий отдельного упоминания:** на настоящем артефакте через `float`
портятся 247 границ из 315 — квантильная граница это значение выборки, поэтому
среди них целые (`294` → `294.0`) и суммы с хвостовым нулём
(`2500.50` → `2500.5`).

### aware и naive время

`aware` — момент с указанием зоны, `naive` — без. Наивное время неоднозначно:
непонятно, что за момент имеется в виду.

**У нас:** наивное время на выходе — блокирующая ошибка (`schema/event.py:87`).
Наивным приходит вход от `app_logs` (`"2024-01-08T18:32:54"`) — зону ему
назначает политика источника, а не догадка.

### IANA timezone, zoneinfo, tzdata

IANA-зона — имя вида `Asia/Almaty`, за которым стоит вся история переводов
часов. `zoneinfo` — питоновский модуль, который это имя понимает. `tzdata` —
пакет с самой базой; на Windows без него истории нет.

**У нас:** в записи хранится **имя зоны**, а не смещение
(`schema/event.py:96`). Причина конкретная: Казахстан перешёл на UTC+5
1 марта 2024, до этого Алматы жил в UTC+6. Фиксированное `+05:00` дало бы для
истории час, которого не было; имя зоны помнит, число — нет.

В данных есть 5993 события до 2024-03-01, так что путь не теоретический
(`PLAN.md`, 2.17).

### epoch millis / epoch microseconds

Время как число единиц от 1 января 1970. Карточный процессинг присылает
миллисекунды (`1705069132000`); в пре-образ хэша время идёт микросекундами
целым числом.

**У нас:** `core/hashing.py:143`. Перевод считается через `timedelta`, а не
делением на 1000 — `float` потерял бы точность на миллисекундах.

### Артефакт и заморозка

Артефакт — файл, который обязан пережить прогон и по которому потом
восстанавливают, чем именно получены данные. Заморозка — момент, когда
посчитанное записывается и больше не пересчитывается.

**У нас:** `artifacts/<версия препроцессинга>/`, 32 обязательных пункта §31
(`artifacts.py:61`) плюс рабочие файлы и читаемые копии — всего 39 файлов.
Один пункт = один файл, чтобы перечень читался как листинг каталога.

### Версионирование

У каждого конфига и каждого посчитанного артефакта есть версия. Комплект всех
версий обязан быть полным: пустая версия хуже отсутствующей — она выглядит как
версия и сравнивается как версия.

**У нас:** `core/versions.py:30`, незаполненная помечается строкой `UNSET`
(`:23`) и ловится `require_complete()` перед заморозкой и перед выдачей
метаданных.

### golden vectors, golden_input, golden_expected

Замороженная пара «эталонный вход → эталонный выход». Любой прогон обязан
воспроизвести выход байт-в-байт.

**У нас:**

- `data/golden_input/` — 14 клиентов, 5 источников, 148 файлов, 2554 записи,
  все 32 краевых случая;
- `data/golden_expected/` — 374 события, 14 профилей, набор допустимых значений
  bucket-полей и хэш состояния;
- сверка — `golden.py:146`, четыре артефакта сравниваются **порознь**, чтобы
  расхождение называлось по имени.

**Встроенная вырожденность, которую надо помнить:** эталон снимается тем же
кодом, с которым потом сравнивается, поэтому первое сравнение зелёное **по
построению** и не доказывает ничего. Доказывает обратное — что изменение кода
красит именно тот артефакт, который изменился; это прогонялось отдельно по
каждому из четырёх.

### conformance

Проверка соответствия эталону — полная цепочка от `seed` до сравнения с
`golden_expected`.

**У нас:** `tests/test_conformance.py`, помечен маркером `conformance` и
**исключён** из обычного прогона: он поднимает генератор, полный BUILD и четыре
процесса — около минуты. Запуск явный:
`pytest -m conformance -p no:faulthandler`.

Весь модуль уходит в **пустой временный каталог**: там нечего подставить, и
относительный путь к входным данным упадёт на любой машине, а не только на
чистом клоне.

### Мутационное тестирование

Проверка самих проверок: в код специально вносится ошибка, и смотрят, упадёт
ли тест. Не упал — тест пустышка.

**У нас:** `tools/mutation.py`. Мутация **объявляет**, каким тестом и с каким
сообщением она обязана быть поймана, а harness сверяет объявленное с
фактическим. Вердикты (`:65`):

| вердикт | смысл |
|---|---|
| `CAUGHT` | упало объявленное, с объявленным сообщением |
| `WRONG_CATCH` | упало, но не то или не с тем сообщением — **считается не пойманной** |
| `SURVIVED` | прогон зелёный |
| `HUNG` | превышен предел времени |
| `NOMATCH` | фрагмент для замены не найден, мутация не применилась вовсе |

**Зачем такая строгость:** «красный прогон» дважды принимался за доказательство,
хотя падал сам Python, а не наша проверка.

### Страховка от вырожденности

Утверждение внутри теста о том, что **данные теста годятся** для проверки.
Например: «вход не отсортирован заранее», «границы не переживают перевод через
float», «локальный час отличается от часа UTC».

**У нас:** `assert_input_is_not_ordered` и `assert_key_is_decisive`
(`tests/test_timeline_builder.py:138,149`),
`assert_edges_do_not_survive_float` (`tests/test_encode_phase.py:67`),
`assert_local_hour_differs_from_utc` (`tests/test_time_features.py:81`).

**Предел страховки:** каждая сторожит ровно то свойство, под которое написана,
и ни миллиметром больше. Универсальной не бывает — что данные не выродились по
следующему признаку, показывает только мутационная проверка.

### §N — ссылка на регламент

Знак параграфа с номером — ссылка на раздел регламента: `§19` — бакетизация,
`§29.1` — каноническая сериализация. По умолчанию имеется в виду
`preprocessing_rules_official.md` (38 разделов); если речь о токенайзере, это
сказано словами.

### no-op

Вызов, который ничего не делает. У нас так работает debug-режим при
`debug = false`: вызовы остаются в коде компонентов, но не делают ничего и
результат не меняют.

### YAML

Формат конфигов: человекочитаемый, с отступами вместо скобок.

**У нас:** все 12 конфигов. В хэш состояния идёт **разобранное** содержимое, а
не текст: переставленные строки, правка комментария и другой отступ не меняют
ни одного решения пайплайна, а хэш по тексту менялся бы от каждого из них.

### Poetry, package-mode = false

Poetry — менеджер зависимостей. `package-mode = false` означает «это не
библиотека для установки, а проект, который просто запускают».

**У нас:** `pyproject.toml`. Зависимостей всего четыре: `pydantic`,
`pydantic-settings`, `pyyaml`, `tzdata`. Ни веб-фреймворка, ни базы данных, ни
обращений к сети — вся логика детерминированная и оффлайновая.

### pytest marker

Метка на тесте, по которой его можно включить или исключить из прогона.

**У нас:** один маркер — `conformance` (`pyproject.toml:59`), и обычный прогон
идёт с `-m 'not conformance'`.
