# Шпаргалка по препроцессингу — навигация

Этот каталог отвечает на один вопрос: **открыли любой файл проекта — что это,
зачем оно тут и на каком пункте плана появилось.**

Источник истины — код. Если `PLAN.md` и код расходятся, прав код; расхождения
помечаются прямо в тексте словами «в плане написано X, в коде Y».

---

## Как пользоваться

1. Не знаешь термин → [01-glossary.md](01-glossary.md). Читается отдельно, без
   остального.
2. Ткнули пальцем в файл → [обратный индекс](#обратный-индекс-файл--раздел)
   ниже. Находишь строку, идёшь в названный раздел.
3. Не понимаешь, что происходит с данными → [07-data-flow.md](07-data-flow.md):
   одна настоящая запись проходит всю цепочку.

## Что где лежит: пять слоёв проекта

```
config/*.yaml            ← правила: что считать валидным, как переводить, где границы
       │
src/generator/           ← этап 0: делает грязные данные, которых иначе неоткуда взять
       │  пишет
       ▼
data/raw/  data/golden_input/
       │  читает
       ▼
src/preprocessing/core/  ← этап 1: фундамент (байты, хэши, настройки, метрики)
src/preprocessing/schema/ ← этап 1: модели «как выглядит правильное»
src/preprocessing/*.py   ← этап 2: 17 компонентов, каждый делает одну вещь
src/preprocessing/pipeline.py ← этап 3: собирает их в BUILD и ENCODE
       │  пишет
       ▼
artifacts/<версия>/      ← замороженные правила (границы бакетов, версии, хэш)
data/prepared/<набор>/   ← то, что уедет токенайзеру
       │  сверяется с
       ▼
data/golden_expected/    ← эталон: тот же вход обязан дать те же байты
tests/                   ← этап 4 и проверки к каждому шагу
tools/mutation.py        ← проверка самих проверок
```

Ключевое разделение, из-за которого файлы делятся на две группы:

- **BUILD** считает правила **один раз** на обучающих данных (границы бакетов,
  границы дельты, набор допустимых значений) и **замораживает** их в
  `artifacts/`;
- **ENCODE** эти замороженные правила **применяет** и никогда не пересчитывает.

Оба живут в `pipeline.py`, но это разные функции с разными типами аргументов —
см. [01-glossary.md](01-glossary.md), статьи «BUILD» и «ENCODE».

сюда по своим пунктам плана — в блоки «ключевые решения и почему именно так».

Чего в нём **нет** и ради чего написана эта шпаргалка:

- ни одной ссылки на файл или строку — по нему нельзя найти, где что лежит;
- этапы 3 и 4 не разобраны вовсе;
- этапы 0 и 1 сжаты до полутора страниц без разбора по файлам;

## Как проверялась привязка «файл → пункт плана»

Честно про метод, потому что от него зависит доверие к таблицам выше.

1. **Docstring модуля.** Каждый файл `src/` начинается с описания, где назван
   раздел регламента (`§19`, `§29.1`) и суть компонента. Прочитаны все 60.
2. **`PLAN.md`, строки «Реализовано:».** У каждого пункта плана перечислены
   файлы, которые на нём появились.
3. **Реестр компонентов в коде.** `core/debug_dump.py:74` — кортеж
   `COMPONENTS`, где у каждого из 17 компонентов проставлены и номер в цепочке,
   и раздел регламента, и **пункт плана**. Для этапа 2 это привязка из самого
   кода, а не из плана.
4. **История git.** Работает только для файлов, добавленных после 3.2: этапы
   0–3.2 приехали одним коммитом (`Препроцессинг: этапы 0-3.2`), и по нему
   пункт не определить. Для `artifacts.py`, `golden.py`, `output_contract.py`,
   `parallel.py`, `prepared_output.py`, `tools/mutation.py` и семи тестов пункт
   виден прямо в теме коммита.

Где методы 1–3 давали разное, в таблице стоит диапазон (`0.1–0.2`, `2.1–2.3`) —
это значит «файл обслуживает оба пункта», а не «не разобрались».

**Чего не сделано:** `pytest` в этом окружении запустить не удалось —
виртуального окружения на машине нет, `pydantic`, `pydantic-settings`, `yaml`
и `tzdata` не установлены. Поэтому число тестов посчитано текстом, а не
прогоном, и примеры «было → стало» для промежуточных шагов цепочки пока
брать неоткуда: `data/prepared/`, `data/debug/` и `artifacts/` на диске
отсутствуют. Настоящие данные, которые есть прямо сейчас, — это вход
(`data/golden_input/`) и выход (`data/golden_expected/`).
