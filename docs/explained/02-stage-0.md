# Этап 0 — генератор синтетики (0.1–0.4)

Пункты плана: 0.1 каркас, 0.2 пять источников, 0.3 краевые случаи,
0.4 два набора данных.

Запуск всего этапа — одна команда:

```
python -m src.generator.build_dataset          # оба набора
python -m src.generator.build_dataset --only golden
```

## 0.1 Каркас генератора

### Что за задача

Отлаживать обработку данных не на чем: боевые данные банка недоступны, а без
входа ни один компонент цепочки не проверишь. Поэтому первым делом пишется
фабрика поддельных данных — с тем же разнобоем форматов, что у настоящих
систем.

Главное требование к ней то же, что и ко всему проекту: **один и тот же seed →
байт-в-байт те же файлы**. Иначе эталон §29.2 не воспроизвести — сравнивать
будет не с чем.

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `src/generator/config.py` | появился | один объект, полностью определяющий выход генератора |
| `src/generator/rng.py` | появился | детерминированная случайность: RNG на каждый поток отдельно |
| `src/generator/records.py` | появился | контейнер сырой записи `RawRecord` |
| `src/generator/writer.py` | появился | запись в партиции + контрольные суммы для манифеста |
| `src/generator/clients.py` | появился | 200 синтетических клиентов с идентификаторами в каждой системе |
| `src/generator/timing.py` | появился | время: событие рождается локальным, потом переводится в UTC |
| `src/generator/build_dataset.py` | появился | точка входа: собрать набор, проверить полноту, записать манифесты |

### Что внутри каждого файла

**`config.py`** — `GeneratorConfig` (`:28`), неизменяемая (`frozen=True`) модель
из 12 полей: `seed`, число клиентов, период истории, `cutoff_time`, множитель
объёма, каталог, имя и роль набора, версии.

Отдельно `DatasetRole` (`:14`) — ровно два значения, `train` и `golden_input`.
Ролей Validation и Test **нет**: объявить набор, которого генератор не делает,
значило бы пообещать разбиение.

Валидатор `_check_period` (`:79`) требует, чтобы T попадал **внутрь** периода
истории — иначе события после T сгенерировать не из чего, а без них не
проверить отсечку.

**`rng.py`** — три функции.
`derive_rng(seed, *parts)` (`:15`) — вернуть отдельный генератор для потока,
заданного ключом: `derive_rng(seed, "core_payments", "C000007")`.
`_digest` (`:21`) склеивает части с length-prefix — тем же приёмом, что §29.1
п.10 требует от препроцессинга.
`weighted_choice` (`:33`) — взвешенный выбор с **отсортированными** ключами.

**`records.py`** — `RawRecord` (`:11`): источник, дата партиции, ключ
сортировки, `payload`. Payload намеренно нетипизирован: у каждого источника
своя схема, приводить их к общему виду — работа препроцессинга.

**`writer.py`** — `JsonlWriter` (`:33`). `write` (`:45`) группирует записи по
партициям, сортирует внутри партиции по `sort_key`, чистит файлы прошлого
прогона (`:62`) и пишет каждую партицию, возвращая `FileInfo` с числом записей
и SHA-256 (`:79`).

**`clients.py`** — `SyntheticClient` (`:20`) и `build_clients` (`:49`).
У клиента с индексом 7: `client_id = C000007` (ground truth),
`client_ref = 000007`, `cardholder_id = CH000007`, `login_id = L000007`,
`cif = CIF000007`. Плюс регион, зона, занятость, год рождения, дата открытия
счёта, множитель активности, продукты, зарплата.
`identity_mapping` (`:93`) собирает таблицу «ссылка источника → `client_id`» —
она уедет в `_meta/` набора и станет входом для §7.

**`timing.py`** — `draw_local_datetime` (`:25`) выбирает момент по суточному
профилю активности `HOUR_WEIGHTS` (`:17`): ночью почти пусто, пики в обед и
вечером. `month_start` (`:55`) даёт имя партиции. `epoch_millis` (`:94`)
считает миллисекунды **целочисленно** через `timedelta`.

**`build_dataset.py`** — `build(config)` (`:72`): раздать роли краевых случаев,
рассчитать их календарь, сгенерировать все пять источников, записать,
**проверить полноту** и записать три файла в `_meta/`.

### Ключевые решения и почему именно так

**1. RNG выводится из ключа потока, а не из общей последовательности.**

Обычный подход — один `random.Random(seed)` на весь генератор. Тогда результат
зависит от **порядка обхода**: поменяли местами два источника — изменились все
данные. Здесь у каждого потока свой генератор из seed и ключа
(`rng.py:15`), поэтому записи клиента `C000007` в `core_payments` одни и те
же независимо от того, сколько клиентов и источников обработано до него.

*Иначе:* любая перестановка кода меняла бы весь датасет, и golden-эталон
пришлось бы перезамораживать после каждой правки.

**2. Порядок ключей при выборе фиксируется сортировкой** (`rng.py:36`).

`rng.choices(list(options), ...)` дал бы результат, зависящий от порядка
вставки в словарь.

**3. Три вещи, от которых зависит побайтовая одинаковость файлов**
(`writer.py:34-40`): сортировка записей внутри партиции, перевод строки всегда
`\n` (а не CRLF от Windows), `sort_keys=True` в JSON.

*Иначе:* два прогона на одной машине совпали бы, а на разных — нет, и это
выяснилось бы на чужом компьютере в самый неудобный момент.

**4. Файлы прошлого прогона удаляются** (`writer.py:62`).

Изменили период истории — старые партиции остались бы лежать рядом с новыми, и
набор перестал бы соответствовать своему манифесту.

**5. Время рождается локальным.**

Событие сначала выбирается в зоне клиента и только потом переводится в UTC
(`timing.py:25`). Если делать наоборот, «пик активности в обед» размажется по
клиентам из разных зон, и локальные признаки §25 нечего будет проверять.

### Пример на реальных данных

Настоящая строка из `data/golden_input/core_payments/2024-01-01.jsonl`:

```json
{"amount": "24 534,82", "branch_region": "ASTANA", "client_ref": "000000",
 "counterparty_ref": "KZ745896886064", "currency": "тенге", "direction": "OUT",
 "loaded_at": "2024-01-13T08:52:12Z", "op_code": "PMT",
 "operation_time": "11.01.2024 21:44", "payload_version": 1,
 "source_record_id": "CP-000000-00007"}
```

Видно всё разом: ключи отсортированы по алфавиту (`amount` первый), сумма —
строка с неразрывным разделителем тысяч и запятой, валюта написана словом,
время локальное без зоны, а `loaded_at` (когда запись доехала до хранилища) на
двое суток позже самой операции.

Манифест набора (`data/raw/_meta/manifest.json`) на основном наборе:

```
seed = 20260101, n_clients = 200, total_records = 76797, файлов = 152
history_start = 2023-09-01, history_end = 2026-02-28
cutoff_time = 2026-01-31T23:59:59Z, dataset_role = train
```

### Что сломается, если этого не будет

Без генератора нечего обрабатывать — ни один компонент этапа 2 не запустить, и
эталон §29.2 снять не с чего. Без **детерминированности** генератора эталон
теряет смысл: перегенерировали вход — он стал другим, и «выход не совпал»
перестало что-либо значить.

## 0.2 Пять источников с разными схемами

### Что за задача

Source Contract (§4) проверяет, что данные соответствуют объявленной схеме. На
пяти одинаковых источниках проверять нечего — разнородность и есть предмет
проверки. Поэтому у каждого источника **намеренно свой** формат времени, своя
запись суммы, свой идентификатор клиента.

Отдельное требование плана: событийных источников должно быть **минимум два** —
иначе нечем проверить tie-break по рангу источника (§13) и межисточниковые
дубли (§9.2).

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `src/generator/catalogs.py` | появился | справочники намеренно грязных значений |
| `src/generator/sources/__init__.py` | появился | перечень имён источников |
| `src/generator/sources/core_payments.py` | появился | ядро платежей — «человеческий» формат |
| `src/generator/sources/card_processing.py` | появился | карточный процессинг — машинный формат |
| `src/generator/sources/app_logs.py` | появился | логи приложения — сырьё для сессий |
| `src/generator/sources/profile_snapshots.py` | появился | помесячные снимки профиля |
| `src/generator/sources/fx_rates.py` | появился | курсы валют по рабочим дням |

### Что внутри каждого файла

**`catalogs.py`** — только данные, без логики. Ключевое:

- `REGIONS` (`:14`) — регион → IANA-зона. Регионы с **разными** зонами взяты
  специально: `Asia/Almaty`, `Asia/Qostanay`, `Asia/Aqtobe`, `Asia/Atyrau`,
  `Asia/Oral`;
- `CURRENCY_ALIASES_TEXT` (`:46`) — как валюта выглядит в человеческом вводе:
  `KZT`, `kzt`, `тенге`, `ТЕНГЕ`, `398`; `CURRENCY_ISO_NUMERIC` (`:52`) — как
  её пишет процессинг;
- `MERCHANT_CATEGORY_WEIGHTS` (`:75`) — 18 категорий с длинным хвостом:
  `GROCERY` 26%, а `FALCONRY_SUPPLIES` 0.1%. Хвост нужен, чтобы у токенайзера
  было что схлопывать в `RARE`;
- `EXTENDED_PRODUCTS` (`:137`) — 11 продуктов, заведомо больше лимита в 8;
- `RARE_ONLY_CATEGORY = "TAXIDERMY"` и `UNSEEN_ONLY_CATEGORY = "CRYPTO_EXCHANGE"`
  (`:145-146`) — категории, которые **никогда не выпадают случайно**: они
  появляются только через инъекцию, поэтому их частота предсказуема.

**`core_payments.py`** — `generate` (`:47`) отдаёт фоновые события
(`_background`, `:63`) и инъекции (`_injections`, `:131`). Формат payload
собирает `_payload` (`:321`). Сумма форматируется `_format_amount` (`:361`):
в 25% случаев `"15000.50"`, иначе `"15 000,50"` — обе формы реально
встречаются в выгрузках, и разобрать обязан обе.

**`card_processing.py`** — `_background` (`:60`). Три операции: `PUR` (покупка,
78%), `WDR` (снятие, 20%), `BLK` (блокировка, 2%). У блокировки нет ни суммы,
ни валюты; у снятия нет мерчанта, но есть `atm_id`. **Ключи просто
отсутствуют** — это §15.1 «поле неприменимо», а не `MISSING`.

**`app_logs.py`** — `_sessions` (`:63`) и `_session_script` (`:94`): вход
(`LOGIN`), затем 3–14 открытий экранов, часть с нажатием кнопки и отправкой
формы. Пауза между действиями 3–240 секунд — заведомо меньше `session_gap` в 30
минут, иначе Sessionizer справедливо разрезал бы сессию.
`_pushes` (`:108`) — push-уведомления **вне** сессий: это самостоятельное
событие, а не действие пользователя.

**`profile_snapshots.py`** — `_for_client` (`:38`) выдаёт снимок на каждый месяц
начиная с открытия счёта. Зарплата индексируется, продукты появляются
постепенно (`_product_acquisition`, `:111`) — благодаря этому
`lifetime_product_count` на T имеет смысл.

**`fx_rates.py`** — `generate` (`:34`). Курс — случайное блуждание от базового
(`USD` 470, `EUR` 505). Блуждание считается **каждый день**, а публикуется
только по рабочим (`:52-58`): иначе выходные «замораживали» бы курс.

### Ключевые решения и почему именно так

**1. Форматы времени различаются радикально.**

| источник | как записано | что это проверяет |
|---|---|---|
| `core_payments` | `"11.01.2024 21:44"` | наивное локальное, зона из региона филиала |
| `card_processing` | `1705069132000` | epoch-мс, UTC |
| `app_logs` | `"2024-01-08T18:32:54"` | наивное локальное, зона из профиля клиента |
| `profile_snapshots` | `"2024-01-01"` | дата без времени → полночь **в зоне источника** |
| `fx_rates` | `"2024-01-01"` | дата публикации курса |

*Иначе:* при одинаковом формате TimestampNormalizer (2.3) свёлся бы к одной
ветке, и три четверти §12 остались бы непроверенными.

**2. Краевые случаи на границе T живут в `card_processing`, а не в
`core_payments`** (`card_processing.py:14-15`).

Причина техническая и красивая: `core_payments` пишет время с точностью до
минуты, и «ровно T = 23:59:59» там **невыразимо**.

**3. Категории `TAXIDERMY` и `CRYPTO_EXCHANGE` исключены из случайного
выбора.**

Если бы редкая категория выпадала случайно, её частота зависела бы от seed, и
проверка «это станет `RARE`» иногда была бы неверной.

**4. У блокировки карты ключей суммы нет вовсе, а не `null`.**

Это разница между «поле неприменимо» (ключа нет) и «значение отсутствует»
(`MISSING`) — два разных исхода §15.1, и без такого источника их нечем
различить.

**5. Курс блуждает, а не постоянен.**

Суммы 2023 года пересчитываются по одному курсу, 2026 — по другому. На
постоянном курсе ошибка «взяли сегодняшний курс вместо исторического» не
проявилась бы вовсе.

### Пример на реальных данных

Одна и та же сущность — покупка — в двух системах, из
`data/golden_input/*/2024-01-01.jsonl`:

```json
// core_payments: человеческий ввод
{"amount": "9 300,70", "currency": "ТЕНГЕ", "operation_time": "13.01.2024 06:38",
 "client_ref": "000000", "op_code": "PMT", "branch_region": "ASTANA", ...}

// card_processing: машинный формат
{"amount_minor": 2792228, "currency_code": "398", "txn_time_ms": 1705069132000,
 "cardholder_id": "CH000000", "op": "PUR", "mcc": "5732",
 "merchant_category": "ELECTRONICS", "merchant_id": "M-2889",
 "terminal_country": "KZ", "schema_version": "1.2", ...}
```

Курс за тот же день (`data/golden_input/fx_rates/2024-01-01.jsonl`):

```json
{"currency": "EUR", "rate_date": "2024-01-01", "rate_to_kzt": "475.1712", "source": "NBK"}
{"currency": "USD", "rate_date": "2024-01-01", "rate_to_kzt": "475.5434", "source": "NBK"}
```

Снимок профиля того же клиента:

```json
{"account_open_date": "2010-01-01", "age": 58, "cif": "CIF000000",
 "employment": "STUDENT", "products": ["CARD", "INSURANCE"], "region": "ASTANA",
 "salary": "473455", "snapshot_date": "2024-01-01"}
```

### Что сломается, если этого не будет

Один источник вместо пяти — и `source_priority` не с чем сравнивать (§13),
дублей между системами не бывает (§9.2), а Source Contract вырождается в
проверку одной схемы. Без `fx_rates` не проверить §18 целиком, без
`profile_snapshots` — ни §6, ни §24, без `app_logs` — ни §20.

## 0.3 Инъекция краевых случаев

### Что за задача

Тридцать два случая, каждый из которых проверяет отдельное правило регламента:
пропуски, невалидные числа, дубли, границу T, редкие значения, историческую
зону. Если полагаться на случайность, на маленьком golden-наборе половина из
них просто не выпадет.

Поэтому каждый случай **закреплён за конкретным клиентом** и вставляется
адресно, а куда он попал — записывается в манифест.

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `src/generator/edge_cases.py` | появился | перечень случаев, роли клиентов, календарь, журнал |
| `src/generator/sources/*.py` | изменены | каждый источник вставляет свою часть случаев |

### Что внутри файла

**`Case` (`:30`)** — перечисление всех 32 случаев с комментарием у каждого:
`MISSING_NULL`, `NUMERIC_UNPARSABLE`, `CLIP_HIGH`, `DUP_CONFLICTING`,
`BOUNDARY_AT_T`, `FX_STALE_GAP`, `RARE_VALUE`, `HISTORIC_TIMEZONE` и так далее.

**`ROLE_CASES` (`:95`)** — кортеж из 12 наборов: роль клиента по индексу.
Клиент 0 — «длинная история», клиент 5 — «все виды грязных значений», клиент 7 —
«дубли», клиент 9 — «FX», клиент 10 — «граница T», клиент 11 — «редкие и новые
значения». Один клиент несёт несколько родственных случаев, чтобы golden-набор
оставался маленьким.

**`CasePlan` (`:135`) и `build_plan` (`:162`)** — календарь: когда именно
происходит каждый случай. Всё выводится из конфига, поэтому один конфиг → одни
и те же даты. Интересные места:

- `boundary_at_t = T`, `boundary_after_t = T + 1 секунда` (`:177-178`);
- `tie_break_moment` с **нулевыми секундами** (`:181`) — иначе «одинаковый
  timestamp» у двух источников не совпал бы, потому что `core_payments` пишет
  время с точностью до минуты;
- `fx_fallback_date` — ближайшее **воскресенье** (`:168`): курса в этот день
  нет, ближайший прошлый пятничный, давность 2 дня меньше лимита в 3, значит
  fallback обязан сработать;
- `fx_gap_start` + 8 дней разрыва (`:172-174`): последний доступный курс
  окажется старше трёх суток, и §18.2 требует `MISSING`.

**`_apply_role` (`:218`)** — некоторым ролям пометки мало. Клиенту с
историческими событиями назначается регион `ALMATY` и зона `Asia/Almaty`
(которая до 2024-03-01 была UTC+6), клиенту с длинной историей — счёт,
открытый не позже 2010 года.

**`CaseLog` (`:260`)** — журнал: `record()` (`:266`) отмечает, куда попал
случай, `missing_cases()` (`:285`) возвращает те, которых в датасете не
оказалось, `as_manifest()` (`:294`) собирает файл.

### Ключевые решения и почему именно так

**1. Не вставился случай — сборка падает** (`build_dataset.py:80-84`).

```python
missing = case_log.missing_cases()
if missing:
    raise ValueError("в датасете не оказалось краевых случаев: " + ...)
```

Это главное решение всего этапа. *Иначе:* можно годами думать «я проверил
обработку дублей», а дублей в данных нет — проверка была пустышкой, и узнать
об этом неоткуда.

**2. Роль привязана к индексу клиента, а не выдана случайно.**

Клиент 7 — всегда дубли, и в основном наборе, и в golden. Значит проверка может
бить точечно: «возьми `C000007`, у него обязан быть конфликт».

**3. Случаи, требующие пары записей, вставляются вместе.**

Бизнес-дубль — две записи с **разными** `source_record_id` и одинаковым
содержимым (`core_payments.py:243-247`). Конфликт — две записи с **одинаковым**
`source_record_id` и разной суммой и версией (`:249-255`). Tie-break между
источниками — запись в `core_payments` и парная к ней в `card_processing` с тем
же моментом.

**4. Манифест содержит `record_id`, а не только имя случая.**

По манифесту проверка находит конкретную строку среди 76 тысяч, а не ищет
иголку в стоге.

### Пример на реальных данных

Настоящие инъекции из `data/golden_input/`:

```json
// клиент 5, невалидное число: NumericValidator обязан дать MISSING, не ноль
{"amount": "abc", "source_record_id": "CPX-000005-bad-amount", "currency": "KZT", ...}

// клиент 5, пропуск: значение null
{"amount": null, "source_record_id": "CPX-000005-null-amount", ...}

// клиент 6, сумма выше всего TRAIN-диапазона → верхний бакет (clipping)
{"amount": "5 000 000 000,00", "source_record_id": "CPX-000006-clip-high", ...}

// клиент 7, конфликт: тот же source_record_id, разная сумма и версия
{"amount": "10 000,00", "payload_version": 1, "source_record_id": "CPX-000007-dup-conflict", ...}
{"amount": "99 999,00", "payload_version": 2, "source_record_id": "CPX-000007-dup-conflict", ...}

// клиент 9, сумма в долларах и «доллар» словом — курс на воскресенье не публикуется
{"amount": "980,50", "currency": "доллар", "source_record_id": "CPX-000009-fx-weekend", ...}

// клиент 10, ровно T и T + 1 секунда
{"txn_time_ms": 1769903999000, "rec_id": "CRDX-CH000010-at-T", ...}
{"txn_time_ms": 1769904000000, "rec_id": "CRDX-CH000010-after-T", ...}
```

Соответствующая запись манифеста
(`data/golden_input/_meta/edge_case_manifest.json`):

```json
"boundary_after_t": [{"client_id": "C000010", "source": "card_processing",
  "record_id": "CRDX-CH000010-after-T",
  "note": "timestamp == T + 1 секунда, событие обязано быть отброшено"}]
```

Всего в манифесте 32 ключа — по одному на случай.

### Что сломается, если этого не будет

Тесты станут проверять только happy path. Дедупликация, отсечка, FX-fallback,
clipping и обработка `MISSING` окажутся написанными, но никогда не
исполнявшимися — а неисполнявшийся код в среднем не работает.

## 0.4 Два набора данных

### Что за задача

Нужен большой набор — чтобы границы бакетов считались по осмысленному
распределению, — и маленький замороженный, который поедет в git и станет
эталоном §29.2. Большой в git не положишь (76 тысяч записей), маленький для
BUILD не годится (границы будут случайными).

Решение: **тот же код, тот же seed, тот же период, другой объём**.

### Файлы

| путь | появился/изменён | зачем |
|---|---|---|
| `src/generator/build_dataset.py` | изменён | `golden_config`, `golden_clients`, аргумент `--only` |
| `data/golden_input/` | появился | замороженный набор, единственные данные в git |
| `.gitignore` | изменён | `data/*` игнорируется, `golden_input` и `golden_expected` — исключения |

### Что внутри

**`golden_config` (`:59`)** — копия основного конфига с четырьмя правками:
число клиентов, `volume_scale = 0.12`, каталог `data/golden_input`, роль
`golden_input`. Seed и период истории **те же**.

**`golden_clients` (`:48`)** — `MIN_CLIENTS + debug_clean_clients` = 12 ролей
плюс 2 «чистых» клиента = 14.

**`.gitignore`** — данные генерируются из seed, и в git им делать нечего.
Исключение ровно одно, и оно объяснено прямо в файле: §29.2 требует
**замороженный** conformance set, который обязан приезжать вместе с кодом.

### Ключевые решения и почему именно так

**1. Golden — не отдельный код, а тот же с меньшим объёмом.**

Отдельный генератор эталона был бы второй реализацией, и расхождение между ними
выглядело бы как ошибка обработки.

**2. Два «чистых» клиента добавлены к двенадцати ролевым (пункт 3.0).**

Изначально golden состоял из 12 клиентов — все с краевыми случаями, ни одного
обычного. Эталон без happy path неполон: поломка нормального пути прошла бы
мимо. Плюс debug-режим не находил в нём клиента, на котором можно показать
обычную транзакцию.

*Что изменилось при этом:* `golden_vectors_version` поднята с `1.0.0` до
`1.1.0` — §29.2 требует версионировать набор, иначе два разных набора
неразличимы по манифесту.

**3. Число чистых клиентов публикуется полем манифеста, а не константой в
коде.**

`debug_clean_clients` (`config.py:54`) уезжает в `_meta/manifest.json`, и
оттуда его читает debug-режим препроцессинга. Константа в коде не выразила бы
того, что у main и golden это число может отличаться.

**4. `volume_scale = 0.12`, а не «сгенерировать 12 клиентов из 200».**

Краевые случаи вставляются **поверх** объёма и от него не зависят
(`config.py:50-51`). Поэтому golden получается маленьким по фону, но полным по
случаям: все 32 на месте.

### Пример на реальных данных

Два манифеста рядом:

| | `main` | `golden_input` |
|---|---|---|
| `seed` | 20260101 | 20260101 |
| `n_clients` | 200 | 14 |
| `volume_scale` | 1.0 | 0.12 |
| `dataset_role` | `train` | `golden_input` |
| файлов | 152 | 148 |
| записей | 76 797 | 2 554 |
| `debug_clean_clients` | 2 | 2 |
| период истории | 2023-09-01 … 2026-02-28 | тот же |

Файл манифеста несёт контрольную сумму каждой партиции:

```json
{"path": "app_logs/2023-09-01.jsonl", "records": 24,
 "sha256": "fd22bafc787ddb1765479c5a6f303d7871876fc2f9ba47bd923ae1585148b594"}
```

### Что сломается, если этого не будет

Без golden-набора нет эталона §29.2, а значит нет способа доказать, что другая
машина, другая версия Python или другая реализация дают тот же результат.
Сравнение single/multi-worker этого **не** заменяет: оно доказывает
идентичность одной реализации при разном числе процессов, и только.

Без основного набора границы бакетов считались бы по 2554 записям 14 клиентов —
и распределение сумм оказалось бы случайным.
