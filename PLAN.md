# PLAN — реализация препроцессинга

План реализации `preprocessing_rules_official.md` (38 разделов). Токенайзер — отдельный этап после приёмки препроцессинга.

Порядок этапов продиктован регламентом: сначала генератор синтетики (без данных нечем отлаживать компоненты), затем фундамент детерминизма (от него зависят `event_id`, dedup-fingerprint и sampling), затем компоненты строго по цепочке §37.2, в конце — три критичные проверки.

Ссылки вида §N — на разделы `preprocessing_rules_official.md`, если не указано иное.

## Зафиксированные решения

| Решение | Значение |
|---|---|
| Python | 3.11.0rc2 (текущий `.venv`, оставляем как есть) |
| Синтетика | 5 источников, ~200 клиентов |
| Проверка детерминизма | `multiprocessing`, 1 воркер vs 4 |
| Конфиги | YAML на входе + валидация pydantic; в хэш — только канонический JSON по §29.1 |
| Формат float в канонической сериализации | shortest round-trip repr — **и на сегодня он ни на что не влияет**, см. ниже |
| Cutoff T | единый глобальный из конфига |
| Quarantine (§34) + метрики (§33) | включены, минимально: JSONL + счётчики в JSON-отчёт |
| `delta_prev` между событиями (§25.2) | **бакеты**, а не continuous. `time_delta_edges` считаются на BUILD (3.2) и публикуются артефактом |

**Float в хэшируемом состоянии: его там нет.** Замер после 3.3 на собранном
состоянии — 22 раздела, **ноль** значений с плавающей точкой. Причина не в
удаче: границы бакетов (§19) и границы дельты (§25.2) хранятся строками
десятичных дробей, суммы разбираются через `Decimal` (§17), а всё остальное
в состоянии — целые числа и строки. Единственный float во всём BUILD живёт в
`train_baselines.json` (21 значение, доли метрик §33), и baselines в хэш не
входят.

Следствие: выбранный формат float (§29.1 п.4) на `preprocessing_state_sha256`
сейчас не влияет, и межъязыковой риск «другая реализация напечатала double
иначе» для хэша снят **не соглашением, а отсутствием предмета спора**.
Свойство не вечное — достаточно одного дробного порога в YAML. Поэтому оно
не просто записано, а сторожится: `test_configs_contribute_no_floats_to_the_state`
падает, как только float появится в конфигах, где он появится раньше всего
(их пишут руками). Формат остаётся объявленным и версионируемым: он нужен
`train_baselines.json`, который тоже пишется канонически, и понадобится хэшу,
если float в состояние вернётся.

**Обоснование решения по `delta_prev`.** §25.2 условный: «если delta кодируется
бакетами» — то есть выбор регламент оставляет нам. Continuous-вариант требует
обучаемого компонента (нормализация, эмбеддинг числа), а это уже решение о
модели, регламента на которую не существует; принимать его в препроцессинге
значит принимать за чужой слой. Бакеты оставляют решение внутри нашего слоя:
границы — версионируемый артефакт, вход в `preprocessing_state_sha256` (§30),
расчёт детерминированный и проверяемый golden-векторами, механизм тот же, что
у §19, и повторно проверять его нечем. Само применение границ остаётся за
токенайзером — он пересчитывает `delta_prev` после truncation (§25.1).

### Пробелы регламента, требующие решения при реализации

- §29.1 п.10 — сказано «length-prefix», но не сказано какой: ширина префикса и порядок байт не заданы. Зафиксировано в `hash_policy`: 8 байт, big-endian, считает байты UTF-8.
- §29.1 п.11 vs §5/§32.2 — расхождение внутри регламента: §29.1 нормативно определяет `event_id` как первые 128 бит SHA-256 (32 hex-символа), а примеры в §5 и §32.2 показывают `"evt_..."` и `"evt_1"`. Реализовано по §29.1 (без префикса), примеры трактуются как иллюстративные. **Требуется правка регламента:** привести примеры `event_id` в §5 и §32.2 к настоящему 32-hex виду — документ должен быть согласован сам с собой. Правит владелец регламента; код уже соответствует §29.1.
- §29.1 п.12 — формула комбинирования reservoir seed с `global_seed` не задана (см. A2). Первая версия формулы (простой XOR) оказалась неверной по существу: `global_seed = 20260101` занимает 25 младших бит, а выборка упорядочивается по значению целиком, то есть по старшим. Замерено на 20 000 ключей: при простом XOR два соседних seed давали **пересечение выборок 500 из 500** — то есть seed не влиял на выборку вовсе. После умножения seed на нечётную константу золотого сечения пересечение стало **0 из 500**. `hash_policy_version` поднята до 1.1.0.
- §19.2 — число бакетов объявлено гиперпараметром без дефолта (см. A3).
- §33 — пороги метрик «уточняются по baseline банка»; на синтетике считаем значения, пороги не применяем.
- §11 — не проговорено, что одноимённое поле в разных типах событий обязано иметь одинаковые тип, `vocabulary_policy` и domain. Ограничение выводится из токенайзера: токен значения имеет вид `value:<field>:<value>` (§14.4.1.1 токенайзера) и про тип события не знает, поэтому два разных domain у одного имени дали бы один токен для разных сущностей. **Требуется правка регламента:** дополнить §11 требованием согласованности `type`/`vocabulary_policy`/`domain` для одноимённых полей между типами событий, с оговоркой, что `priority` и `required` различаться могут. Проверка уже реализована в `FeatureSchema`.
- §12 п.9 — «timestamp из будущего относительно clock-skew policy маркируется», но самой policy регламент не задаёт (см. A8).
- §7 п.6 vs §37.2 — §7 требует, чтобы merge/split клиентов был исторически корректен относительно `T`, а цепочка §37.2 ставит разрешение `client_id` **до** нормализации времени. Противоречия нет: `T` — глобальная константа конфига, а не время события, поэтому применимость связи проверяется без разобранного timestamp. Стоит проговорить это в §7 явно, иначе прочтение «относительно времени события» ломает порядок цепочки.
- §19.6 vs §29 п.5 — противоречие внутри регламента. §19.6 предписывает **алгоритм**: «deterministic reservoir sampling». §29 п.5 требует **свойство**: «reservoir sample не зависит от числа workers». Классический reservoir (алгоритм R) этому свойству удовлетворить не может: он идёт по потоку и на каждом шаге бросает жребий из одного общего генератора, поэтому результат зависит и от порядка записей, и от того, как поток порезан между процессами; собрать выборки четырёх воркеров в одну, получив ответ однопоточного прогона, там невозможно в принципе. Реализовано priority sampling: каждой записи считается ключ из неё самой и `global_seed` (§29.1 п.12), в выборку идут `k` наименьших — результат равен `sorted(все ключи)[:k]` и от нарезки потока не зависит по построению. **Требуется правка регламента:** §19.6 должен требовать свойство (независимость от нарезки потока и порядка завершения задач), а не называть конкретный алгоритм. Иначе следующий реализатор пойдёт делать reservoir и упрётся в ту же стену.
- §37.2 — порядок цепочки ставит дедупликацию (§9) **до** FX-нормализации (§18), то есть до момента, когда суммы разных источников становятся сравнимыми. Пример §9.2 задаёт бизнес-отпечаток по `amount + currency`, но на шаге дедупликации это ещё сырые значения источника: строка `"33 000,00"` в ядре платежей и целое `3300000` тиын в карточном процессинге. Межисточниковый бизнес-дубль (одна покупка, увиденная двумя системами) в таком порядке неразличим в принципе — это дырка в порядке цепочки, а не в реализации. **Требуется правка регламента:** либо §9.2 оговаривает, что отпечаток считается внутри источника, либо §37.2 разносит дедупликацию на два прохода — внутриисточниковый до FX и межисточниковый после.
- §24 vs §37.2 — противоречие в порядке цепочки. §24 требует бакетизировать life-long признаки (`raw lifetime value → validation → bucketization → profile field`), а §37.2 даёт **один** шаг бакетизации и ставит его **до** «profile on T → life-long features». §27 шаг 12 тоже единственный. То есть границ для этих полей не существует ни в один момент: на BUILD значений ещё нет, к ENCODE границ уже нет. Круг мнимый — все шесть признаков §24 считаются из дат, счётчиков и множества событий ≤ T и не зависят ни от одного бакетизированного значения, — но линейная запись цепочки его создаёт. Реализовано переносом: профиль и life-long считаются **до** единственного шага бакетизации, и появляется проверяемый инвариант «у §19 все bucket-поля уже имеют значения». **Требуется правка регламента:** либо §37.2 переносит «profile on T» и «life-long features» до бакетизации, либо §37.2 и §27 явно вводят второй проход бакетизации после расчёта профиля.
- §2.2 vs §5 п.7 и §13 — противоречие по букве. §2.2 требует, чтобы на входе токенайзера не оставалось «сырых технических ID», а §5 п.7 и §13 требуют `ordering_key`, построенный из `source_record_id`, и §32.2 показывает его в `prepared_events`. То есть сырой идентификатор источника доезжает до токенайзера — в метаданных записи, не в `fields`. Разрешение очевидно по смыслу (значением поля он не становится, токеном не будет, `max_tokens_per_event` не тратит), но в тексте его нет, и следующий реализатор прочтёт §2.2 буквально. **Требуется правка регламента:** §2.2 должен оговорить, что запрет относится к значениям полей модели, а не к служебным атрибутам записи, и назвать `ordering_key` явным исключением. **Следствие, которое мы закрыли кодом:** раз `source_record_id` попадает в выход, его состав перестаёт быть внутренним делом источника — колонка `primary_key`, классифицированная как `direct_identifier`, теперь отвергается при загрузке контракта. §7 п.4 запрещал PII в поле клиента; со стороны ключа записи была та же дыра, и на синтетике она безобидна только потому, что генератор нумерует записи сам.
- §34 vs §33 — две из восьми причин карантина не имеют своей метрики в §33: «невозможно определить client_id» (identity resolution в §33 не описан) и «content hash не совпадает». Считаются только общим счётчиком `quarantined`, иначе нарушалось бы правило §34 «не удалять молча без метрики».

Противоречий между регламентами препроцессинга и токенайзера не обнаружено — перекрёстные ссылки согласованы.

### Отложено

Механизмы, которые регламент описывает, а реализация пока не даёт. Общий
принцип: непроверенный механизм хуже отсутствующего — он выглядит рабочим и
молча не срабатывает. Разблокируются эти пункты по-разному, поэтому и списка
два.

  - **Важно:** ≥2 событийных источника обязательны — иначе нечем проверить tie-break по `source_priority` (§13) и business-дубли между источниками (§9.2).

- [x] **0.3 Инъекция краевых случаев §29.2** — каждый случай генерируется адресно и попадает в `edge_case_manifest.json` (`client_id`/`source_record_id` → метка кейса), чтобы проверки били точечно:
  - `MISSING`: `null`, пустая строка, placeholder (`"N/A"`, `"-"`), отсутствующий ключ;
  - **FX**: суммы в USD/EUR; дата без курса → fallback на прошлый (§18.2); разрыв курсов > `fx_max_staleness` → `amount_base_bucket = MISSING`;
  - **clipping**: значения ниже `min_train_edge` и выше `max_train_edge` (§19.4);
  - **tie-break**: два события с одинаковым `timestamp_utc` из разных источников (решает `source_priority`) и из одного источника (решает `source_record_id`);
  - **дубли**: exact, business (разные `source_record_id`, один факт), conflicting (тот же ключ, разный payload → quarantine);
  - **граница T**: событие ровно в `T` (входит) и `T + 1s` (не входит);
  - **редкие значения**: open-set `merchant_category` с частотой < `min_count` (будущий `RARE`) и значение, которого нет в TRAIN (будущий `[UNK]`);
  - **длинная история**: клиент с историей длиннее model window (`WINDOW_START`), клиент с единственным событием (`lifetime_first = true`), клиент без profile snapshot (§6 п.3), клиент без событий;
  - **невалидные числа**: `"abc"`, `NaN`, `Inf`, отрицательный age (§17.2, §17.3);
  - **неизвестный source event code** → quarantine (§10 п.3);
  - **наивный timestamp** без tz и timestamp из будущего (§12 пп.6, 9);
  - **сессия, пересекающая T** (§14.1);
  - **multivalue** длиннее `max_values_per_field` (§21).

- [x] **0.4 Два набора данных**: основной (~200 клиентов, для BUILD и quantile-edges) и `golden_input` — маленький фиксированный (12 клиентов: по одному на роль краевых случаев), покрывающий **все** кейсы §29.2; замораживается и версионируется (`golden_vectors_version`).

## Этап 1 — фундамент детерминизма

> Идёт до компонентов сознательно: `event_id` (§8), business fingerprint (§9.2) и reservoir seed (§19.6) обязаны использовать единый `hash_policy` из §29.1. Сделать это позже = перевыпускать все хэши и golden-наборы.

- [x] **1.1 `core/canonical.py`** — §29.1 пп.1–8
  - **Вход:** любой Python-объект артефакта. **Выход:** `bytes` канонического JSON.
  - UTF-8 без BOM; ключи лексикографически по UTF-8 byte order; компактные разделители; float = shortest round-trip repr; `-0.0 → 0.0`; int/bool без плавающей точки.
  - **Краевые:** `NaN/±Inf` в хэшируемом артефакте → блокирующая ошибка BUILD (§29.1 п.6); вложенные словари и списки; кириллица в значениях.

- [x] **1.2 `core/hashing.py`** — §29.1 пп.9–13
  - SHA-256, встроенный `hash()` запрещён; пре-образ = поля в фиксированном порядке, каждое как UTF-8 с **length-prefix** (символ-разделитель запрещён); timestamp = целое epoch-микросекунд.
  - `event_id` = первые 128 бит (32 hex); reservoir seed = первые 8 байт как uint64 big-endian ⊕ `global_seed` (A2).
  - **Краевые:** поля, склеивание которых без length-prefix дало бы коллизию (`("ab","c")` vs `("a","bc")`) — должны дать разные хэши.

- [x] **1.3 `core/settings.py` + `core/versions.py`** — §30
  - pydantic-settings: пути, `global_seed`, `cutoff_time`, `fx_max_staleness`, `session_gap`, `max_values_per_field`, число воркеров.
  - Флаг `debug: bool = false` и `debug_dir` — включают трассировку компонентов (см. 1.6). На поведение пайплайна не влияют, только на побочную запись дампов.
  - Реестр всех 19 версий из §30 + `preprocessing_state_sha256`.

- [x] **1.4 `core/quarantine.py` + `core/monitor.py`** — §34, §33
  - **Выход:** `data/quarantine/*.jsonl` (raw reference, reason code, source, processing time, pipeline version, recoverability) и `data/prepared/run_report.json` со счётчиками §33.
  - Правило: молча удалять записи запрещено — каждая отброшенная запись имеет reason code и метрику.

- [x] **1.5 `schema/` — pydantic-модели** — §5, §6, §11
  - Canonical event (§5, все 13 правил, включая `lifetime_first`), canonical profile (§6), Feature Schema (§11 + §11.2 секция `PROFILE`).
  - Инвариант, проверяемый моделью: `event_type` есть top-level и **отсутствует** в `fields`.
  - Конвенция календаря: `hour_of_day_local` 0..23, `day_of_week_local` 0..6, **Пн = 0** (§5 п.12).

- [x] **1.6 `core/debug_dump.py` — debug-режим трассировки** — не раздел регламента, а инструмент отладки
  - **Зачем:** цепочка §37.2 длинная, и по конечному `prepared_events` не видно, на каком шаге значение испортилось. Дамп «вход → выход» каждого компонента даёт покомпонентный разрез одного клиента.
  - **Вход:** имя компонента, стадия (`in`/`out`), записи, номер раздела регламента.
  - **Выход:** `data/debug/<NN>_<component>/<stage>.jsonl`, где `NN` — порядковый номер компонента в цепочке этапа 2 (`01_source_reader`, `02_identity_resolver`, … `17_time_feature_builder`) — чтобы каталоги сортировались в порядке обработки.
  - **Привязка каждой строки:** `client_id` + `event_id`. До `EventMapper` (2.6) `event_id` ещё не существует — там ключом служит `source_record_id`; поле `spec_section` (`"§12"`, `"§18"`) помечает, какой раздел регламента отработал.
  - **Уточнено на шаге 2.1:** до `IdentityResolver` (2.2) канонического `client_id` тоже нет — есть только ссылка источника (`client_ref`), поэтому строка дампа несёт оба поля, а фильтр смотрит на любое из них. `default_client_filter` добавляет к 14 клиентам их источниковые ссылки из `identity_mapping.json`. Строка вовсе без клиента (справочник курсов) фильтром не отбрасывается: фильтр по клиентам не может судить о записи без клиента.
  - **Правила:**
    - пишется только при `settings.debug = true`, иначе вызов — no-op;
    - **не входит** в `preprocessing_state_sha256` (§30) и в обязательные артефакты (§31): это диагностика, а не состояние пайплайна;
    - не меняет поведение — ни порядок записей, ни их содержимое; при `debug=false` результат обязан быть байт-в-байт тем же;
    - `data/debug/` чистится перед прогоном и попадает в `.gitignore`.
  - **Ограничение объёма:** на 200 клиентах полный дамп 17 компонентов — сотни мегабайт, поэтому фильтр по списку `client_id`. По умолчанию — клиенты из `edge_case_manifest.json` **плюс 2 «чистых» клиента без единого краевого случая: на демо-UI главный экран показывает путь нормальной транзакции, и дамп из одного брака показывать нечего.**
  - **Следствие для golden-набора:** в `golden_input` сейчас ровно 12 клиентов — все ролевые, чистых нет. Чтобы фильтр по умолчанию работал и там, `GOLDEN_CLIENTS` нужно поднять до 14 (одна строка в `build_dataset.py` + перегенерация). Заодно это делает golden-эталон полнее: сейчас в нём нет ни одного обычного клиента.

## Этап 2 — компоненты в порядке цепочки §37.2

- [x] **2.1 `SourceReader`** — §4, §29 п.1
  - **Вход:** YAML Source Contracts + `data/raw/**/*.jsonl`. **Выход:** валидированные raw-записи в детерминированном порядке файлов/партиций.
  - Контракт: владелец, схема, типы, PK, поле клиента, event/processing time, **`source_priority`**, timezone, correction/reversal, late-arrival policy, PII classification.
  - **Краевые:** изменение схемы источника без новой версии контракта → остановка pipeline или quarantine + alert (молчаливое принятие новых полей запрещено); неизвестная колонка; порядок файлов не зависит от файловой системы.
  - **Реализовано:** `config/source_contracts.yaml` (один файл на весь набор — §30 знает одну `source_contract_version`), `schema/source_contract.py` (модель + загрузка), `source_reader.py` (обход партиций + проверка записей).
  - **Границы компонента:** проверяется только соответствие схеме. Время не разбирается (§12), суммы не приводятся (§17), `client_id` не разрешается (§7) — `"abc"` в сумме и `null` вместо значения обязаны дойти до своих компонентов живыми.
  - **Решения этого шага:**
    - `required` в контракте («источник гарантирует ключ») ≠ `required` в Feature Schema («признак нужен модели»). Ключ, которого источник не гарантирует, обязан быть `required: false`, иначе краевой случай «нет ключа → MISSING» уходит в карантин вместо §15;
    - `source_priority` уникален между источниками. §13 этого не требует (третий ключ tie-break всё равно решает), но при равных рангах порядок начинает зависеть от формата `source_record_id`, а не от решения владельца данных;
    - каталог в `data/raw/` без контракта — блокирующая ошибка; исключения перечислены в `ignored_paths`. Та же логика, что и с полями: молча читать данные, о которых не договаривались, нельзя;
    - составной `source_record_id` (`profile_snapshots`, `fx_rates`) склеивается через `|` с проверкой, что разделитель в значениях ключа не встречается.

- [x] **2.2 `IdentityResolver`** — §7
  - **Вход:** `client_ref` / `cardholder_id` / `cif` / `device_id` + versioned mapping. **Выход:** канонический `client_id`.
  - **Краевые:** неоднозначный mapping → **не** разрешать случайно, в quarantine; конфликтующие связи; PII не может быть публичным идентификатором; merge/split клиентов исторически корректен относительно T.
  - **Реализовано:** `config/identity_mapping.yaml` (политика) + таблица `data/raw/_meta/identity_mapping.json`, `identity_resolver.py`.
  - **Решения этого шага:**
    - таблица разбирается с `object_pairs_hook`, а не обычным `json.loads`: стандартный разбор на повторяющемся ключе молча оставляет последнее значение — это и есть «конфликтующая связь разрешилась случайно» (§7 п.3);
    - секции таблицы называются `<источник>.<client_field>` и выводятся из Source Contract — имя поля клиента не дублируется в двух конфигах;
    - §7 п.4 проверяется дважды: `client_id` обязан подходить под непрозрачный шаблон `^C[0-9]{6}$`, а поле клиента в контракте не может быть классифицировано как `direct_identifier`;
    - две ссылки одного источника на одного клиента — блокирующая ошибка, а не молчаливая склейка: это merge, который §7 п.6 требует описать политикой относительно T;
    - у справочных источников (`kind: reference`) `client_id` пуст. §34 говорит «невозможно определить client_id»; у курса валют клиент не предусмотрен, и это не карантин.
  - **Отложено:** merge/split клиентов (§7 п.6) — см. «Отложено до боевых данных».

- [x] **2.3 `TimestampNormalizer`** — §12, §12.1, §12.2
  - **Вход:** сырое время в трёх разных форматах. **Выход:** `timestamp_utc` (ISO-8601 UTC) + `calendar_timezone` (IANA).
  - **Краевые:** наивный timestamp без tz → только по source policy; неизвестная timezone → quarantine или явно утверждённый source default; processing time **не** подменяет отсутствующий event time; время из будущего маркируется; события до 2024-03-01 — историческими правилами IANA, а **не** ретроактивным UTC+05 (§12.1); переход на UTC+05 1 марта 2024.
  - **Реализовано:** `config/timestamp_policy.yaml`, `timestamp_normalizer.py`.
  - **Решения этого шага:**
    - `fold=0` задан явно. Переход Казахстана на UTC+05 сдвинул часы назад, поэтому один локальный час 1 марта 2024 встречается дважды; без зафиксированного правила выбор между двумя instant зависел бы от реализации, и golden-vectors не сошлись бы;
    - `epoch_millis` считается через `timedelta`, а не делением на 1000: float потерял бы точность на миллисекундах;
    - дата без времени (снимок профиля, курс) — полночь **в зоне источника**, а не в UTC. Разница в пять часов решает судьбу снимков первого числа месяца относительно T;
    - зона клиента для `card_processing` и `app_logs` берётся из индекса, построенного по профилям на T. Страна терминала для этого не годится: покупка в Турции остаётся поведением казахстанского клиента (§12.1);
    - `late_arriving_rate` (§33.12) считается только там, где источник сообщает processing time. §12.2 разрешает использовать его именно для этого — и только для этого.

- [x] **2.4 `CutoffFilter`** — §14, §14.1, §14.2
  - **Вход:** нормализованные записи + глобальный `T`. **Выход:** записи `timestamp_utc <= T`.
  - **Краевые:** событие ровно в `T` (включается), `T + 1s` (отбрасывается, счётчик `cutoff_violation_rate`); сессия, пересекающая T → действия после T исключаются, summary пересчитывается только по доступной части; profile snapshot `<= T`.
  - **Реализовано:** `cutoff.py`.
  - **Решения этого шага:**
    - отброшенная запись — **не** брак: она не идёт в карантин и не поднимает метрику ошибки. Быть после T нормально, это просто вне окна наблюдения. Считается отдельным `CutoffReport`, чтобы «пропало 2350 записей» не выглядело загадкой;
    - `cutoff_violation_rate` (§33.1) — сторож, а не счётчик отброшенного: он считает записи после T, оказавшиеся **уже за** фильтром. По построению таких нет, и §33.1 это и говорит: «любое значение > 0 — critical». Ту же метрику поднимут Sessionizer (§14.1) и ProfileBuilder (§6 п.1);
    - фильтр применяется ко всем источникам, включая курсы: §18 запрещает брать курс позже события, а все события уже не позже T.

- [x] **2.5 `Deduplicator`** — §9
  - **Вход:** записи `<= T`. **Выход:** дедуплицированные записи + отчёт конфликтов.
  - **Краевые:** exact duplicate (source + record_id + payload version) → одна запись; business duplicate по versioned fingerprint (client + event_time + amount + currency + direction + merchant ref); conflicting duplicate → correction policy / version / quarantine, но **не** `drop_duplicates(keep="first")`; reversal — отдельное событие, а не дубль (§9.4).
  - **Реализовано:** `config/dedup_policy.yaml`, `deduplicator.py`.
  - **Решения этого шага:**
    - неразрешимый конфликт отправляет в карантин **всю группу**, не оставляя представителя: оставить произвольного — это `keep-first` под другим именем, а §9.3 запрещает именно его;
    - конфликт разрешается только объявленным правилом. `core_payments` объявил `update_rules: versioned_by_field` → выигрывает бо́льшая `payload_version`. Ничья по версии при разном payload не разрешается — правило не выбрало, и выбирать больше нечем;
    - в бизнес-дубле выживает запись с наименьшим `source_record_id` — объявленное правило, а не «та, что попалась первой»;
    - пре-образ отпечатка несёт маркер присутствия поля, иначе отсутствующий `direction` и `direction: ""` дали бы один отпечаток;
    - дедупликация собирает поток целиком: дубль может лежать в другой партиции. Это точка схождения воркеров, а не параллельный шаг. Порядок выдачи — каноническое место выжившей записи (§29 п.1), поэтому перемешанный вход даёт тот же выход;
    - `Quarantine.add(count_metric=False)` — конфликт есть свойство группы, и группа уже посчитана. Иначе группа из трёх записей подняла бы `dedup_conflict_rate` трижды при знаменателе «число групп». Умолчание осталось `True`: забыть метрику по-прежнему нельзя, от неё можно только отказаться явно.
  - **Отложено:** reversal (§9.4) и межисточниковый бизнес-дубль (§9.2) — см. «Отложено до боевых данных».

- [x] **2.6 `EventMapper`** — §8, §10
  - **Вход:** дедуплицированные записи + versioned event mapping. **Выход:** canonical event с top-level `event_type` и стабильным `event_id`.
  - **Краевые:** неизвестный source code → quarantine + `unknown_event_type_rate`, автосоздание нового `event_type` запрещено; `OTHER` только как утверждённая категория; повторный прогон даёт тот же `event_id` (никаких UUID/времени/номера воркера); lineage событие → raw-запись → файл/партиция → версия схемы.
  - **Реализовано:** `config/event_mapping.yaml`, `event_mapper.py`.
  - **Решения этого шага:**
    - fallback-типа нет вовсе. `default_event_type` вместе с `code_field` — ошибка конфигурации: иначе неизвестный код молча получал бы тип по умолчанию, то есть ровно то автосоздание, которое запрещает §10 п.2. Заодно это структурно исключает `OTHER` как свалку (§10 п.4);
    - `codes: {LOGIN: null}` — утверждённый технический message (§10 п.5), а не неизвестный код. Разница принципиальна: неизвестный уходит в карантин, технический — к Sessionizer;
    - снимок профиля событием не становится: §6 держит профиль отдельно, и место снимка в `prepared_profile` на T (§24), иначе клиент «совершал» бы по событию каждый месяц. Курс валют — тем более: он материал §18, а не timeline;
    - совпадение `event_id` у двух записей — блокирующая ошибка. Это либо пропущенный дубль (§9), либо коллизия пре-образа; ниже по цепочке оба выглядят как «событие потерялось», и причину там уже не найти;
    - поле кода обязано быть `required` в контракте: тип события не должен зависеть от поля, наличие которого источник не гарантирует.

- [x] **2.7 `Sessionizer`** — §20
  - **Вход:** app-логи (`screen_open`, `button_click`, …). **Выход:** события `APP_SESSION` с полями сессии.
  - Новая сессия: смена клиента / разрыв > `session_gap` (30 мин) / явная граница / рестарт приложения.
  - **Краевые:** сессия, пересекающая T (§14.1) — длительность **не** смотрит в будущее; пустая сессия; порядок screens детерминирован; `max_values_per_field` соблюдается; raw click ID не попадает в поля.
  - **Реализовано:** `config/sessionization.yaml`, `sessionizer.py`.
  - **Решения этого шага:**
    - §14.1 выполняется **структурно**, а не проверкой: отсечка (§14) стоит раньше по цепочке §37.2, и до сессионизации доживает только доступная часть. Сессия, пересекавшая T, приходит уже обрезанной и считается как обычная короткая;

    - `event_id` сессии считается здесь по той же формуле §8 и той же `hash_policy`: событие родилось на этом шаге, но правила у него общие. `source_record_id` сессии — идентификатор её первой строки: он настоящий и сохраняет lineage до конкретной записи источника;
    - порядок экранов хронологический, а не алфавитный. Сортировка по алфавиту тоже детерминирована (§20.3), но для экранов порядок значим (§21), и она была бы детерминированно неверной;

    - имена полей в схеме **конечные** (`amount_base_bucket`), а значение под именем меняет форму по дороге: сырая строка → число (§17) → тенге (§18) → `bucket_17` (§19). Переименование в середине цепочки потеряло бы связь между сырым значением и его конечным местом;

Без этой трактовки два исхода §15.1 («MISSING» и «поле не добавляется») нечем различить.

- [x] **2.10 `NumericValidator`** — §17
  - **Вход:** строковые/числовые поля. **Выход:** валидные числа или `MISSING`.
  - **Краевые:** `"15 000,50"` (разделители тысяч + запятая); `"abc"`; `NaN`; `±Inf`; пустая строка; значение вне business range; отрицательное — валидно для баланса, невалидно для age. Запрещено: замена на 0, отправка в `[UNK]`, создание нового бакета, падение на обычном production inference. Счётчики: `numeric_parse_error_rate`, `numeric_nan_rate`, `numeric_business_range_error_rate`.

  - **Реализовано:** блок `numeric` в `config/feature_schema.yaml`, `numeric_validator.py`.
  - **Решения этого шага:**
    - все четыре запрета §17.2 выполнены **устройством**: единственное, что метод умеет вернуть кроме числа, — `MISSING`. Нуля в коде нет, `[UNK]` взять неоткуда, бакетов ещё не существует, исключений компонент не бросает;
    - разбор идёт по `Decimal`, а не по `float`: деньги в двоичной дроби дали бы плавающую границу бакета, а ошибка округления вскрылась бы только на сравнении хэшей;
    - `numeric_type` описывает форму **исходного** значения, поэтому целочисленность проверяется **до** применения `scale`: сумма в тиынах целая, а те же деньги в тенге — уже нет;
    - `"1,234.56"` (обе формы разделителя сразу) — ошибка разбора, а не повод угадать, что здесь дробное;
    - `bool` не считается числом: `True` иначе стал бы суммой в один тенге;
    - business range (§17.2, → `MISSING`) и clipping (§19.4, → крайний бакет) разведены явно: первое — значение бессмысленно, второе — осмысленно, но вне TRAIN-диапазона.
  - **Пробел регламента:** §17.2 требует мониторить `numeric_nan_rate` и `numeric_business_range_error_rate`, но §33 определяет только `numeric_parse_error_rate` (§33.7). Метрики заведены по §17.2 без порогов — придумывать пороги за регламент нельзя, а не считать величину, которую он требует считать, тем более. **Требуется правка регламента:** добавить обе метрики в §33 с порогами.

  - **Вход:** сумма + валюта + `timestamp_utc` + versioned таблица курсов. **Выход:** сумма в KZT; исходная `currency` сохраняется отдельным полем.

- [x] **2.12 `DeterministicSampler`** — §19.6, §29 п.5
  - **Вход:** TRAIN-записи. **Выход:** воспроизводимый sample для fit edges.
  - **Краевые:** результат не зависит от числа воркеров и порядка завершения задач; seed из stable hash записи ⊕ `global_seed` (A2).
  - **Реализовано:** `sampler.py`, `bucket_sample_size` в `core/settings.py` (доменная политика — влияет на границы бакетов, значит входит в хэш состояния §30).
  - **Решения этого шага:**
    - взят **priority sampling**, а не классический алгоритм R. Алгоритм R идёт по потоку с одним общим генератором, поэтому зависит и от порядка записей, и от нарезки потока между процессами — собрать из четырёх воркеров тот же ответ, что у одного, там невозможно в принципе. Здесь каждая запись получает ключ только из себя и `global_seed`, а в выборку идут `k` наименьших: результат равен `sorted(все ключи)[:k]`, и §29 п.5 становится арифметическим фактом, а не свойством, за которым надо следить;
    - слияние воркеров — то же взятие `k` наименьших из объединения. Значения, отброшенные при уплотнении буфера, потерять нельзя: каждое больше всех `k` оставшихся и в итог не попало бы ни при каком порядке;
    - совпадение приоритетов разрешается `record_key`, а не порядком поступления;
    - `MISSING` в выборку не попадает (§19.1) — отсеивается здесь, а не в §19: к моменту fit уже не из чего понять, почему значения нет;
    - сырое значение (строка до §17) в выборку не пускается вовсе: сэмплер работает после NumericValidator, и молча пропустить неразобранное число значило бы посчитать границы по части данных.
  - **Пересмотр A2.** Первая формула (простой XOR с `global_seed`) прошла все тесты 1.2 и была неверной по существу: seed занимает младшие биты, а порядок выборки задают старшие. Замер на 20 000 ключей — пересечение выборок при соседних seed **500 из 500**, то есть «повторим с другим seed» давало тот же самый эксперимент. После умножения seed на нечётную константу золотого сечения — **0 из 500**. `hash_policy_version` → 1.1.0, замороженный эталон `reservoir_seed` в тесте обновлён (он и поймал изменение).

- [x] **2.13 `Bucketizer`** — §19, §2.1, §2.2
  - **BUILD (только TRAIN):** fit `bucket_edges` per-field (quantile / equal-width / log-space / business), публикация `bucket_field_domains` и `bucket_metadata`.
  - **ENCODE:** transform + clipping. **Выход поля:** только `bucket_0…bucket_N` или `MISSING`.
  - **Краевые:** `MISSING` и невалидные значения **не участвуют** в fit (§19.1); совпадающие quantile edges → дубли удаляются, фактическое число бакетов фиксируется (§19.3); `value < min_train_edge → lowest_bucket`, `value > max_train_edge → highest_bucket`, новый бакет не создаётся (§19.4); значение вне configured domain → `bucket_domain_violation` (critical); у каждого денежного поля свои edges (§18.3); имена: FX-нормализованные → `<field>_base_bucket`, прочие → `<field>_bucket`.
  - **Реализовано:** `config/bucketization.yaml`, `bucketizer.py`.
  - **Решения этого шага:**
    - BUILD и ENCODE разделены **типами**, а не соглашением: `fit_bucket_edges` — функция, возвращающая замороженный артефакт, а у класса `Bucketizer` нет метода `fit` вовсе. Посчитать границы на Validation, Test или на одном примере (§27) им физически нечем;
    - границы хранятся **строками десятичных дробей**, а не float. Значение ровно на границе должно попадать в один и тот же бакет всегда, а двоичная дробь этого не гарантирует. §29.1 п.4 фиксирует формат float для случаев, когда float используется; здесь он не используется;
    - интервалы левозамкнутые `[edge[i-1], edge[i])`, конвенция зафиксирована и проверена на границе;
    - квантильная граница берётся как **значение выборки** в позиции квантиля, а не интерполяция между соседями: интерполяция породила бы границу, которой в данных нет, и дробную границу на целочисленном поле;
    - clipping (§19.4) происходит сам — сравнение с границами так и работает, новый бакет создать неоткуда. Смысл §19.4 в том, чтобы это **заметить**, поэтому считаются `numeric_clip_rate` и раздельные low/high счётчики (§19.5);
    - метка вне опубликованного domain (§33.4) — блокирующая ошибка: по построению это невозможно и означает, что границы и `bucket_field_domains` приехали из разных BUILD;
    - поле без единого валидного значения в выборке — блокирующая ошибка, а не «один бакет»: молчаливый один бакет спрятал бы сломанный источник.
  - **Наблюдение о проверке clipping:** на полной выборке clipping структурно невозможен — `min_train`/`max_train` взяты из тех же данных, что потом размечаются. Настоящий случай — ENCODE видит значения, которых BUILD не видел, поэтому проверка гоняет BUILD по усечённой выборке. На ней clipping и проявился: `amount_base_bucket` 15 low / 102 high.
  - **§19.3 на реальных данных:** `screens_count_bucket` — запрошено 32 бакета, фактически 8. Значения целые и их мало, поэтому квантильные границы совпали, дубли удалены, фактическое число зафиксировано и опубликовано.
  - **Отложено:** методы `log_space` и `business_defined` из §19.2 не реализованы — ни одному полю они не нужны, а неиспользуемая ветка расчёта границ молча дала бы неверные edges при первом применении. В `BucketMethod` их нет, поэтому объявить такой метод в конфиге нельзя. Выбор числа бакетов «по Validation» (§19.2) тоже отложен: Validation-разбиения на этом этапе не существует.

Проверено обратным: цепочка без ProfileBuilder падает на BUILD с «нет ни одного валидного значения», а не выдаёт молча неполные границы.
  - **Инвариант порядконезависимости.** Все шесть признаков §24 — счётчики и минимумы по множеству событий ≤ T. Порядок им не нужен, и это условие переноса, а не совпадение: TimelineBuilder (§13, §26) идёт позже, и признак, которому нужен порядок, получил бы здесь порядок партиций, зависящий от нарезки потока. Закреплено двумя способами: интерфейс аккумулятора видит события по одному и последовательности не получает, а постоянный тест проверяет неизменность под перестановками (включая обратный порядок) — **добавили признак, которому нужен порядок, тест падает**. Чинить надо не тест, а место признака.
  - **Решения этого шага:**
    - `validate_numeric` вынесена в общую функцию: §24 требует `validation` перед `bucketization`, но собственная проверка внутри ProfileBuilder означала бы два места с одним правилом — то, на чём я дважды ловил баги;
    - снимок выбирается `max` по `(timestamp, source_record_id)`: без второго ключа два снимка одним моментом решались бы порядком поступления;
    - клиент без снимка получает профиль с `MISSING` и флагом `profile_snapshot_missing` (§6 п.3). Будущий снимок не берётся — его в потоке нет, §14 отсекла раньше, поэтому «взять последний доступный» и «взять последний до T» это одно действие;
    - у клиента без событий `first_seen_age` — `MISSING`, а не ноль: ноль означал бы «событие сегодня» (§15.3).

- [x] **2.16 `TimelineBuilder`** — §13, §26
  - **Вход:** подготовленные события клиента. **Выход:** единый timeline + `ordering_key`.
  - Сортировка: `timestamp_utc` → `source_priority` → `source_record_id`/`event_id`.
  - **Краевые:** одинаковый timestamp в одном источнике и в разных источниках; порядок не зависит от файла, воркера, времени завершения задачи; timeline сохраняется целиком, truncation — забота токенайзера (§26 п.7).
  - **Реализовано:** `timeline_builder.py` (конфига нет — ранги источников уже объявлены в Source Contract §4, второй источник истины был бы лишним), `tests/test_timeline_builder.py` (18 тестов).
  - **Решения этого шага:**
    - `ordering_key` кладётся в событие (§5 п.7): решение о порядке видно в выходных данных, а не выводится читателем заново из кода сортировщика;
    - ранг печатается фиксированной шириной (`0{6}d`) — иначе строковое сравнение ключа поставило бы ранг `10` перед `9`, и `ordering_key` разошёлся бы с настоящим порядком;
    - `position` проставляется здесь же: §25.1 (`lifetime_first`) нужен именно номер 0, а не «самое раннее время» — при совпадении моментов это разные вещи;
    - событие позже T, без `client_id` или без `source_record_id` — блокирующая ошибка, не карантин: сюда оно может прийти только мимо §12/§14, то есть это баг кода, а карантин предназначен для плохих данных (§34);
    - timeline сохраняется целиком (§26 п.7), обрезка окна не делается — это решение токенайзера о том, сколько истории он видит.
  - **Мутационная проверка:** 12 мутаций, все пойманы, 0 зависших (предел 30 с на запуск). Четыре обязательные — сортировка убрана (12 failed), убран второй ключ (3), убран третий ключ (3), обратный порядок (8).
  - **Третий случай вырожденных данных — и вывод про пределы страховок.** Мутация «убран первый ключ, `timestamp_utc`» сначала пережила все 17 тестов: `source_record_id` строился из того же индекса, что и время (`event(minutes=i, record_id=f"CP-{i:03d}")`), поэтому третий ключ в одиночку воспроизводил ответ первого. Страховка `assert_input_is_not_ordered` при этом честно проходила — вход был перемешан, вырожденность сидела в коллинеарности ключей, а не в порядке входа. Исправлено двумя вещами: идентификатор по умолчанию идёт **против** времени (`anti_chronological_id`), и добавлена вторая страховка `assert_key_is_decisive(records, registry, часть)` — утверждает, что без указанной части ключа порядок обязан измениться. Она обобщает находку на любую пару частей ключа, а не только на попавшуюся; отдельный тест `test_every_part_of_the_key_decides_something` утверждает значимость всех трёх сразу. Сама страховка проверена мутацией: возврат коллинеарности в данные роняет именно её, со своим сообщением. Подробности — в `CLAUDE.md`, раздел «Страховка сторожит конкретное свойство».

- [x] **2.17 `TimeFeatureBuilder`** — §25, §25.1, §25.3
  - **Вход:** timeline + `calendar_timezone`. **Выход:** `hour_of_day_local`, `day_of_week_local`, `lifetime_first`.
  - **Краевые:** локальные час/день считаются в бизнес-таймзоне, **не** из UTC; конвенция Пн = 0; `lifetime_first = true` только на самом раннем известном событии клиента; финальная `delta_from_previous_event` **не** фиксируется (её пересчитывает токенайзер после truncation) — допускается только QA-поле, не model input.
  - **Реализовано:** `time_feature_builder.py`, `tests/test_time_features.py` (13 тестов). Конфига нет: зона приходит с записью из §12, конвенция Пн = 0 задана регламентом, выбирать нечего.
  - **Решения этого шага:**
    - подстановки UTC не существует: событие без `calendar_timezone` — блокирующая ошибка. Ветки «зоны нет → считаем по UTC» нет в коде, потому что она дала бы правдоподобное число вместо ошибки (§25, QA §35 п.8) — вечернее событие стало бы дневным без единого следа;
    - в компонент попадает **имя** IANA, а не смещение: `ZoneInfo` помнит, что Алматы жил в UTC+6 до 2024-03-01, число не помнит (§12.1);
    - `lifetime_first` не назначается, а **выводится** из `position == 0` (§13). Параметра, которым его можно поставить в другое место, нет;
    - первое встреченное событие клиента обязано иметь `position == 0` — иначе обработка останавливается. Это защита от обрезки истории до §25: после неё `position == 0` означал бы начало окна, а не жизни, и флаг соврал бы токенайзеру, который различает `FIRST_EVENT` и `WINDOW_START` именно им (§25.1);
    - `delta_from_previous_event` не считается вовсе, хотя §25.1 разрешает QA-вариант: поля, которого нет, нельзя случайно отдать модели;
    - календарные признаки живут отдельным атрибутом, а не в `fields` — §25.3 запрещает токенизировать их как обычные key/value и тратить на них `max_tokens_per_event`;
    - счётчики `hours_shifted_from_utc` / `days_shifted_from_utc` заведены как **детектор**, а не статистика: они уходят в ноль ровно тогда, когда кто-то начнёт считать признаки из UTC.
  - **Мутационная проверка:** 12 мутаций, все пойманы. Одна выжила с первого раза — «поля родителя переносятся перечислением, теряется `position`»: тесты не проверяли обещание докстринга, что достройка ничего не теряет. Закрыто тестом `test_nothing_from_the_timeline_record_is_lost`, который сверяет **все** поля родителя разом — список полей будет расти, тест нет.
  - **Полный проход 2.1–2.17:** 31093 события, 199 клиентов, `lifetime_first` ровно по одному на клиента и на самом раннем событии; час сдвинут относительно UTC у всех событий, день недели уезжает у 442 ночных. На данных есть 5993 события до 2024-03-01 (самое раннее 2023-08-31), смещения до и после перехода различаются — исторические правила §12.1 исполняются не в теории. Из каждого выхода собирается `CanonicalEvent` — все 13 правил §5 держатся на реальных данных.

- **Зависимость, уходящая в Этап 3:** `time_delta_edges` (§25.2, §27 шаг 13) здесь **не** считаются. §25.2 применяет их после truncation в токенайзере, а fit по TRAIN — работа BUILD (3.2). Решение «кодируется ли delta бакетами вообще» принято: бакеты — см. «Зафиксированные решения».

    - дельта **считается, но не сохраняется**. 2.17 её не считал вовсе — поля, которого нет, нельзя случайно отдать модели; здесь она живёт внутри расчёта границ и в записи не попадает;
    - у первого события клиента дельты нет, и в выборку оно не идёт (тот же принцип, что §19.1). Ноль вместо неё означал бы «предыдущее событие в тот же миг» и сдвинул бы первый бакет на всех клиентах сразу;
    - `FIRST_EVENT` и `WINDOW_START` публикуются отдельным ключом артефакта и в `labels()` не входят: §25.2 и §10.2 токенайзера называют их значениями **вне** обычных границ, и расчётом в них попасть нельзя. В `domain()` они есть — иначе `min_count` токенайзера схлопнул бы их в `RARE` (§2.2);
    - `DeltaSampler` — тот же priority sampling, что у значений полей, намеренно тем же кодом: два алгоритма выборки в одном пайплайне дали бы два разных ответа на вопрос «зависит ли результат от нарезки потока»;
    - **baselines в состояние не входят, `bucket_edges` входят** — и граница между ними не «конфиг против данных». Оба посчитаны из TRAIN. Граница в том, **участвует ли артефакт в преобразовании**: `bucket_edges` применяются к каждому значению и меняют выход, поэтому их подмена обязана менять хэш; baselines ни на одно значение не влияют, их только сравнивают при мониторинге, и включение их в хэш означало бы, что тот же самый пайплайн на других данных объявляется другим пайплайном. Формулировка «хэш зависит от конфигурации, а не от данных» тут неверна и опасна: в токенайзере ровно та же пара — `token_counts_open_set` считается по TRAIN и в `tokenizer_state_sha256` (§24.1) **не входит**, а Vocabulary тоже считается по TRAIN и входит. По критерию «из данных» словарь выпал бы из хэша; по критерию «участвует в преобразовании» — остаётся, потому что именно он превращает значение в `token_id`;
    - `PartitionOrder` содержит `canonical` и `reversed` — третьего значения нет. «Случайный порядок» сделал бы проверку шага 16 невоспроизводимой, а невоспроизводимая проверка хуже отсутствующей.
  - **Шаг 16 выполнен частично, и это заявлено явно.** Проверяется свойство §29 пп. 5–6: BUILD прогоняется по партициям в каноническом и обратном порядке, артефакты сравниваются побайтно. Сравнение процессов (1 воркер против 4, `spawn`) остаётся за 4.1, где оно охватывает и ENCODE; здесь оно дало бы половину проверки под видом целой.
    **Следствие для заморозки:** артефакты BUILD заморожены до полной проверки детерминизма. Пока 4.1 не пройден, `golden_expected` замораживать нельзя — иначе эталон снимется с состояния, которое 4.1 ещё может забраковать. Записано в 4.2.
  - **Мутационная проверка:** 10 мутаций, все пойманы, и каждая — тем тестом, которым задумано (проверял по именам упавших тестов, а не только по красному прогону).

    - «ENCODE не пересчитывает edges» выражено устройством: у `Bucketizer` нет метода `fit`, а `fit_bucket_edges` в ENCODE-пути просто не вызывается. Границы приходят единственным способом — `FrozenArtifacts.load` с диска;

Хэш пересчитывается по текущим конфигам плюс загруженным границам и сверяется с записанным в артефактах, поэтому правка любого YAML после BUILD останавливает ENCODE, а не портит выход молча;

Писать проверку на то, чего нельзя объявить, значит завести код, который никогда не срабатывает, — и однажды принять его срабатывание за ложную тревогу. **Но у невыразимости есть срок:** §2.2 — граница с токенайзером, она защищает от изменений выше по течению, а §13 токенайзера прямо говорит, что BPE/subword может быть добавлена «в отдельной версии архитектуры». Текстовый тип поля — запланированное будущее, а не гипотеза. Поэтому проверяется не текст в каждом значении, а **сама гарантия**: `test_field_type_still_has_no_text_kind` падает ровно тогда, когда в `FieldType` появляется новый тип. Сторож на конкретное событие в одну строку, а не мёртвый код;
    - `OutputContractReport` считает, сколько значений проверено: «контракт прошёл» на пустом потоке не значит ничего, и счётчик — единственный способ отличить работающую проверку от отработавшей вхолостую.
  - **Найдено прогоном:** справочные записи курсов (1250 штук) шли в отчёте контракта как профили — их 200. Ни одна проверка от этого не падала, а число клиентов в отчёте выглядело завышенным втрое. Заведён отдельный счётчик `reference`. В `prepared_*` этим записям места нет — исключает их 3.4.

На настоящем артефакте через float портятся 247 границ из 315: квантильная граница это значение выборки, поэтому среди них целые (`294` → `294.0`) и суммы с хвостовым нулём (`2500.50` → `2500.5`). Данные теста были аккуратнее реальных и потому слабее. Подробности — в `CLAUDE.md`, случай 4.

Тихая ложь, вскрывающаяся позже всего. Поэтому основной пункт — `code_state_sha256` по каноническому списку файлов `src/`, `tools/`, `config/`; коммит и `dirty` идут рядом справкой.     - `deterministic_build_config` собирается из кода и настроек, а не переписывается руками, и содержит прямой список того, что в хэш **не** входит — вопрос «почему хэш не изменился» задают регулярно.

То есть заморозка BUILD произошла **без** полной проверки детерминизма. Если 4.1 покажет расхождение, чинить придётся код, и эталон, замороженный раньше, окажется снятым с неверного состояния. Порядок: 4.1 зелёный → только потом заморозка `golden_expected`.
  - Этот же набор закрывает требуемые `CLAUDE.md` краевые случаи (FX→KZT, clipping, tie-break, MISSING, дедупликация) — по §29.2 они входят в `golden_input` по построению, отдельных тестов на них не пишем.
  - `golden_expected` — это вход `golden_prepared` токенайзера (tokenizer §14.4.3): сквозная цепочка raw → token_id соберётся позже без переделки.

- [ ] **4.3 Content hash** — §30, §35 F.38–F.40
  - Проверить: hash рассчитывается по канонически сериализованному состоянию; при загрузке артефактов сверяется; при несовпадении обработка **блокируется**, а не продолжается с предупреждением; output metadata содержит все версии §30.
